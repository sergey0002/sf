# Поток `docs-only` для `docs`

Следуйте выбранному потоку и возобновляйтесь с первого незавершённого шага. `stageN/` обозначает текущую итерацию.

1. `architecture-context` — Примените `architecture-read`. Возьмите применимые правила манифеста и проекта, `related_docs`, точные разделы контрактов и действующие ADR. В плане запишите источник, правило, что сохранить или изменить, и как проверить. Если правило конфликтует с задачей, уточните его до затронутой правки.
2. `change` — По `architecture-docs` исправьте нужный документ, скилл или конфигурацию документации. Сверьте содержание с источником правила и проверьте затронутые ссылки.
3. `validate` — Выполните подходящие структурные проверки. При изменении источников индекса проверьте его свежесть, пересоберите и проверьте результат.
4. `close` — Сверьте критерии и актуальные результаты, проверьте обязательных детей. Примените правила одобрения текущей задачи. Выполните закрытие по `go-to-task`.

Для новой карточки используйте `acceptance_policy: "case-coverage-v1"`. Запускайте кейсы приёмки через `task evidence --run`: команда сценария и фактически запущенная команда должны совпадать. Не меняйте exit code, хеши или диагностику вручную. Красный прогон остаётся `failed`, а задача может оставаться в фазе `verification`. Устаревшие и неполные результаты требуют повторной проверки.

Для `docs-only` с этой политикой `diagnose` и `close` после проверки кейсов и снимка заново проверяют архитектуру, индекс и объявленные пути. Запись чужой успешной команды не заменяет эти проверки.
