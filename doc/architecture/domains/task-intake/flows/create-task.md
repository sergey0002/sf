# Поток создания задачи

## Назначение и возможность

Превратить один внешний/ручной запрос в рабочее пространство задачи, осведомленное об источнике, с каноническим `task.json`.

## Триггер, участники и задействованные системы

Пользователь, источник трекера или чата, адаптер/CLI, скилл агента и рабочее пространство задачи. Точные продукты/протоколы не указаны.

## Предусловия и авторизация

Существует настроенный источник или запрос в ручном чате. Разрешения на чтение трекера и пути рабочего пространства — явная конфигурация проекта; не определены в этом примере.

## Основные и альтернативные пути

| Path ID | Охрана/событие | Актёр | Действие/побочный эффект | Исход | Отказ/следующий шаг |
|---|---|---|---|---|---|
| FLOW-create-task-P1 | Запрошена задача трекера | Адаптер CLI | Извлеките точные поля/комментарии/вложения; сохраните ссылки на ревизию/снапшот источника | Доступны необработанные доказательства источника | Отказ адаптера/API сообщается; задача не создаётся молча |
| FLOW-create-task-P2 | Запрос человека в чате | Скилл агента | Интерпретируйте намерение, идентифицируйте блокирующую неопределённость и задайте вопросы | Уточнённые семантические поля | Ждите ответов при блокировке; не позволяйте CLI делать выводы |
| FLOW-create-task-P3 | Достаточно известных данных для создания ввода | Скилл агента | Создайте осведомлённый об источнике `task.json` | Кандидат на канонический ввод | Неизвестные поля остаются явными/неустановленными только там, где разрешено |
| FLOW-create-task-P4 | JSON предоставлен | CLI | Валидируйте схему/пути/ID и создайте безопасное рабочее пространство/шаблоны | Рабочее пространство задачи создано | Ошибка схемы или идентичности останавливает; никакой обратной записи в трекер по умолчанию |

## Данные и ссылки

Каждый кандидат на задачу должен иметь ровно четырёхзначное `task_number`; детерминированный ключ — чистый для Jira, с префиксом `UI-` для ввода пользователя/UI, и явно с префиксом для любого другого источника. CLI только валидирует/выводит: он не выделяет числа. Глобальное выделение чисел/уникальность и итоговая схема не стандартизированы еще. `task.json` — единственный канонический нормализованный ввод задачи; необработанный снапшот источника и вложения остаются отдельно идентифицируемыми доказательствами.

## Приёмка постановки

| Условие | Действие и результат |
|---|---|
| Источник и наблюдаемый результат однозначны | Укажите потребителя, текущее поведение, дельту и то, что должно сохраниться. По [architecture-read](../../../../skills/architecture-read/SKILL.md) выберите контракт и свяжите его точный раздел с критериями и тестом. |
| Вопрос меняет результат, scope, полномочия или оракул | Уточните выбор владельца. Сохраните принятый вариант с источником. До решения блокируйте затронутый сценарий. |
| Поведение меняется | Дайте AC и отдельный обязательный `CASE-N` для каждого применимого варианта. Для случая укажите состояние до, публичный вызов, точные ожидаемые выходы и состояние после. Для совместимости и отказа задайте явные постусловия. |
| Несколько независимо проверяемых результатов | Свяжите каждый результат ребёнка со сценарием родителя и его точным входом. Проверьте зависимости, порядок интеграции и итоговый сквозной сценарий. |
| Карточка и стадия готовы | Сверьте цепочку `источник → изменение → AC → CASE → проверка` с точки зрения модели без доступа к чату. Затем проверьте структуру через CLI. |

Для локальной задачи достаточно одного точного сценария. Существенное изменение контракта требует сценариев совместимости и фактически релевантных отказов. Не размножайте артефакты между `task.json`, планом и верификацией. В первом находятся требования, в плане — оракул и порядок, в верификации — идентификаторы сценариев и результаты. [Контракт верификации](../../task-lifecycle/entities/verification-evidence.md)

### Пример из UI-0012

Фраза «`index build/check` работают на перенесённом корне» позволяла обеим командам проходить с одним ошибочным путём. Проверяемый сценарий задаёт чистую fixture без индекса, `roots.architecture: handbook` и `roots.index: cache/catalog.json`. После запуска `index build` из другого cwd должно появиться ровно `handbook/cache/catalog.json`. В корне и в прежней раскладке индекса быть не должно. Для ошибочной конфигурации добавьте отдельный случай с конкретным exit code и сравнением дерева до и после. В историческом аудите также видны поздний сквозной прогон и повторные чтения широких файлов. Один исполнимый сценарий до массовой правки выявляет ошибку раньше. Путь к матрице и карточке аудита задаётся конфигом проекта. Начните с `arch task diagnose UI-0012 --json --brief`, затем откройте план и `research_docs` карточки.

### Что перенесли из справочников `data`

- **Spec Kit** — уточнение пропусков, проверка качества требований и read-only сверка связности перед реализацией. В фабрике всё укладывается в один проход по трём существующим артефактам. [Spec Kit](<../../../../../data/sdd-encyclopedia/Инструменты/GitHub Spec Kit.md>)
- **OpenSpec** — у изменения действующей системы есть явно описанная дельта. Сценарии проверяют новую спецификацию, а изменение канонического контракта связывается с результатом. [OpenSpec](<../../../../../data/sdd-encyclopedia/Инструменты/OpenSpec.md>) · [Delta Specs](<../../../../../data/sdd-encyclopedia/Сущности/Delta Specs.md>)
- **Kiro / EARS и контракт задачи для агента** — формулировка «дано / когда / тогда» с наблюдаемым утверждением, границей записи и действием на отказ. [Kiro](../../../../../data/sdd-encyclopedia/Инструменты/Kiro.md) · [Контракт задачи для агента](<../../../../../data/machinedocs-encyclopedia/Практики/Контракт задачи для агента.md>)
- **Контекст и evals** — исполнитель читает карточку и нужные ссылки, затем раскрывает контекст при конкретном пробеле. На одинаковых входах сравнивайте отдельные прогоны постановки и реализации. Для постановки измеряйте пропущенные требования, долю проверяемых сценариев и пригодность карточки для нового исполнителя. Для реализации измеряйте приёмку с первого раза, число повторов, вызовы до первого целевого теста и `input`/кэш отдельно. Контрольный набор должен содержать чистый happy path, совместимость и намеренно дефектный вариант. [Progressive Disclosure](<../../../../../data/cli-skills-encyclopedia/Форматы/Progressive Disclosure.md>) · [Evals](<../../../../../data/machinedocs-encyclopedia/Практики/Evals и метрики агентной разработки.md>)

## Явные исключения

Нет автоматических обновлений трекера, семантической классификации в CLI, вывода полноты задачи или выбора релиза.
