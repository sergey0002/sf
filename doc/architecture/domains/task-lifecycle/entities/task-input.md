# Канонический ввод задачи

## Назначение

Захватите намерение пользователя и происхождение в переносимой, машино-валидируемой записи `task.json` для последующего выполнения.

## Концептуальная информация

- версия схемы, требуемое `task_number` из четырёх цифр, `source.type`, опциональный префикс источника и детерминированно выведенный `task_key`;
- тип источника, нативная идентичность и происхождение/ссылки;
- заголовок, намерение, область, явные исключения, критерии приёмки/ссылки на оракул;
- ограничения, допущения, нерешённые вопросы, ссылки на контекст;
- целевой репозиторий/релиз только когда явный и проверенный; требования одобрения/разрешения;
- жизненный цикл `phase` (intake → … → completed) и отдельная ось исполнительного `status` (`open`, `in_progress`, `paused`, `blocked`, `review`, `done`, `cancelled`, `rejected`); `status` не подменяет `phase`;
- `target_release`, рабочая ветка `branch` и ветка мерджа `release_branch`; значения по умолчанию берутся из `project.release` в `paths.yaml`, ребёнок наследует ветку родителя.

## Контракт именования

- `task_number` — ровно четыре десятичные цифры и требуется.
- Ключи Jira — чистый номер (`1234`); ключи ввода пользователя/UI — `UI-1234`; каждый другой источник требует явного настроенного префикса, такого как `GH-1234`.
- CLI ведёт JSON-реестр; для `source: ui` команда `task new` выделяет следующий свободный номер, создаёт задачу и добавляет запись. Дублирующийся или отсутствующий идентификатор останавливает создание задачи. Глобальная уникальность между источниками не решена.

## Инварианты

- Это единственный канонический ввод задачи; не создавайте task.md вручную.
- Исходный ввод неизменим после начала выполнения; поправки — явные, прослеживаемые версии/дельты.
- Структурная валидность отличается от семантической полноты и одобрения.
- Скаффолд `task new`/`task init` валиден для `task validate` сразу: тип и flow выбирает агент, а обязательные поля получают дефолты из конфига, а не `unset`.
- Новое обязательное поле вводится только вместе с дефолтом скаффолда, миграцией существующего корпуса и тестом `init → validate`.
- Тип задачи выбирается по характеру работ; смена типа ради обхода `subtask_policy` запрещена — нужна декомпозиция.

## Статус контракта

Продакшн JSON Schema не выбрана. Этот концептуальный список не является最終ным точным полевым контрактом.
