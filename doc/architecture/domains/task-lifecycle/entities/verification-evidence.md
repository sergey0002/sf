# Запись доказательств верификации

## Значение домена и граница

Ссылконосящая запись того, что фактически было проверено на этапе задачи. Это доказательство, а не утверждение, что требование продукта семантически удовлетворено.

## Значимые атрибуты, описанные манифестом

- Точная команда/селектор теста и соответствующая конфигурация.
- Код выхода и краткая диагностическая сводка.
- Проверенный коммит кода или явное состояние рабочего дерева.
- Ссылки на артефакты доказательств (логи, следы, отчёты), хранятся отдельно, если велики.
- Статус, такой как pass/fail/not run, только когда схема это определяет; `not run` никогда не является pass.
- Исходная задача/этап и время верификации/идентичность исполнителя только по требованию итоговой схемы.

## Инварианты {#invariants}

- Не сообщайте о тесте как пройденном без захваченного результата.
- Доказательство должно идентифицировать состояние, которое было проверено.
- Самоотчёт агента не является независимым оракулом.

## `case-coverage-v1` {#case-coverage}

Политика включается полем `acceptance_policy: "case-coverage-v1"` в карточке. Новые поведенческие задания и их технические дети используют её при постановке. Для карточек без этого поля действуют существующие проверки закрытия.

| Где | Поля и проверка |
|---|---|
| `task.json` | Уникальные критерии в форме `AC-N: наблюдаемый результат`. |
| Последний числовой `stageN/plan.md` | Маркер `<!-- plan-tier: micro|standard|full -->`, вход, действие, независимое ожидание и проверка каждого случая. |
| `verification.json` до запуска | Фактические `task_key` и `stage_id`, `status: not_run`, `checked_revision: null`, `checks: []`. Каждый `planned_checks[]` содержит уникальный `id: CASE-N`, непустой `covers` из существующих AC и `expected`. Объединение `covers` покрывает все AC. |
| `verification.json` после запуска | `status: passed`, идентификатор `checked_revision`, `snapshot_files: [{path, sha256}]`. Пути проектно-относительные. Добавьте план и входы, от которых зависит проверка. Каждый последний результат обязательного случая назван в `checks[].cases` и содержит `command`, `exit_code: 0`, `result`. Для общей проверки `cases` оставляют пустым. |

`task diagnose` возвращает `acceptance_plan_ready` при такой политике. `task subtask validate` проверяет готовность плана ребёнка. `task close` и `--dry-run` используют те же блокировки, что диагностика. Закрытие проверяет доказательства текущей стадии, обязательные кейсы, SHA-256 заявленных файлов и применимые доказательства закрытых детей. Готовность плана и проверка хешей оставляют оценку оракула, полноту списка входов и одобрение владельцу и агенту. Изменение реализации, плана или тестов после проверки требует новой верификации. Обязательные разделы, tier и шаблоны плана — в [plan-task](../../../../skills/plan-task/SKILL.md).

Свежесть снимка отделена от факта закрытия. `diagnose` и `doctor` возвращают `evidence_freshness.status` (`current`, `stale`, `missing`, `unknown`) и `stale_files`; для `phase: completed` несовпадение сопровождается пояснением, что историческое закрытие записано, а текущее дерево отличается от проверенного снимка. Это пояснение не снимает блокировку нового закрытия: устаревший обязательный снимок нельзя использовать как доказательство текущего состояния.

Политика tier'ов читается из `task plan-policy`: дефолты `plan-defaults.yaml` дополняются блоком `plan` выбранного типа. Обязательные разделы и правила приёмки берутся из разрешённой политики; неизвестный tier, несовместимая сложность и нарушенное структурное правило блокируют готовность. Flow политику не переопределяет. Tier плана проверяется структурно и не зависит от модели. Соответствие tier сложности, лимит непустых строк и обязательные разделы задаёт сама политика типа, а не фиксированная таблица: `micro` обычно ограничен `low`, но точный набор читается из `plan-defaults.yaml` и блока `plan`. Для каждого tier проверяется наличие обязательных разделов по ключевым словам заголовков, а safety floor (покрытие AC, точная команда, откат) действует всегда: правила типа дополняют floor, а не заменяют его. Правила с `applies_to` действуют только на перечисленных tier'ах, поэтому `micro` может оставаться лёгким. Маркер обязателен, когда в карточке задан `estimate_hours`; план без маркера сохраняет прежнее поведение и не оценивается правилами типа. Неизвестный или несовместимый tier делает `acceptance_plan_ready: false`.

Для родительских задач `docs/docs-only` с этой политикой, если остальные условия закрытия выполнены, `diagnose`, `close --dry-run` и `close` выполняют структурные проверки архитектуры с индексом и объявленных путей на текущем дереве. Записанная команда или статус в evidence не заменяют эти проверки. Для версионированной карточки этой группы переход в `completed` доступен через `task close`, а не через `task event`. Существующие карточки без политики не мигрируют автоматически.

## Сбор результата через CLI {#capture}

Текущий CLI поддерживает чтение и фиксацию результата. `arch task evidence <key> --check` сравнивает SHA-256 на текущей стадии и возвращает `data.status` (`current`, `stale`, `missing`), `data.stale_files`, `data.missing_files` и `data.problems`; exit 1, если снимок не `current`. `arch task evidence <key> --file <path> [--file <path> ...] [--case CASE-N ...] --run <program> <args>` запускает явно переданные аргументы из корня проекта. План автоматически добавляется к проектно-относительным входам. Результат записывается только если файлы, карточка и запись evidence сохранились между началом и публикацией. При неуспешном процессе CLI возвращает его реальный exit code и короткую диагностику.

`--replace-snapshot` разрешает заменить результаты старого снимка, сохранив план. При повторе на том же снимке сохраняются результаты других команд и кейсов. `checked_revision` идентифицирует набор путей и содержимое. Применимость оракула устанавливается по контракту и ревью.

`arch task baseline <key> --file <path> --run <argv>` пишет `stageN/baseline.json` с командой, exit code и хешами входов до изменения. Baseline служит исходной точкой для сравнения и аудита, не подтверждает AC и не блокирует закрытие. Если вход изменился во время запуска, запись отклоняется.
