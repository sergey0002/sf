# Работа с задачами фабрики

Команды ниже запускаются из корня проекта. `arch` означает `python3 doc/tools/arch/__main__.py`. [Дорожная карта](../nextplan.md) описывает будущие возможности.

Для работы с командами откройте [arch-cli](skills/arch-cli/SKILL.md) и при необходимости точный `--help`. **При обычном использовании не читайте реализацию CLI.** Исходники нужны, когда задача меняет CLI или диагностирует воспроизводимое расхождение. Тогда найдите конкретный символ и загрузите нужный диапазон строк.

## Сначала выберите режим

| Запрос | Действие |
|---|---|
| Создать задачу или разложить план на карточки | Прочитать [create-task](skills/create-task/SKILL.md). Результат — проверенные карточки и планы. |
| Перейти к задаче и подготовиться к выполнению | Использовать путь подготовки в [go-to-task](skills/go-to-task/SKILL.md). Результат — план и готовность к старту. |
| Выполнить, продолжить или проверить задачу по ключу | Прочитать [go-to-task](skills/go-to-task/SKILL.md). Открыть карточку по точному ключу. |
| Только объяснить, исследовать или провести аудит | Проверить источники и сообщить вывод. Создавать карточку по запросу на её регистрацию. |
| Зафиксировать результаты обсуждения | Прочитать [document-session](skills/document-session/SKILL.md). |
| Найти или разобрать прошлую сессию Kilo Code | Прочитать [kilo-session-audit](skills/kilo-session-audit/SKILL.md). Подтвердить нужную сессию и анализировать её по локальному журналу. |
| Определить действующий архитектурный контракт для задачи | Применить [architecture-read](skills/architecture-read/SKILL.md). Взять нужный раздел и связать его с планом и проверкой. |
| Проверить diff реализации перед верификацией | Применить [review-implementation](skills/review-implementation/SKILL.md). Передать стабильный снимок, точные критерии и нужные контракты. |
| Меняется каноническая архитектура | Дополнительно прочитать [architecture-docs](skills/architecture-docs/SKILL.md). |

[Каталог скиллов](skills/README.md) — источник условий вызова. Загружайте применимые навыки и документы по ссылкам.

Для новой задачи с изменением поведения используйте `case-coverage-v1`. Если `task diagnose` сообщает `acceptance_plan_ready: false`, сначала восстановите трассировку AC и сценариев. При точном ключе начинайте с `refs` и одного целевого сценария.

## Какой источник отвечает на вопрос

- **Цель, границы, критерии и зависимости** — `task.json`, уточнения владельца и план текущей стадии. При существенном расхождении остановите затронутый шаг и уточните контракт.
- **Допустимые пути, типы и flow** — [paths.yaml](config/paths.yaml), YAML выбранного типа и потока. Prompt объясняет способ выполнения. Путь из дорожной карты сначала сверяйте с текущей конфигурацией.
- **Текущее поведение** — фактический прогон и тесты. При изменении реализации используйте граф кода или точечный поиск и сверяйте найденный символ с исходником. **Принятое архитектурное решение** — применимый контракт, flow или ADR, найденный через [architecture-read](skills/architecture-read/SKILL.md).
- **Справочные практики** — [MOC в data/](../data/README.md) → оглавление области → нужный раздел. Используйте при конкретном вопросе. Вывод со ссылками храните в задаче. `data/` служит справочником при работе над фабрикой.

## Цикл выполнения

1. **Проверьте вход.** `git status --short` и `arch task diagnose <key> --json --brief`. При блокировках раскройте полный вывод. Прочитайте указанные карточку и план, затем только нужные prompts и зависимости. Для проверки карточки отдельно есть `task validate`.
2. **Сопоставьте результат и проверку.** Для каждого AC родителя и детей определите fixture, действие, наблюдаемый исход и состояние после операции. Проверьте, что целевой сценарий различает исходное поведение и требуемое. При известном ключе открывайте релевантные символы и диапазоны строк. Полный roadmap и соседние карточки нужны для обзора или когда на них ссылается задача.
3. **Сделайте ограниченный срез.** Сохраните чужие изменения. Если изменения пересекаются с вашей задачей и безопасно отделить их нельзя, уточните дальнейшие действия. При изменении контракта обновите ближайшие тесты и документацию, которую это затрагивает.
4. **Проверьте итог.** Сначала целевые проверки, затем один итоговый компактный прогон. Запишите в `stageN/verification.json` фактические команды, исходы, AC и проверенный снимок. Снимок относится к коду и входам, которые действительно проверялись. Для пропуска укажите затронутый AC и следующий проверяемый шаг. Проверьте итоговый diff.
5. **Закройте по результату.** Проверьте каждый обязательный AC, объявленные подзадачи, актуальность результатов и требуемое одобрение. Подтвердив эти условия, используйте `arch task close <key>`. Неполная проверка или ожидание владельца отражаются в статусе задачи.

Для локальной правки с ясным результатом достаточно прочитать карточку и один затронутый контракт, найти нужный символ, выполнить целевую проверку до и после изменения, затем собрать итоговое evidence. Расширяйте чтение при конкретном пробеле. Повторный прогон имеет смысл после изменения кода, данных проверки или окружения. При итоговой проверке фабрики используйте `bash doc/tests/run.sh --brief`. Он проверяет существующий индекс и раскрывает вывод только провалившегося шага.

## Инварианты

- Единственный вход — `task.json`. Используйте `stageN/plan.md` и `stageN/verification.json`, где они нужны. Номер выдаёт владелец или утверждённый реестр. UI использует `UI-NNNN`, Jira — `NNNN`, иной источник — зарегистрированный префикс.
- Исходный intent, scope и критерии во время реализации меняются только явным уточнением. Технические результаты записываются в стадию и в существующие поля состояния. Новые пути проверяйте по `allowed_paths`.
- Для локальной работы используйте известный checkout в пределах scope. `task workspace` выдаёт метаданные и подсказку ветки. Отдельная среда нужна по условиям задачи. Целевую ветку и релиз уточняйте, когда от них зависит нужное действие.
- Push, merge, deploy и запись во внешний трекер выполняются по явному разрешению. CLI выполняет структурные проверки, агент оценивает смысл и сообщает, чего не удалось подтвердить.
