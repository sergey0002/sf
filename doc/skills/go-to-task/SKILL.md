# Выполнение зарегистрированной задачи

Команды и приоритет источников описаны в [doc/AGENTS.md](../../AGENTS.md).

1. Откройте точный ключ. A top-level task uses four digits with the source-specific prefix rules. Для родителя используйте `arch task validate <key>` и `arch task diagnose <key> --json`. Для непосредственного ребёнка используйте `arch task subtask validate <parent> <id>` и `arch task subtask status <parent> <id>`. Прочитайте его запись и ссылки из родителя.
2. Сверьте `depends_on` с фактическими карточками. Для дочернего ключа откройте запись ребёнка по пути родителя. Незавершённая, отсутствующая или невалидная зависимость блокирует затронутую работу. Назовите ключ и причину. Выполнение отдельной задачи-зависимости требует, чтобы она входила в поручение.
3. Выберите незавершённую стадию по плану, истории и evidence. Прочитайте выбранные type/flow prompts и только нужные контракты. Помните, что `diagnose` и `close` сейчас не проверяют все зависимости и доказательства. `target_release: unset` допустим для локального изменения, которому не нужен целевой релиз.
4. Проверьте рабочее дерево и границы проверки. Сопоставьте `scope`, `authority`, требования и AC с исходниками. Подтвердите baseline для значимого изменения. Если нужен выбор подхода, проведите точечное исследование и запишите решение в плане или исследовательской заметке по разрешённому пути.
5. Выполните план в согласованном scope. Для значимого изменения архитектуры согласуйте затронутый контракт по [architecture-docs](../architecture-docs/SKILL.md). При изменении требований или области сначала запишите уточнение и соответствующее решение.
6. Запустите релевантные проверки. Для задачи с CLI используйте обычную точку входа и нужные успешные и отказные сценарии. Для архитектуры проверьте структуру, пути и свежесть индекса. Сначала запустите `index check`, если оценивается свежесть существующего индекса. Пересобирайте индекс отдельным действием при обоснованном изменении источников.
7. Запишите в verification проверенный commit или идентификатор снимка diff, команды, исходы и покрытые AC. Для части, которую нельзя проверить, укажите ограничение. В `task.json` обновляйте фактические поля состояния и ссылки, сохраняя исходный контракт и происхождение.
8. Перед закрытием вручную сопоставьте каждый обязательный AC с результатом, сверяйте объявленных детей с их записями и проверьте применимость одобрения. `can_close: true` может появиться уже в `intake` и подтверждает только текущую проверку каталогов детей. Состояние ребёнка берите из его `task.json`. У CLI есть `task close` для родителя, отдельного `subtask close` пока нет. Статус ребёнка обновляйте по существующему формату только после его приёмки. Если завершение ещё не подтверждено, укажите текущую стадию и конкретный блокер в handoff.
