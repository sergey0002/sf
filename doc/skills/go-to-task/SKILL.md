# Выполнение зарегистрированной задачи

Приоритет источников описан в [doc/AGENTS.md](../../AGENTS.md). Формат, коды и побочные эффекты команд описаны в [arch-cli](../arch-cli/SKILL.md).

Для выбранного потока получите порядок через `arch task flow-steps --type <type> --flow <flow>`. По плану и evidence найдите первый незавершённый шаг и загрузите его через `arch task flow-prompt --type <type> --flow <flow> --step <id>`. На переходе сверяйте `gate` и результат шага. Общий `flow-prompt` открывайте для обзора или если нужны общие инструкции потока.

Для составной записи проверяйте один рискованный переход до массовых правок. Составьте fixture на границах публикации журнала, записи дочерних и родительской записей, удаления журнала. Для отказа сравните пути и байты всего затронутого дерева. Случаи повторной записи включают поздний конфликт, повреждённый журнал и временный остаток. При одновременных правках приёмку привяжите к стабильному снимку. Повторяйте полный набор при изменении проверяемого снимка или условий, с которыми связан провал.

На шаге `architecture-context` проверьте применимые правила проекта по [architecture-read](../architecture-read/SKILL.md). Начните с `related_docs` и `project_context_refs`. Запишите блок `Правила проекта` в плане. На `architecture-sync` сопоставьте его с diff и примените [architecture-docs](../architecture-docs/SKILL.md), если есть изменение канонического описания. На верификации проверьте эти же правила на итоговом снимке. Для flow без отдельных шагов используйте этот порядок только в части, относящейся к цели задачи.

Если пользователь просит **перейти к задаче, ознакомиться или подготовиться к выполнению**, используйте путь подготовки. Прочитайте запрошенные входы, найдите AC, зависимости и целевые проверки, при необходимости снимите baseline командами без записи. Верните краткий план, риски и готовность. Реализация, генерация индекса и смена фазы начинаются по поручению на соответствующее действие. Если пользователь явно поручил реализацию, переходите к шагам ниже.

1. Откройте точный ключ. A top-level task uses four digits with the source-specific prefix rules. Для родителя начните с `arch task diagnose <key> --json --brief` и откройте файлы из `refs`. Если блокировки обрезаны, повторите без `--brief`. Для непосредственного ребёнка используйте `arch task subtask validate <parent> <id>` и `arch task subtask status <parent> <id>`.
2. Возьмите зависимости из `diagnose`. Откройте карточку конкретной зависимости, если нужно разобрать сообщённую причину или проверить разрешённый входной снимок. Незавершённая, отсутствующая или невалидная зависимость блокирует затронутую работу. Выполнение отдельной задачи-зависимости требует, чтобы она входила в поручение.

   `diagnose` и `close` используют общие блокировки `depends_on`. Если владелец разрешил реализацию поверх незавершённой зависимости, зафиксируйте разрешение и точный снимок входа в плане. Блокировка закрытия сохраняется до завершения зависимости.
3. Выберите незавершённую стадию по плану, истории и evidence. Прочитайте промпт типа, промпт текущего шага и нужные контракты. Помните, что `diagnose` и `close` сейчас не проверяют все зависимости и доказательства. `target_release: unset` допустим для локального изменения, которому не нужен целевой релиз.
4. Проверьте рабочее дерево и границы проверки. Сопоставьте `scope`, `authority`, требования и AC с затронутыми контрактами. В плане сопоставьте каждый AC родителя и детей с конкретной проверкой. Для уже заведённой задачи уточните в плане fixture, действие и оракул, сохраняя исходные критерии. До массовых правок проверьте один сценарий через публичный вход, который обнаруживает дефект или отсутствие нового поведения. Когда baseline недоступен, запишите причину и проверяемый альтернативный источник.

   Если `acceptance_plan_ready: false`, восстановите связь `AC → CASE → оракул`. Начинайте запись лишь после устранения пропусков в затрагиваемом сценарии. При воспроизводимой неоднозначности требования используйте владельца, когда выбор изменит контракт. Стабильность оракула проверьте до правки: модель должна увидеть отказ исходной реализации либо явное обоснование альтернативной проверки.
5. Выполните план в согласованном scope. Для значимого изменения архитектуры согласуйте затронутый контракт по [architecture-docs](../architecture-docs/SKILL.md). При изменении требований или области сначала запишите уточнение и соответствующее решение.

   Перед записью сравните `git status --short` и diff с конкретными файлами плана. Непересекающиеся правки сохраняйте. При пересечении используйте отдельный worktree на нужной базе или явно согласованный стабильный снимок. Если нужная зависимость существует только в рабочем дереве, сначала включите её согласованные версии в базу. При `review-implementation` примените [скилл ревью](../review-implementation/SKILL.md).
6. Для CLI используйте исходный entry point с `--root` на временной валидной fixture. Переиспользуйте `_cli_at` в `doc/tests/test_task_identity.py`. Проверяйте stdout, stderr и код процесса отдельно. Для отказа или preview сравните байты до и после. Сначала запустите целевой тест, полный набор — на итоговом срезе. Для архитектуры проверьте структуру, пути и свежесть индекса до его пересборки.
7. Запишите в verification проверенный commit или идентификатор снимка diff, команды, исходы и покрытые AC. Явно укажите отказавший или непроверенный обязательный AC. При таком результате сохраните состояние незавершённой работы и зафиксируйте следующий целевой шаг. В `task.json` обновляйте фактические поля состояния и ссылки, сохраняя исходный контракт и происхождение.

   Для `case-coverage-v1` итоговая стадия содержит все обязательные `planned_checks`. В `checks[].cases` укажите только `CASE-N`, которые команда действительно проверила. Сохраните `command`, целочисленный `exit_code` и `result`. В `snapshot_files` включите путь и SHA-256 `plan.md`, проверенных контрактов, изменённой реализации и целевых тестов. Веса и охват утверждений модели CLI не оценивает. Для независимого ревью выберите самый рискованный кейс и сравните оракул с публичным контрактом, а затем сопоставьте итоговый diff с границами. При изменении оракула зафиксируйте договорённость и снова прогоните затронутый сценарий.

   Используйте `task evidence` для реального запуска и фиксации хешей. Передайте одинаковый список проверяемых файлов для всех проверок итогового снимка. Если снимок сменился, `--replace-snapshot` начинает новую серию с теми же запланированными кейсами и пустыми результатами. Сначала запускайте точный селектор, затем итоговый `run.sh --brief` один раз на стабильном снимке.
8. Перед закрытием проверьте AC и применимость одобрения. `can_close` и `would_close` отражают машинные предусловия. Они могут быть истинны уже в `intake`. Состояние ребёнка берите из его `task.json`. Финальный отчёт должен совпадать с сохранённой фазой: готовность к ревью допускает `verification`, завершение подтверждается `completed`.

При изменении входного конфига или разрешения путей до массового перевода потребителей запустите сквозной тест на чистой fixture с переопределённым значением. Утверждайте фактический путь чтения и записи, отсутствие артефактов в старой локации, обработку ошибочного конфига и неизменность файлов при отказе. Для перемещаемых корней включайте один положительный сценарий и один запрещённый файл в новом корне. При несовместимости с существующими callers сначала локализуйте первый отказ на целевом тесте. Для компактного итога используйте `bash doc/tests/run.sh --brief` или захватывайте вывод и исход процесса раздельно.
