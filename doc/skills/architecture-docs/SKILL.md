# Skill: architecture-docs (строгий регламент архитектурной документации)

## Назначение

Навык обеспечивает жёсткое регулирование структуры `doc/`:
- в `doc/` сохраняются **только задекларированные пути** из `doc/config/paths.yaml`;
- произвольные файлы в документации **недопустимы** и подлежат диагностике;
- любое отклонение от формата или регламента структуры фиксируется CLI-командой `arch docs paths --check`;
- структура и формат дорабатываются только при явной необходимости и с обновлением `paths.yaml`.

Навык не создаёт задачи rétroactivly, не удаляет файлы автоматически и не принимает семантических решений за агента.

## Политика структуры doc/

### Допустимые пути

Единственный источник истины о допустимых путях — `doc/config/paths.yaml` (раздел `allowed_paths`).
- Точные пути (например, `doc/architecture/system/manifest.md`) разрешены как есть.
- Шаблонные пути (например, `doc/tasks/{task_key}/task.json`) разрешены при подстановке валидных значений: `task_key` соответствует `TASK_KEY_RE`, `{stage}` — положительное целое, `{domain}` / `{slug}` — строчные латинские буквы, цифры и дефисы.

### Запрещено

- Любой файл в `doc/`, не совпадающий ни с одним объявленным путём или шаблоном.
- Копии корневого манифеста в `doc/` (манифест един — `doc/architecture/system/manifest.md`).
- `task.md` в любой задаче (единый канонический input — `task.json`).
- Редактирование `data/` как проектных файлов (`data/` — справочный материал вне репозитория).
- Пустые placeholder-файлы и каталоги «на будущее».
- Ручное редактирование сгенерированных файлов (например, `doc/architecture/index.json`).

### Фронтмatter и schéma

Каждый `.md` в `doc/architecture/` должен иметь YAML-фронтмatter со следующими обязательными полями:
- `id` — стабильный уникальный идентификатор документа.
- `type` — один из допустимых `document_types` в `paths.yaml`.
- `title` — человекочитаемое название.
- `summary` — зачем загружать документ.
- `status` — один из `document_statuses`.
- `domain` — для документов домена; системные документы могут иметь `domain: system`.

Опциональные поля — только при необходимости: `related`, `source_refs`, `owner`, `implemented`, `applies_to`, `superseded_by`.
Для `type: decision` обязателен `decision_status`; при `status: superseded` или `decision_status: superseded` обязателен `superseded_by`.

## Процедура работы с архитектурной документацией

1. **Перед любым изменением** прочитать `doc/config/paths.yaml` и подтвердить, что целевой путь объявлен.
2. **Индекс-first retrieval:** начать с `doc/architecture/README.md` и компактного индекса; загружать только затронутые документы.
3. **Минимальный diff:** править ближайший раздел небольшим патчем, не переписывать całый файл.
4. **Статусы:** неутверждённое содержание — `status: draft`; решение в ADR — `decision_status: proposed`; неизвестное помечать `NEEDS CLARIFICATION`, не маскировать под факт.
5. **Валидация:** после изменений запустить `arch validate` и `arch docs paths --check`. Исправлять структурные ошибки — агент/человек; CLI не авточинит семантику.
6. **Review/approval:** человеческое ревью и утверждение по правилам проекта перед коммитом в канонические docs.

## CLI-команды, связанные с навыком

- `arch docs paths --check` — обход `doc/`, обнаружение файлов вне `allowed_paths`, диагностика несоответствий формату и регламенту структуры.
- `arch validate` — структурная валидация frontmatter, JSON Schema, уникальность ID, ссылки.
- `arch index build / index check` — построение и проверка актуальности `index.json`.
- `arch show <id>` — точный показ одного документа по ID.

## Что навык не делает

- Не выделяет `task_number` автоматически.
- Не создаёт `task.md`.
- Не классифицирует смысл файлов эвристиками.
- Не удаляет «мусор» без явного подтверждения пользователя.
- Не принимает семантические решения за агента (релевантность, правомерность изменения, утверждение contenта).
- Не редактирует `data/` как проектные файлы.

## Диагностика несоответствий

При запуске `arch docs paths --check` CLI должен сообщить:
1. Какие файлы в `doc/` не совпадают ни с одним объявленным путём/шаблоном (мусор).
2. Какие объявленные пути отсутствуют на диске (пропуски в структуре).
3. Какие `.md` в `doc/architecture/` не имеют фронтмatter или имеют невалидные поля.
4. Какие поля/типы/статусы не предусмотрены форматом и регламентом (предложение доработать `paths.yaml` или структуру).

Все сообщения содержат точный `file/path` и actionable описание. Exit code ненулевой при наличии отклонений.
