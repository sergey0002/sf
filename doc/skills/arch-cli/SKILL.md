# Работа с CLI фабрики

В примерах `arch` означает `python3 doc/tools/arch/__main__.py`. Для временной копии данных поставьте `--root <path>` перед командой и запустите актуальный скрипт по абсолютному пути. Если YAML лежит вне стандартного `doc/config/paths.yaml`, добавьте `--config <path>` перед командой. Относительный `--config` считается от `--root`.

**Исходники CLI закрыты для обычного использования.** Определяйте параметры по этому справочнику и `arch <команда> --help`, результат — по фактическому ответу. Открывайте исходник только при изменении самого CLI или при диагностике воспроизводимого расхождения с интерфейсом. В таком случае найдите конкретный символ через граф или точечный поиск и прочитайте нужный диапазон строк. При недоступности команды используйте задокументированный вариант или сообщите точную ошибку.

## Прочитать или проверить

| Нужно | Команда | Результат |
|---|---|---|
| Войти по точному ключу | `task diagnose <key> --json --brief` | Фаза, тип, flow, блокировки и `refs` к карточке и последней по номеру стадии. При `blockers_truncated` снимите `--brief`. |
| Проверить готовность кейсов приёмки | `task diagnose <key> --json --brief` | Для `case-coverage-v1` поле `acceptance_plan_ready` отражает наличие плана и покрытие AC запланированными кейсами. Пропущенные кейсы и устаревшие хеши блокируют `close`. |
| Проверить снимок верификации | `task evidence <key> --check` | `status: current|stale|missing`, `stale_files`, `missing_files` и `problems`; exit 1, если снимок не `current`. |
| Проверить карточку или ребёнка | `task validate <key>` · `task subtask validate <parent> <id>` | Структурная проверка. `task status <key> --json` и `task subtask status <parent> <id>` показывают состояние и артефакты. |
| Проверить рабочую область | `task workspace <key> --json` | Валидация, пути, подсказка ветки и `preflight`: `clean|review|isolate|unknown`, пересечения с `changed_files`, необязательным `scope.write_files` и разрешёнными модулями. Git checkout не выполняется. |
| Получить одну сводку рисков | `task doctor <key> --json` | Фаза, блокировки, `evidence_freshness`, незавершённая запись, зависимости и `preflight`. Только чтение. |
| Выбрать действующий тип и flow | `task types` · `task flows --type <type>` | Перечень доступных комбинаций. `task flow-steps --type <type> --flow <flow>` показывает порядок, результаты и условия перехода без тел промптов. |
| Открыть один шаг flow | `task flow-prompt --type <type> --flow <flow> --step <id>` | Markdown одного объявленного шага. При отсутствии отдельного файла команда берёт соответствующий пункт общего `prompt.md`. |
| Найти канонический документ | `list --id <id> --json` · `list --type <type> --domain <domain>` | Метаданные и путь без тела. `--id` можно повторять. Выбор нужного раздела и извлечение правил описаны в [architecture-read](../architecture-read/SKILL.md). |
| Получить полное оглавление архитектуры | `docs tree` | JSON с каталогами, заголовками, ID, статусами и путями без тел. |
| Найти раздел по термину | `docs search <query> --limit N --json` | Детерминированные хиты с `id`, якорем, строкой, статусом и сниппетом. `--scope reference` или `all` подключает `data/` явно. Архив исключён без `--include-archived`. |
| Прочитать один раздел | `docs read <DOC-ID#section-id> --max-bytes N --json` | Путь, диапазон строк, SHA-256 файла и текст раздела. Явный `{#anchor}` стабилен к переносу; slug служит совместимым резервом. |
| Посмотреть якоря документа | `docs toc <id> --json` | Явные и slug-якоря с диапазонами строк. |
| Проверить ссылки и якоря | `docs check-links --json` | Битые файлы, отсутствующие якоря и выход за корень; exit 1 при инцидентах. |
| Собрать контекст задачи | `docs context --task <key> [--case CASE-N] --json` | Ограниченный пакет объявленных ссылок с причинами, авторитетом, evidence и дельтой снимка. `complete: false` означает пробел или усечение, а не пустой успех. |
| Оценить влияние изменений | `docs impact --since <rev> --json` | Изменённые разделы и объявленные потребители; непокрытые изменения отдельно. Текстовое совпадение не считается влиянием. |
| Проверить архитектуру и пути | `validate --brief` · `docs paths --check` | Первая команда проверяет документы и индекс; вторая — правила путей. Для точечного просмотра инцидентов используйте `scan --scope <scope> --brief --fix-hints`. |
| Узнать активный YAML и пути | `docs paths --resolved` | JSON с `project_root`, `config`, `doc_root` и `roots`. Запрос без записи. |
| Проверить только свежесть индекса | `index check` | Проверяет существующий индекс без записи. |
| Найти сессию Kilo по фразе | `session find --match "<text>" --json` | Сессии с числом совпадений, первым `message_id` и сниппетом. По умолчанию ищет в каталоге проекта; `--all-projects` расширяет область. |
| Получить снимок сессии | `session digest <session_id> --json` | Компактное дерево: метки flow, скиллов, правил и задач, статистика инструментов, фазы, аномалии, токены и ссылки для углубления. |
| Углубиться в сообщение | `session events <session_id> --message <message_id> --json` | Части выбранного сообщения с входами, результатом и `part_id`. |

## Операции записи

| Нужно | Команда и условие |
|---|---|
| Создать карточку | `task new --title "<title>"` выделяет следующий UI-ключ из CLI-реестра, создаёт карточку и запись реестра одним вызовом. `task init <key> --title "<title>"` делает то же для известного ключа. `task-key --source ui --next` — только предпросмотр. `task registry --json` — чтение реестра; `task registry add <key>` — регистрация существующей карточки; `task registry check` — read-only сверка с каталогами; `task registry sync [--prune]` — синхронизация. Порядок описан в [create-task](../create-task/SKILL.md). |
| Создать детей | `task decompose <key> --subtask-id <id> --subtask-title "<title>"` проверяет весь пакет до записи, создаёт детей и обновляет список родителя. Сверьте все ID до пакетного вызова. `task subtask init <parent> <id>` создаёт отдельный каркас ребёнка. |
| Возобновить прерванную запись | Если `task diagnose` или `task status` показывает `incomplete_write`, проверьте `state`. При `invalid` сохраните журнал и сверяйте его с записями. Для валидного журнала повторите `task decompose` с тем же пакетом. CLI проверит всех детей перед записью и уберёт остатки своей временной записи перед удалением журнала. При exit 5 различайте активного писателя и конфликт данных по сообщению. |
| Проверить и закрыть | `task close <key> --dry-run --json` возвращает `would_close` и блокировки без записи. `task close <key> --json` меняет фазу при выполненных машинных предусловиях. Перед фактическим закрытием примените [правила приёмки](../go-to-task/SKILL.md). |
| Обновить производный индекс | `index build` проверяет источники и записывает индекс. Запускайте после изменений, затрагивающих индекс. |
| Выполнить проверку и записать evidence | `task evidence <key> --file <path> --case <CASE-N> --run <command> <args>` запускает явную команду из корня проекта. Повторяйте `--file` для входов снимка и `--case` для реально проверяемых кейсов. Ставьте параметры перед `--run`. Для общей проверки можно опустить `--case`. |
| Записать pre-change baseline | `task baseline <key> --file <path> --run <command> <args>` пишет `stageN/baseline.json` с командой, exit code и хешами входов. Если вход изменился во время запуска, запись отклоняется. |

Рабочий маршрут чтения: `docs context` для задачи → `docs search` для неизвестного термина → `docs read` для точного раздела. `docs toc` помогает выбрать якорь, `docs check-links` проверяет ссылки, `docs impact` оценивает последствия правки. Полный контракт — [адресуемые контракты](../../architecture/system/addressable-contracts.md).

Для расчёта результата используйте exit code. `can_close` и `would_close` описывают машинные предусловия. Предпросмотр может вернуть exit 0 и `would_close: false`, фактический отказ `close --json` даёт exit 1 и JSON в stderr. `validate --brief` и `scan --brief` дают одну строку при успехе и диагностические детали при отказе. Полный список инцидентов доступен без `--brief`.

Свежие флаги проверяйте через точный `--help`. Если нужны выходные поля или гарантии, откройте только нужный раздел [спецификации команд](../../architecture/system/implementation-spec.md) или строку [карты команд](../../architecture/system/cli-command-map.md). Для итерации используйте `bash doc/tests/run.sh --only <pattern>`, для компактной проверки стабильного среза — [режим тестов `--brief`](../../tests/README.md), для обязательного финала — `--gate`.

`diagnose` и `close` сообщают блокирующие зависимости. `task evidence --run` сохраняет реальный exit code только при совпадении входов до и после. При смене снимка `--replace-snapshot` начинает новую серию результатов с сохранением плана. [Контракт evidence](../../architecture/domains/task-lifecycle/entities/verification-evidence.md)
