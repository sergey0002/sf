# Оценка и декомпозиция

Оценку и решение о декомпозиции ставит агент. CLI принимает выбранные значения и проверяет допустимость; он не угадывает сложность.

## Оценка в часах

Оценка — труд агента: чтение входов, изменение файлов, новые тесты, документация, ревью, верификация. Не календарный срок человека.

1. Перечислите работы.
2. Для каждой укажите базу: число файлов, команд, тестовых сценариев.
3. Сложите и округлите до `0.5, 1, 2, 4, 8, 16, 24, 40, 80`.
4. Поставьте `estimate_hours` в `task.json`; для ребёнка — в его карточке.
5. При неизвестной базе используйте верхнюю границу и зафиксируйте допущение в `assumptions`.
6. Пересчитайте после `architecture-context` и первого сквозного среза; изменение фиксируйте в плане.
7. Для родителя оценка не меньше суммы детей плюс интеграция и общая верификация.

Запрещено: «примерно день» без перечня работ, ложная точность (`3.7`), занижение ради отказа от декомпозиции.

## Соответствие tier, complexity и часов

| Tier | `complexity` | Часы | Обязательные разделы |
|---|---|---|---|
| `micro` | `low` | ≤ 2 | Приёмка, Проверка |
| `standard` | `low`, `medium` | 2–24 | Цель, Приёмка, Оценка, Проверка + правила и решения |
| `full` | `high`, `critical` | > 24 | Все разделы и разделы по риску |

Расхождение часов и риска объясните в плане: `critical` при трёх часах остаётся `full`, потому что важна необратимость.

## Когда декомпозировать

Декомпозируйте, если выполняется не менее двух условий:

- два и более независимо проверяемых наблюдаемых результата;
- разные границы записи: файлы, каталоги, хранилища, внешние системы;
- разные домены или модули, которые можно менять параллельно;
- разный риск или обязательные одобрения;
- оценка больше 8 часов и делится на связные срезы;
- нужен отдельный сквозной срез через публичную точку входа до массовой правки;
- результат одного среза блокирует проверку другого.

Не декомпозируйте, если:

- результат один и атомарен;
- изменение контракта связано и разделение создаст временную несовместимость;
- работа короче 2 часов;
- дети потребуют синхронной правки одного файла без независимой проверки;
- деление искусственное: «исследование / реализация / проверка» без собственного наблюдаемого результата.

## Требования к ребёнку

1. Точный вход: какие AC родителя и какие строки `CASE` он закрывает.
2. Собственный `AC-N` и `CASE` с независимым оракулом.
3. Граница записи: какие пути ребёнок вправе менять.
4. Ссылка на строку родительского плана.
5. Явные зависимости от других детей.
6. Осознанные `task_type`, `flow`, `complexity`, `estimate_hours` — не значения по умолчанию.

Количество детей выводится из результата. Один ребёнок — норма; типично 2–5; больше 7 — пересмотрите срез.

## Команды

```bash
arch task decompose <key> \
  --subtask-id 0001 --subtask-title "..." \
  --subtask-type 0001=subtask --subtask-complexity 0001=medium --subtask-estimate 0001=6

arch task subtask init <parent> 0001 --task-type subtask --complexity medium --estimate-hours 6
```

`task_type` выбирается по содержанию: `subtask` — нейтральный лист работы, `bugfix`/`refactor`/`docs` — по характеру изменения. `feature` — только если ребёнок сам будет декомпозирован. `scaffold` для семантической работы не используется.
