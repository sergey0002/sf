# Чек-лист качества плана

Загружайте при постановке, ревью плана и перед переходом к реализации. При исполнении уже готового плана достаточно safety floor из `SKILL.md`.

## Перед реализацией

- [ ] Tier объявлен маркером и соответствует `complexity`.
- [ ] Все обязательные разделы для tier присутствуют.
- [ ] Каждый AC покрыт `CASE` с независимым оракулом.
- [ ] У каждого `CASE` указано «Дано», публичное действие и точное ожидание.
- [ ] Оракул различает исходную и требуемую реализацию.
- [ ] Блок «Правила проекта» связывает ID и раздел с AC или CASE.
- [ ] Оценка в часах опирается на перечень работ и округлена.
- [ ] Решение о декомпозиции обосновано; число детей выведено из результатов.
- [ ] У каждого ребёнка есть собственный AC, оракул, граница записи и оценка.
- [ ] Порядок работ не требует дважды менять один контракт.
- [ ] Откат описан конкретными действиями.
- [ ] Открытые вопросы и одобрения перечислены явно.
- [ ] План не переписывает требования и не дублирует `verification.json`.
- [ ] `planned_checks` в `verification.json` покрывают все AC.

## Антипаттерны

| Антипаттерн | Почему плохо | Как исправить |
|---|---|---|
| `micro` для задачи с контрактом или миграцией | Пропускает отказные и совместимые сценарии | Эскалируйте до `standard`/`full` |
| `micro` на 90 строк | Формально tier, фактически полный план без структуры | Перейдите на `standard` |
| План из одной строки-заглушки | Формально валиден, но не даёт исполнителю ничего | Заполните разделы по tier |
| Фиксированные три ребёнка | Не связаны с результатами, раздувают координацию | Выведите число из независимых результатов |
| «Реализовать X» без оракула | Нельзя выставить pass/fail | Добавьте `CASE` с наблюдаемым ожиданием |
| Оракул = повторный вызов проверяемого компонента | Ложный зелёный | Возьмите независимое состояние: файл, код выхода, JSON-поле |
| План переписывает AC | Требования дрейфуют | Верните изменение в `task.json` через уточнение |
| Оценка «примерно день» | Не воспроизводима | Перечень работ и часы по шагам |
| Подзадача типа `scaffold` для семантической работы | Отключает обязательные поля и гейты | Выберите `task_type` по содержанию |
| Раздел «Правила проекта» без источника | Нельзя проверить актуальность | Укажите ID и раздел контракта |
| Дублирование evidence в плане | Расхождение при повторном прогоне | В плане — команды и ожидания, в evidence — результаты |
| Понижение tier «чтобы короче» | Прячет риск и отказные сценарии | Tier можно только повышать |

## Ревью плана

1. Сверьте tier с `complexity`, `risk` и часами.
2. Проверьте, что safety floor не сокращён.
3. Для каждого AC найдите `CASE` и оракул; оракул не должен вызывать проверяемый компонент.
4. Сверьте порядок работ с зависимостями и границами записи.
5. Проверьте, что дети дают самостоятельный результат, а не пересказ родителя.
6. Убедитесь, что откат выполним на текущем снимке.
