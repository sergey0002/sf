# Подготовка плана задачи

План — технический ответ на вопрос «как получим наблюдаемый результат». Требования живут в `task.json`, оракулы и порядок — в `stageN/plan.md`, фактические результаты — в `stageN/verification.json`. Не дублируйте одно и то же в трёх местах.

Этот навык применяется при постановке задачи, при подготовке к выполнению, при новой стадии и при ревью плана. Постановку карточки ведёт [create-task](../create-task/SKILL.md), исполнение — [go-to-task](../go-to-task/SKILL.md), проверку diff — [review-implementation](../review-implementation/SKILL.md).

## Граница навыка

- План отвечает «как», а не «что». Новое требование сначала попадает в `acceptance_criteria` карточки, затем в план как `CASE`.
- CLI проверяет структуру: наличие плана, tier, покрытие AC, хеши. Смысл разделов и качество оракула оценивает агент.
- Решение о декомпозиции принимает агент по правилам ниже. CLI только создаёт детей с выбранными агентом `task_type`, `flow`, `complexity` и `estimate_hours`.
- Никаких фиксированных «трёх подзадач». Число детей выводится из числа независимо проверяемых результатов.

## Шаг 1. Получите политику типа

Перед выбором tier выполните `arch task plan-policy --type <task_type> --json`. Команда только читает конфигурацию. Используйте возвращённые `tiers`, `required_sections`, `template` и `acceptance.rules`.

Глобальная таблица ниже — только дефолт для типа без собственного блока `plan`. Политика разрешается как `type → doc/config/task-conf/plan-defaults.yaml`; блок `plan` во flow игнорируется. `plan_policy: replace` заменяет tier'ы, но сохраняет safety floor разделов. Списки заменяются по полям tier'а, а обязательные разделы дополняются, а не теряются.

Каталог правил ограничен `section_present`, `section_min_items`, `link_min`, `table_column`, `case_min`, `command`. CLI проверяет структуру и называет файл, раздел и правило. Смысл оракула оценивает агент. Правило с `when` остаётся условным и не применяется машинно без отдельного признака.

## Шаг 1а. Выберите tier плана

Tier задаётся `complexity` карточки. Агент может повысить tier, но не понизить.

| Tier | `complexity` | Когда | Бюджет | Шаблон |
|---|---|---|---|---|
| `micro` | `low` | ≤ 2 ч, 1–2 файла, один AC, без изменения контракта | ≤ 60 непустых строк | [plan-micro](references/plan-micro.md) |
| `standard` | `low`, `medium` | 2–24 ч, несколько файлов или модулей | ориентир ≤ 120 строк | [plan-standard](references/plan-standard.md) |
| `full` | `high`, `critical` | > 24 ч, необратимое изменение или несколько стадий | без лимита | [plan-full](references/plan-full.md) |

Маркер ставится первой строкой плана:

```markdown
<!-- plan-tier: standard -->
```

Правила выбора:

1. Tier не может быть ниже `complexity`: `medium` требует минимум `standard`, `high`/`critical` — `full`.
2. Маркер обязателен, если в карточке задан `estimate_hours`. Для старых карточек без оценки он не требуется.
3. **Эскалация по риску.** Если затронут публичный контракт, формат хранения, миграция, конкурентная запись, внешняя система или безопасность — минимум `standard`, независимо от часов. Для необратимого изменения — `full`.
4. Расхождение часов и риска объясните в разделе «Риски».

## Шаг 2. Загрузите только свой шаблон

Откройте ровно один файл из таблицы выше. Не читайте остальные шаблоны: это и есть экономия контекста.

- `micro` — минимальный каркас, оракул и команда проверки.
- `standard` — цель, правила проекта, решения, артефакты, порядок, приёмка, оценка, проверка.
- `full` — все разделы плюс разделы по риску: данные, границы прерывания, безопасность, производительность, наблюдаемость.

## Шаг 3. Не нарушайте safety floor

Независимо от tier план обязан содержать:

1. Каждый `AC-N` покрыт `CASE-N` с независимым оракулом.
2. Точный путь затронутого файла и точную команду проверки.
3. Откат: для `micro` — одной строкой, для остальных — конкретными действиями.
4. `planned_checks` в `verification.json`, покрывающие все AC.

Всё остальное сокращается по tier. Safety floor не сокращается никогда.

### Оракул для записи, восстановления и миграций

Если `CASE` меняет файлы, возобновляет прерванную операцию или мигрирует данные, таблицы «вход → действие → ожидание» недостаточно. Для каждого такого случая запишите:

- исходное состояние fixture (наличие и содержимое записей, журнала, временных файлов, блокировки);
- публичный вызов и точный селектор;
- ожидаемый код процесса и диагностику;
- постусловие по всему затронутому дереву: какие пути и байты изменились, какие обязаны совпасть;
- один сценарий, который различает исходную и требуемую реализацию. Если такого сценария нет, AC не доказан.

Для отказа и предпросмотра сравнивайте дерево до и после, а не только ответ команды. Для восстановления моделируйте точку остановки между шагами, а не только итоговое состояние. Если исторический снимок недоступен, укажите проверяемую альтернативу и ограничение.

## Шаг 4. Оцените объём и решите о декомпозиции

Правила оценки в часах, критерии split/no-split и требования к ребёнку — в [estimation](references/estimation.md).

Коротко:

- `estimate_hours` ставит агент по перечню работ и округляет до `0.5, 1, 2, 4, 8, 16, 24, 40, 80`.
- Декомпозиция нужна, если есть два и более независимо проверяемых результата с разными границами записи.
- Один ребёнок — норма, типично 2–5, больше 7 — пересмотрите срез.
- Каждому ребёнку задайте `task_type`, `flow`, `complexity`, `estimate_hours`; не оставляйте `scaffold`.

## Шаг 5. Проверьте план

Содержательный чек-лист и антипаттерны — в [quality-checklist](references/quality-checklist.md). Машинные проверки:

| Проверка | Команда | Что означает |
|---|---|---|
| Структурная готовность | `arch task diagnose <key> --json --brief` | `acceptance_plan_ready: true` |
| Готовность ребёнка | `arch task subtask validate <parent> <id>` | Карточка и план ребёнка валидны |
| Свежесть доказательств | `arch task evidence <key> --check` | Хеши снимка совпадают |
| Пути и документы | `arch validate --brief`, `arch docs paths --check` | Новые файлы объявлены |

`acceptance_plan_ready` проверяет tier, обязательные разделы для tier, покрытие AC и наличие плана; `diagnose` возвращает распознанный `plan_tier`. Смысл оракулов CLI не оценивает.

## Жизненный цикл стадии

- Новый контракт или существенное изменение требований → новая стадия `stageN+1` с собственным планом.
- Уточнение в рамках того же контракта → правка текущего плана и повторная верификация затронутых кейсов.
- После изменения плана, реализации или тестов старый evidence устаревает.
- Прежние стадии сохраняются как история; не переписывайте их задним числом.
