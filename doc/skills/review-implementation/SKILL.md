# Ревью реализации

Выполняйте шаг `review-implementation` после целевых тестов и перед `architecture-sync`. Цель — найти состояние, где изменение нарушает AC, сохраняемый контракт или границу записи. Начните с наиболее рискованного сценария и сами сформулируйте возможный контрпример.

## Пакет ревью

1. Возьмите `task_key`, intent, границы, `AC` и `CASE` из карточки и плана. Добавьте ожидаемые ошибки и постусловия для затронутой записи. Сверьте сам план по [plan-task](../plan-task/SKILL.md): обязательные разделы, независимость оракулов и обоснование декомпозиции.
2. Укажите базу задачи и идентификатор проверяемого снимка. Соберите diff по точным путям задачи с учётом staged, unstaged и новых файлов. Включите свои новые файлы отдельно, поскольку обычный `git diff` их не выдаёт. Для локальных игнорируемых входов используйте явный список и хеши. При пересечении чужих правок подготовьте неизменяемую копию нужного среза или worktree с правильной базой.
3. Приложите ID и точные разделы контрактов и ADR, селекторы целевых тестов и краткий результат. Раскрывайте полный лог и дополнительные файлы по конкретному спору. Пакет не требует историю разговора, весь roadmap или вывод автора о готовности.

## Выполнение и результат

- Для небольшого обратимого изменения проведите саморевью и один целевой контроль через публичную точку входа.
- Для изменений записи, восстановления, миграций или публичных контрактов используйте независимого ревьюера в свежем контексте, когда делегирование разрешено и доступно. Передайте пакет и доступ к этому снимку. Задача ревьюера — найти пропущенный сценарий, ложный зелёный тест, регрессию или расхождение документации с поведением. Проверки с записью запускаются на временной fixture. Если независимое ревью недоступно, выполните отдельный проход по этому пакету, отметьте ограничение и вынесите самый рискованный случай на ревью владельца.
- Для находки верните `серьёзность | AC/CASE | файл или раздел | исходное состояние и вызов | ожидание | фактический исход`. Если находок нет, перечислите проверенные сценарии и границы. Отсутствие независимого оракула укажите явно.
- Запишите результат в `stageN/plan.md` под `Ревью реализации`. Исполнитель исправляет блокеры и повторяет целевой сценарий. Сверьте изменившийся diff перед переходом к синхронизации архитектуры и финальной верификации. Ревью не заменяет одобрение владельца.
