# Чтение архитектуры проекта

Сначала определите вопрос задачи. Что должно измениться, какой контракт сохранить и каким результатом это проверить. В примерах `arch` — публичная команда из [arch-cli](../arch-cli/SKILL.md).

| Что известно | Следующий шаг |
|---|---|
| Ключ задачи | `arch task diagnose <key> --json --brief`. Из `refs` откройте карточку и текущий план. Возьмите `related_docs`, разделы из `project_context_refs` и AC затронутого сценария. |
| Точные ID | `arch list --id <id> --id <id> --json` возвращает пути и статусы без тел документов. Сверьте, что вернулись нужные ID. |
| Домен или тип | `arch list --domain <domain> --type <type>`. Если домен неизвестен, используйте [карту архитектуры](../../architecture/README.md). Ограничьте поиск одним подходящим доменом, затем выберите ближайший контракт, flow, сущность или ADR. |
| Нужна карта всей архитектуры | `arch docs tree` выводит JSON-оглавление по каталогам с ID, заголовками, статусами и путями. Используйте его для обзора или неизвестного домена. |
| Остался конкретный пробел | Откройте ссылку из найденного раздела либо вызовите `arch docs related <id> --depth 1`. Выберите только запись, которая отвечает на оставшийся вопрос. |

`list` возвращает путь относительно каталога архитектуры. Если его расположение неизвестно или изменено, возьмите `roots.architecture` из `arch docs paths --resolved` с тем же `--root` и `--config`. Откройте frontmatter и нужный раздел по заголовку или точному термину. `arch show <id>` подходит для короткой записи, когда нужно прочитать её целиком. Полный `index.json`, длинный контракт и соседние домены раскрывайте только при явной нехватке сведений.

Из выбранного раздела выпишите только то, что влияет на задачу: вход и результат, порядок переходов, обязательные ограничения, владельца состояния, побочные эффекты и проверки отказа. В карточке сохраняйте ID в `related_docs`, а точный раздел и его применение — в плане. Для изменённого или сохраняемого правила свяжите ID и раздел с `AC` или `CASE`, затем проверьте это правило на итоговом снимке.

## Результат шага `architecture-context`

| Источник | Что взять и зачем |
|---|---|
| Инструкции проекта, манифест `MAN-software-factory` и действующие ADR | Только применимые ограничения, полномочия, запреты и точки одобрения. Они определяют границы допустимого решения. Используйте уже загруженные правила. |
| Карточка и затронутый раздел архитектуры | Точное обязательство для потребителя, допустимые состояния, ошибки и побочные эффекты. Отметьте, что сохраняется и что меняется по задаче. |
| Проверка или наблюдаемый результат | Вход и публичное действие, которые показывают соблюдение правила. Если правило ограничивает сам способ работы, укажите способ проверить diff, артефакт или полномочия. |

Запишите в `stageN/plan.md` компактный блок `Правила проекта` по форме `ID или путь и раздел → правило → сохранить / изменить → AC, CASE или проверка`. Например, правило «индекс находится внутри настроенного каталога архитектуры» связывается с конкретным путём файла и `CASE` чистой сборки. Отсутствие применимого документа отметьте одной строкой с основанием и альтернативным источником. При возобновлении переиспользуйте записи, если их источники и границы задачи актуальны.

Сверяйте статус, применимость и связанные решения. Черновик служит источником контекста. Принятое правило подтвердите по контракту и действующим решениям, текущую реализацию — по публичной проверке и при необходимости по целевому символу через граф кода. При расхождении запишите ID и наблюдаемый факт. Если выбор меняет контракт или критерий, уточните его до затронутой правки. Если применимого документа нет, отметьте пробел и укажите источник, по которому проверяете поведение.

Для изменения канонического документа используйте [architecture-docs](../architecture-docs/SKILL.md). Для исследования общих практик ищите в [data](../../../data/README.md).
