# Постановка задачи

Создайте одну каноническую карточку `task.json`. Источники, приоритеты и точка входа описаны в [doc/AGENTS.md](../../AGENTS.md). Команды берите из [arch-cli](../arch-cli/SKILL.md). Постановка заканчивается передачей проверяемого задания.

**Граница постановки.** Этот навык не выполняет задачу: не начинайте реализацию, не создавайте продуктовые изменения и не переходите к [go-to-task](../go-to-task/SKILL.md) без отдельного поручения. Завершите постановку предложением «Хотите, приступлю?» и дождитесь явного подтверждения. Согласие на постановку, вопрос о номере или молчание не являются подтверждением реализации.

**Короткий путь для задачи из чата.** `arch task new --title "<title>"` → заполнить поля `task.json` по шагу 3 → `arch task validate <key>`. Номер, каталог и запись реестра создаёт CLI; реестр не читается и не правится вручную.

При формулировании требований найдите действующее правило по [architecture-read](../architecture-read/SKILL.md). В карточку сохраните ID, в план — точный раздел и связанный AC или CASE. Для кандидата без ключа начинайте с известного домена или поведения.

1. **Соберите минимальный контекст.** Откройте запрос владельца или ревизию трекера, точный действующий контракт и ближайший пример либо тест. Сохраните источник и ссылки. Сформулируйте пользователя или потребителя, текущее поведение, требуемое наблюдаемое изменение, scope, что должно сохраниться, полномочия и зависимость. Для существующего поведения укажите, что добавляется, изменяется или убирается. Подтверждённый источник определяет требования. Обратимые технические предположения запишите явно. Если варианты меняют контракт, полномочия или результат приёмки, задайте один адресный вопрос или зафиксируйте блокирующее решение в `open_questions`.
2. **Выберите форму задачи.** Получите тип и flow через `task types`, `task flows --type <type>` и prompts выбранной комбинации. Используйте глубину по риску. Для локальной правки достаточно одного проверяемого сценария, для изменений интерфейса или хранения нужны совместимость и применимые отказы. Декомпозицию и оценку выполняйте по разделу «Оценка и декомпозиция» ниже. Ребёнок получает точный вход, свой критерий, границу записи и ссылку на строку родителя. Сверьте зависимости, точки интеграции и порядок. План пишите по навыку [plan-task](../plan-task/SKILL.md).
3. **Сделайте приёмку исполнимой.** Каждый `AC-N` описывает наблюдаемое обещание. Каждый `CASE-N` описывает отдельный вариант с полями `дано → действие через публичный вход → точное ожидание → способ проверки`. Укажите точный fixture, аргументы, код выхода или ответ и ожидаемое состояние. Для записи укажите, что должно измениться и где, какие файлы или данные должны сохраниться. Для изменённого контракта проверьте применимые стандартный, совместимый, новый и отказной варианты. Если вариант неприменим, кратко объясните это в плане. Каждый оракул выводите из требования или независимого состояния, например из точного пути файла, а не из второго вызова того же компонента, который читает его результат. Сценарий должен выявлять реализацию, которая выглядит правдоподобно и нарушает критерий.

   Для многошаговой записи укажите границы поддерживаемого прерывания, состояние на каждой границе, действие повтора и состояние после отказа. Если есть журнал или конкурентный писатель, задайте отдельные случаи для повреждения журнала, конфликта при возобновлении и конкуренции. Проверка отказа сравнивает всё затронутое дерево, включая дочерние записи и журнал.
4. **Соберите карточку и стадию.** Для задачи из чата выполните один вызов `arch task new --title "<title>"`. CLI выделяет следующий свободный UI-номер из своего реестра, создаёт каталог, `task.json` и запись в реестре. Не читайте и не редактируйте `doc/config/task-registry.json` вручную, не сканируйте `doc/tasks` и не спрашивайте пользователя, какой номер выбрать. Для известного ключа (Jira, внешний источник, заранее назначенный номер) используйте `arch task init <key> --title "<title>"`; CLI сам добавит запись в реестр. `arch task-key --source ui --next` — только предпросмотр без записи. A four-decimal-digit task number is required. For chat use `source.type: ui`. Keys are Jira `1234` (no prefix), UI `UI-1234` and other sources `<PREFIX>-1234` with a registered prefix. Never invent or allocate one yourself. Коллизию останавливает CLI (`task new`, `task init`, `task validate`), а не перебор каталогов. В `task.json` сохраните intent, scope, критерии, источники, тип/flow, зависимости, полномочия и ссылки на тесты по схеме. Поставьте `complexity` и `estimate_hours`. В `stageN/plan.md` запишите обязательные разделы и таблицу `CASE | AC | Дано | Действие | Ожидание и проверка | Ребёнок` по [plan-task](../plan-task/SKILL.md). Для поведенческой задачи и её технических детей используйте `acceptance_policy: "case-coverage-v1"`. В `stageN/verification.json` сохраните `task_key`, `stage_id`, `status: "not_run"`, `checked_revision: null`, `checks: []` и `planned_checks` с `id`, `covers`, `expected` на каждый обязательный случай. Зарегистрируйте детей по правилам `task decompose`, передав для каждого выбранные `--subtask-type`, `--subtask-flow`, `--subtask-complexity` и `--subtask-estimate`. События трекера служат источником для записи и требуют отдельного разрешения на обратную запись.
5. **Проверьте задачу глазами нового исполнителя.** Сверьте цепочку `поручение → AC → CASE → публичный вход → проверка → ребёнок`. За один проход найдите потерянное требование, сценарий без оракула, противоречие и скрытую зависимость. Для подзадачи проверьте, что её короткая карточка и ссылки дают достаточно данных для самостоятельного результата. Запустите `task validate`, применимый `task subtask validate`, `task diagnose <key> --json --brief` и `docs paths --check`. `acceptance_plan_ready` проверяет структуру плана и связь кейсов с AC. Смысл оракулов проверяет постановщик. Сообщите ключи, готовность и конкретные открытые решения. Завершите предложением «Хотите, приступлю?» и остановитесь: реализация начинается только после явного подтверждения. При блокировке выполните независимую часть постановки и передайте точный вопрос.

## Оценка и декомпозиция

Оценку и решение о декомпозиции ставит агент. CLI не угадывает: он принимает выбранные значения и проверяет их допустимость.

### Оценка

1. Перечислите работы: чтение входов, изменение файлов, новые тесты, документация, ревью, верификация.
2. Для каждой работы укажите базу: число файлов, команд, тестовых сценариев.
3. Сложите и округлите до `0.5, 1, 2, 4, 8, 16, 24, 40, 80` часов.
4. Поставьте `estimate_hours` в `task.json`; для ребёнка — в его карточке.
5. При неизвестной базе используйте верхнюю границу и зафиксируйте допущение в `assumptions`.
6. Для родителя оценка не меньше суммы детей плюс интеграция и общая верификация.

`complexity` выбирайте по риску и объёму: `low` ≤ 2 ч, `medium` 2–24 ч, `high` 24–80 ч, `critical` > 80 ч или необратимый риск. Расхождение часов и риска объясните в плане.

### Когда декомпозировать

Декомпозируйте, если выполняется не менее двух условий:

- два и более независимо проверяемых наблюдаемых результата;
- разные границы записи: файлы, каталоги, хранилища, внешние системы;
- разные домены или модули, которые можно менять параллельно;
- разный риск или обязательные одобрения;
- оценка больше 8 часов и делится на связные срезы;
- нужен отдельный сквозной срез через публичную точку входа до массовой правки;
- результат одного среза блокирует проверку другого.

Не декомпозируйте, если результат один и атомарен, изменение контракта связано, работа короче 2 часов, дети потребуют синхронной правки одного файла или деление искусственное («исследование / реализация / проверка» без собственного наблюдаемого результата).

### Как создавать детей

- Число детей выводится из числа независимых результатов. Один ребёнок — норма; типично 2–5; больше 7 — пересмотрите срез.
- У каждого ребёнка есть собственный `AC-N`, `CASE` с независимым оракулом, граница записи, ссылка на строку родительского плана и явные зависимости.
- Выберите ребёнку `task_type`, `flow`, `complexity` и `estimate_hours` по содержанию работы. Не оставляйте `scaffold`/`minimal-scaffold` для семантической задачи: этот тип отключает обязательные поля и шаги плана.
- Передайте выбор в CLI: `arch task decompose <key> --subtask-id 0001 --subtask-title "..." --subtask-type feature --subtask-flow standard-implementation --subtask-complexity medium --subtask-estimate 6`. Для одиночного ребёнка используйте `arch task subtask init <parent> <id>` с теми же флагами.
- После создания заполните `intent`, `scope`, `acceptance_criteria`, `implementation_plan` и план ребёнка. Проверьте `arch task subtask validate <parent> <id>`.

Пример и правила приёмки — в [потоке создания задачи](../../architecture/domains/task-intake/flows/create-task.md). Для восстановления или исполнения используйте [go-to-task](../go-to-task/SKILL.md). Полный формат плана, уровни и чек-лист — в [plan-task](../plan-task/SKILL.md).
Для новой задачи `docs-only` также включите `acceptance_policy: "case-coverage-v1"` и запланируйте кейсы для всех AC. Структурные проверки при закрытии не заменяют эти кейсы.
