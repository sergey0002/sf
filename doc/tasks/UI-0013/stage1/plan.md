## Исходное поведение (baseline до изменений)

- `builtin.py` — 1383 строки; `TaskCommand` совмещает parser, lifecycle-сценарии, чтение/запись и форматирование.
- `task decompose` создаёт детей и обновляет родителя последовательными записями без предварительной проверки всего пакета; ID не валидируются, дубли и коллизии обрабатываются только при обходе.
- `task init`, `task close`, `task subtask init`, `decompose` пишут `task.json` напрямую через `write_text`; атомарная замена есть только у индекса (`store.write_index`).
- Registry молча перезаписывает одноимённую команду.
- `task flows`, `task type-prompt`, `task flow-prompt` падают с `NameError: root`; `scan --scope tasks` использует неопределённый `root` в подсказке для ошибки ребёнка.
- Baseline-прогон: 5 unit OK; 39 acceptance OK (один повторный прогон после устранения параллельного запуска).

## Выбранный срез

1. `fs_atomic.py`: атомарная замена одиночного файла (temp в том же каталоге, `fsync`, `os.replace`) и журнал составной записи.
2. `task_ops.py`: прикладные сценарии lifecycle — чтение, init, validate, workspace, status, decompose, diagnose, close, subtask; без argparse и печати.
3. `cli/commands/task.py`: тонкий `TaskCommand` — только parser, dispatch и формат вывода; `builtin.py` сохраняет docs/list/show/index/validate/scan.
4. Decompose: проверка всего пакета (формат и уникальность ID, пустые title, объявленные дети, каталоги) до первой записи; родитель проверяется только на читаемость, массив `subtasks` и отсутствие `task.md`, чтобы не блокировать первый пакет семантическими полями; журнал `.arch-write-journal.json`; повторный вызов с тем же пакетом возобновляет запись, другой пакет — конфликт.
5. `diagnose`/`status`/`scan --scope tasks` сообщают о незавершённой записи; закрытие блокируется до восстановления.
6. Registry отвергает дубли команд; `ArchitectureStore` создаётся лениво при первом обращении.
7. Восстановлены сломанные старые вызовы (`task flows`, `task type-prompt`, `task flow-prompt`, scan-подсказка) без изменения форматов.

## Шаги

1. Выделить lifecycle-сценарии из builtin.py и сохранить совместимые точки входа.
2. Валидировать весь пакет декомпозиции и определить восстановление между записями.

## Приёмка

- AC-1: Некорректный пакет и конфликт обнаруживаются до записи; прерывание обнаруживается и восстанавливается по документированному сценарию.
- AC-2: Старые вызовы и форматы сохраняют семантику; тесты проверяют нормальный и отказный выход.

Перед изменениями зафиксировать исходный результат. Для каждого AC записать фактическую проверку и проверенный снимок в `verification.json`. Базовые команды указаны в записи верификации. Проверки предметного сценария выполнить по критериям выше.
