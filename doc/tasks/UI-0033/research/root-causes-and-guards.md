# Корневые причины дефектов UI-0033 и введённые защиты

Дата: 2026-11-23. Основание: аудит сессии `ses_dfb5666edffelp0HGjpFteRO7t` и независимая проверка рабочего дерева.

## 1. Что было сломано

| # | Дефект | Доказательство |
|---|---|---|
| D1 | `task new`/`task init` создавали невалидную карточку: скаффолд писал `branch`/`release_branch`/`target_release = "unset"`, а валидация их отвергала | `scaffold_task_json` → `unset`; `task init` → `task validate` exit 1 |
| D2 | Обязательные поля ломали весь корпус (31 карточка) | `task validate UI-0001` → 3 блокера |

## 2. Корневые причины

1. **Скаффолд и валидатор развивались раздельно.** Обязательное поле добавлено в валидацию, но не в создание карточки; не было теста, связывающего оба конца. Это класс дефекта «добавили требование — не обновили producer».
2. **Обязательность введена без миграции.** Поле сделали обязательным для всех карточек, не переведя существующий корпус и не предусмотрев фазу включения (`enforce`).
3. **Скилл постановки не был загружен.** Карточка писалась вручную в обход `arch task new`, поэтому не применялись ни дефолты, ни проверки, ни правила выбора типа.
4. **Тип подбирался под валидатор, а не под работу.** Вместо декомпозиции выбран тип с более мягкой политикой.
5. **Изменение контракта не считалось отдельным событием.** Не было обязательного чек-листа «тесты + архитектурные документы + полный gate».
6. **Заявление об успехе не привязано к exit code полного гейта.** Долгий `--gate` заменялся прогоном подмножества.

## 4. Остаточные риски

- Контракт Git-операций (подготовка, публикация, интеграция) по-прежнему принадлежит UI-0027; здесь поля обязательны, но автоматизация ветки не реализована.
- `status` меняется вручную в `task.json`; отдельного события журнала для него нет — при необходимости вводится в UI-0027/отдельной задаче.
- Историческая семантика `status` для старых карточек выведена из `phase` (completed→done, verification→review); владелец может уточнить.
