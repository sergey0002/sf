# UI-0031: Согласованность реестра типов архитектурных документов

Карточка: [task.json](../task.json). Стадия `stage1`. Родителя нет.

## Цель и границы

- Текущее поведение: реестр ARCH-contract §6.1 (17 типов), `paths.yaml` (27 записей, дубль `rule-set`), body-схемы (15) и `index.json` (20 типов) расходятся; `glossary.json` не парсится; enum статусов различается в трёх источниках.
- Требуемое поведение: один реестр типов в `paths.yaml`, синхронный с контрактом и фактическим использованием; формат и условие применения описаны для каждого типа; все body-схемы валидны; проверка согласованности автоматизирована.
- Сохраняется: типы и смысловые разделы существующих документов, валидность статусов `draft`/`accepted`, производность `index.json`.
- Не входит: переклассификация документов, новые продуктовые документы, изменения task-conf и поведения CLI вне проверки реестра.
- Ручной контроль: итоговый diff и приёмку проверяет владелец; агент не закрывает задачу самостоятельно.

## Решения

| Решение | Причина | Отклонённые варианты |
|---|---|---|
| Единственный источник истины — `paths.yaml project.document_types`; контракт и тест сверяются с ним | Валидатор уже читает этот конфиг, значит расхождение контракта и практики устраняется в одном месте | Дублировать enum в схеме и контракте и сверять вручную |
| Неиспользуемые типы сохраняются как зарезервированные с условием применения | Для `integration`, `quality-view`, `deployment-operations-view`, `verification-map`, `cross-cutting-concept`, `system-overview` есть архитектурный concern | Удалить их из реестра и потерять описанные точки зрения |
| Body-схема требуется только там, где структура тела проверяема; остальные типы помечаются prose-only | Прозаические форматы (`runbook`, `examples`, `implementation-spec`, `testing-spec`, `architecture-view`) не моделируются полностью | Требовать JSON-схему для каждого типа и дублировать Markdown |
| Единый enum статусов документа фиксируется в `document.schema.json` и `paths.yaml`, контракт ссылается на него | Три разных набора делают невалидным одно и то же значение | Оставить различия и документировать исключения |

5. Пересобрать индекс при изменении frontmatter, прогнать проверки.

## Приёмка

Фикстура F: временная копия `doc/architecture` с теми же типами документов. Эталон — текущее дерево, которое должно проходить проверку. Для негативных сценариев используются независимые копии F.

| CASE | AC | Дано | Действие | Ожидание и проверка | Ребёнок |
|---|---|---|---|---|---|
| CASE-1 | AC-1 | Текущее дерево | Сравнить множество типов из `index.json` с `paths.yaml project.document_types` и проверить отсутствие дублей | Множества равны, дублей нет; `docs paths --check` exit 0 | нет |
| CASE-2 | AC-1, AC-2 | Текущее дерево | Извлечь набор типов из таблицы контракта §6.1 и сравнить с `paths.yaml` | Наборы совпадают; для каждого типа есть строка формата и условие применения | нет |
| CASE-3 | AC-2 | Текущее дерево | Проверить неиспользуемые типы в контракте | Каждый неиспользуемый тип помечен зарезервированным с условием, когда его создавать | нет |
| CASE-4 | AC-3 | Копия F | Проверить парсинг всех файлов `schemas/bodies/*.json` как JSON Schema 2020-12 | Все парсятся; `glossary.json` валиден; типы без схемы явно перечислены как prose-only | нет |
| CASE-5 | AC-3 | Копия F с удалённой body-схемой используемого типа | Запустить новый тест | Тест падает и называет тип без схемы и без записи prose-only | нет |
| CASE-6 | AC-4 | Копия F с документом необъявленного типа; копия F с дублем в `document_types`; копия F с невалидной body-схемой | Запустить `doc/tests/run.sh --brief` в каждой копии | Прогон падает с указанием причины; на эталонном дереве проходит | нет |
| CASE-7 | AC-5 | Копия F с документом недопустимого статуса и копия с `draft`/`accepted` | Запустить `validate --brief` | Недопустимый статус отвергается, существующие `draft`/`accepted` валидны; enum совпадает в трёх источниках | нет |
| CASE-8 | AC-6 | Эталонное дерево | Выполнить `validate --brief`, `index check`, `docs paths --check`, `doc/tests/run.sh --brief` | Все exit 0; diff не меняет смысловые разделы документов | нет |
