# UI-0029-0001: JSON-контракт и пилот

## Цель
Подготовить независимый эталон продуктового поведения для CLI и сквозной приёмки. Вход, ветки и ожидаемые состояния заданы в [плане родителя](../../../stage1/plan.md#приёмка).

## Правила проекта
`CAP-addressable-contracts#anchors`: ID ветки сохраняет смысл при переносе файла; `#invariants`: ссылка не доказывает прохождение проверки.

## Решения и артефакты
Описать `doc/architecture/schemas/product-flow.schema.json` и применимость контракта в архитектурной записи. В `doc/tests/test_doc_contracts.py` подготовить генератор отдельного локального репозитория P и независимый оракул публичной отмены. Не выводить исходы из JSON, который проверяется. Описать классификацию: процедура фабрики, продуктовый флоу, неоднозначная запись для ручной сверки. У переносимой записи ровно одна активная модель; неперенесённый Markdown остаётся доступен.

## Приёмка
| CASE | AC | Дано | Действие | Ожидание и проверка | Ребёнок |
|---|---|---|---|---|---|
| CASE-1 | AC-1 | P и эталон исходов родительского CASE-1 | Проверить схему и выполнить отмену | Четыре ветки совпадают с независимым оракулом состояний и количества возвратов; тест повтора в baseline обозначен пробелом | нет |
| CASE-2 | AC-2 | P без `outcome`, Markdown-процедура `FLOW-create-task` и пример переносимой продуктовой записи | Проверить схему и применить правила классификации | Ошибка у `deny-shipped/outcome`; процедура не переносится, продуктовому ID не оставляют второй активный источник | нет |

## Оценка и декомпозиция
8 ч: 3 ч схема и контракт, 5 ч эталон и фикстура. Дочерних задач нет.

## Проверка
`python3 -m unittest doc.tests.test_doc_contracts -q`. После проверки сохранить хеши модели и фикстуры. Откат: оставить прежний Markdown и снять регистрацию JSON-схемы.
