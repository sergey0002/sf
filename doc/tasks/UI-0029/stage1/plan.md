# UI-0029: Карта продуктового поведения для агента

## Задача и связи

[Карточка](../task.json), `stage1`. Уточнение владельца заменяет первоначальное предложение о каталоге внутренних маршрутов. Постановка не запускает реализацию.

## Цель и границы

Помочь агенту найти применимые правила и варианты поведения в большой базе, не превращая модель в оркестратор. `task-conf`, `task select-flow`, существующие карточки и журналы остаются как есть. JSON вводится только для продуктовых флоу; Markdown процедур, ADR и ещё не перенесённых флоу сохраняется.

## Правила проекта

- `CAP-addressable-contracts#anchors`, `#search`, `#context`: стабильные адреса, ограниченная выдача и явная неполнота (AC-1–AC-2).
- `CAP-addressable-contracts#impact`, `#invariants`: фактический diff, доказуемые связи, никакой записи при чтении (AC-3).
- `ENT-verification-evidence#case-coverage`: результат и его свежесть относятся к проверенному снимку (AC-4–AC-5).
- `ARCH-contract`, разделы о флоу и правилах: трассировка условий, исходов и исключений; изменение формата оформить как ADR, не выдавая проект за принятый стандарт (AC-1).
- Справочные практики, не проектные требования: [виды флоу и таблицы решений](<../../../../data/sdd-encyclopedia/Флоу/Стандарты описания флоу.md>), [отказы и границы процесса](<../../../../data/machinedocs-encyclopedia/Документация/Флоу.md>), [живые спецификации на примерах](../../../../data/sdd-research/09-bdd-исполняемые-спеки.md). Заимствуем представления и независимые оракулы, а не обязательную нотацию или движок.

## Решения и альтернативы

- Хранить один JSON на связный процесс, с адресом `FLOW-ID#branch-id`, статусом и применимостью. Условия и постусловия принадлежат ветке, код и тесты остаются внешними источниками. Таблица решений и граф строятся на чтении; отдельный каталог вручную и BPMN/DMN-движок не нужны.
- Расширить `docs`; не вводить второй интерфейс постановки и исполнения. Предлагаемые входы: `docs search <query> --type product-flow --json`, `docs read <FLOW-ID#branch-id> --json`, `docs flow <FLOW-ID> --view decisions|transitions|refs`, `docs context --task <key> --flows --json`, `docs impact --since <rev> --scope all --flows --json`, `docs check-links --json`. Для точных кандидатов `docs search` поддерживает фильтры `--domain`, `--path`, `--symbol`. Существующая выдача без новых флагов сохраняется.
- Новые представления компактны и стабильны: ID, причина, ссылка для раскрытия, применимость, `complete` и `omitted` при усечении. Пустой поиск не равен полному покрытию. Не загружать тела связанных файлов по умолчанию.

## Риски, границы и откат

- Нет гарантии обнаружить необъявленную ветку. Неоднозначность, неподтверждённая применимость и неизвестная база явно отражаются; агент проверяет смысл по публичному поведению.
- Диагностика и dry-run не пишут; фактический отказ закрытия сохраняет состояние и журнал. Гейт только для установленной связи и применимых обязательств; не строить новый журнал или протокол записи. Перепроверять снимок перед изменением состояния.
- Откат: выключить новый гейт, вернуть прежнее чтение Markdown и перестроить только индекс; сохранить JSON, доказательства и историю. Ротация домена только после сверки, без перезаписи истории и двух активных записей одного ID.

## Артефакты и порядок

1. `0001`: предложенные `doc/architecture/schemas/product-flow.schema.json`, запись формата и перечень категорий переноса; локальная многомодульная фикстура в тестах. Объявить пути в `doc/config/paths.yaml`. Пилот строится в отдельном временном Git-репозитории; не использовать поведение `sf` как предмет пилота.
2. `0002`: `doc/tools/arch/` и контракт `doc/architecture/system/addressable-contracts.md`; добавить загрузку/индекс, проекции, проверку ссылок и влияние. Оракулы в `doc/tests/test_doc_contracts.py`.
3. `0003`: `doc/skills/` для подготовки, аудита, проверки, документирования и закрытия; интеграция проверки в `doc/tools/arch/` и сквозные тесты. Следующие домены переносить только после сверки с контрактами и тестами; не обещать полный охват всей базы в этом срезе.

## Приёмка

Фикстура P: отдельный локальный Git-репозиторий с модулями `orders`, `billing`, `shipping`, публичной отменой заказа и ветками `cancel-unpaid`, `cancel-paid`, `deny-shipped`, `retry`. Эталон: неоплаченный заказ отменён без возврата; оплаченный даёт ровно один возврат; отгруженный остаётся без изменения; повтор не удваивает возврат. База B содержит карту и тесты без теста повтора, а также ветку `legacy-cancel`, применимую только к прежней версии API. Diff D меняет возврат в `billing`: оплаченный заказ отменён, при недоступном платёжном сервисе возврат ставится в очередь ровно один раз даже при повторе. Это меняет `cancel-paid` и добавляет `refund-deferred`. D также удаляет `legacy-cancel` вместе с поддержкой прежней версии API и содержит несвязанный файл. Для негативных сценариев использовать независимые копии P. Проверка сравнивает заранее заданные ID и постусловия, а не два представления одного парсера.

## Оценка и декомпозиция

40 ч, high: 8 ч схема/фикстура, 16 ч CLI, 16 ч интеграция. Порядок `0001 → 0002 → 0003`; результаты независимо проверяемы, у технических детей нет собственного маршрута.

## Проверка и evidence

Целевой прогон: `python3 -m unittest doc.tests.test_doc_contracts -q`, затем `bash doc/tests/run.sh --brief`. Зафиксировать хеши базы, определения, кода и тестов, фактические команды и исходы CASE. Проверить размеры выдачи на фикстуре с большим числом несвязанных веток: новый контекст ограничен запрошенным бюджетом, сортировка воспроизводима. `not_run` до выполнения.

## Открытые вопросы и одобрения
