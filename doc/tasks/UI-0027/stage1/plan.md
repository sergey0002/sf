# UI-0027: Git-процесс задач

## Правила проекта

- `FLOW-cli-task-lifecycle`, `task workspace`: сохранить просмотр без записи; отдельная CLI-операция готовит ветку (AC-1–AC-2).
- `MAN-software-factory`, «Release target и ветка» и «Review artifacts и публикация»: неизвестный релиз блокирует переход, шаблоны задаёт тип, публикация не подразумевает расширение прав (AC-1–AC-4).
- `ENT-verification-evidence`: привязать согласование к проверенному снимку; изменение данных или цели делает согласование недействительным (AC-3–AC-4).
- `FLOW-task-lifecycle`: сохранить границу подготовки и исполнения; штатный ребёнок наследует ветку родителя (AC-2 и AC-5).
- До регистрации `index check` уже сообщал о битой ссылке `entities/flow-definition.md`; исправление соседнего изменения не входит в постановку.

## Порядок

1. `0001`: валидация конфига, preview и отдельная команда подготовки. Проект задаёт remote, main, шаблон/реестр релизных веток и `dirty_worktree`; каждый тип задаёт шаблоны и Git-политику. Использовать `features/#{task_key}` и `bugfixes/#{task_key}` для соответствующих типов, поддержать `{task_number}`. CLI проверяет имя средствами Git. При `unset` использовать настроенную основную ветку; при неизвестном релизе не подставлять её.
2. `0002`: клиентонезависимый `git-workflow` и шаги публикации после верификации; сообщение формирует CLI из шаблона и краткого описания агента. По умолчанию только Jira верхнего уровня публикуется после подтверждения; для остальных явная настройка типа. Коммит и push составляют один пакет согласования, но не являются атомарной Git-операцией.
3. `0003`: при выключенной интеграции не менять цель; при включённой показать её и удалённые эффекты до согласования. Не зашивать отдельный worktree или публикацию для детей. Описать будущий режим: отдельный непересекающийся ref от SHA родителя, локальный коммит и интеграция только в родителя без самостоятельной публикации.
4. В реализации закрепить имена команд и коды отказа в публичной справке. Ниже `task git prepare`, `task git publish --preview` и `task git publish --confirm <preview-id>` обозначают предлагаемые публичные точки входа, а не существующие команды. `go-to-task` показывает JSON-результат и запрашивает решение при `ask`; CLI не угадывает ответ. `fetch` выполняется только в разрешённом контексте; при расхождении истории не делать rebase/reset.

## Приёмка

Фикстуры: отдельные временные Git-репозитории с локальным bare remote `origin`, базой `main` и релизной веткой `releases/v2.1`. Оракулы: `git status --porcelain`, `git rev-parse`, `git worktree list`, `git ls-remote` и хеши файлов до/после. Никаких операций с настоящим remote.
