## 4. Дефекты реализации

**D1. Типовая политика не применяется в реальном CLI (критично).**
`acceptance_state` принимает `root` и разворачивает политику только при `isinstance(root, ProjectConfig)`. Все три вызова передают `project_config.root` (Path): `task_ops.py:1239`, `task_ops.py:1711`, `validation.py:712`. Проверка:

```
acceptance_state(cfg.root, …, task_type='research') -> True   (политика не применена)
acceptance_state(cfg,      …, task_type='research') -> False  ("unknown plan tier 'full'; use micro, standard")
```

Следствие: `diagnose`, `close` и `validate` не enforce-ят типовые разделы, лимиты и правила; работают старые константы. AC-4/AC-6 не выполнены, тест `test_micro_plan_requires_sections_and_respects_line_limit` падает именно поэтому.

**D2. Правило `case_min` с `when` молча игнорируется.** `evaluate_rules` делает `if rule.get("when"): continue`. Правило `feature: case_min 2 when contract_or_storage` (закрытое решение владельца) не проверяется нигде. Нужен либо признак в карточке (`contract_change: true`), либо явное удаление условного правила из конфига.

**D3. Расхождение с записанным контрактом слияния.** `task.json` фиксирует «списки заменяются целиком», реализация делает union `required_sections` (`_merge_tier`). Union выбран ради safety floor, но контракт и исследование не обновлены — это дрейф, а не документированное решение.

**D4. Хрупкие пути.** В `paths.yaml` добавлены 36 точных записей `types/<type>/plan/<tier>.md`. Любой новый tier или тип требует ручной правки списка. Грамматика путей не поддерживает рекурсивный шаблон.

**D5. Отсутствующий артефакт 0005.** `subtasks/0005/task.json` ссылается на `doc/tasks/UI-0032-0005/research/taxonomy-decision.md`; файла нет, и путь не совпадает с объявленным `{tasks}/{task_key}/research/{slug}.md` для `task_key=UI-0032`.

**D6. HEAD красный.** `bash doc/tests/run.sh --brief` — 27 падений. Причина не в политике: коммит `6213d24` внёс требование `branch`/`release_branch`/`target_release` (из чужого WIP) вместе с реализацией UI-0032, а фикстуры это не задают. На родительском `218c5e8` тот же тест зелёный — проверено worktree.

**D7. Мелкое качество кода.** `except (OSError, ValueError, Exception)` в `_schema_errors` глушит любые ошибки валидатора; `root: Path` в аннотации не соответствует фактическому использованию; `plan_tier_problems` сохраняет мёртвую ветку с константами.

4. Индекс и `validate` проходят, то есть формально документация согласована; содержательное противоречие п.1 машинно не ловится.
