# Политика планов и таксономия типов задач: исследование

Источник для UI-0032. Фиксирует выбранные разделы плана, правила приёмки и предложение по новым типам. Решение по новым типам требует одобрения владельца (см. «Фазы»).

## 1. Вопрос

Сейчас tier'ы плана заданы глобально в `doc/tools/arch/acceptance.py`, а тип задачи влияет только на `required_fields`, `allowed_flows`, `complexity` и политики детей. Нужно: свои разделы, шаблоны и правила приёмки у каждого типа; глобальные дефолты для совместимости; ответ, какие типы задач добавить.

## 2. Принципы выбора

1. **Тип = проверяемый результат, а не активность.** Если у двух «типов» одинаковый оракул, это профиль одного типа, а не новый тип.
2. **Правило проверяемо или не существует.** Требование без метода верификации — пожелание (ISO/IEC/IEEE 29148, `data/sdd-research/06-качество-и-трассируемость.md` §3).
3. **Один AC — одно обязательство; наблюдаемый исход.** EARS/Given-When-Then, негативные сценарии обязательны при изменении контракта (`06-...` §4, `05-шаблоны.md` §1).
4. **Трассировка обязательна.** AC → CASE → публичный вход → проверка (`06-...` §2).
5. **Тяжёлый процесс только для тяжёлой задачи.** Quick Spec для мелочи (`06-...` §7).
6. **Правила живут в конфиге, а не в коде.** `VIEW-cli-package:75`.

## 4. Матрица существующих типов

Общий safety floor для всех: каждый AC покрыт CASE с независимым оракулом; точная команда проверки; откат; `planned_checks` покрывают все AC.

`micro` = разделы сверх «Приёмка»/«Проверка». `standard`/`full` перечисляют разделы сверх floor.

| Тип | Профиль / оракул | micro | standard | full | Правила приёмки |
|---|---|---|---|---|---|
| `feature` | implementation / behavior | Изменение | Цель и границы, Правила проекта, Решения, Артефакты и порядок, Оценка и декомпозиция, Риски и откат | + Задача и связи, Открытые вопросы и одобрения | `case_min: 1`; при изменении контракта или хранения `case_min: 2` и обязательный негативный/совместимый кейс |
| `bugfix` | regression / reproduction | Воспроизведение, Изменение | Цель, Воспроизведение, Причина, Правила, Решение, Регрессия, Оценка, Риски | + Задача и связи, Границы данных | `case_min: 2` (воспроизведение + регресс); `section_present: Воспроизведение`; `section_present: Регрессия` |
| `refactor` | preservation / differential | Изменение, Эквивалентность | Цель, Правила, Решения, Инварианты поведения, Порядок, Дифференциальная проверка, Оценка, Риски | + Задача и связи, Контракты данных, Границы прерывания | `case_min: 2` (до/после эквивалентность + целевой); `section_present: Инварианты поведения` |
| `docs` | documentation / inspection | Изменение | Цель, Источники, Затронутые документы, Правила, Проверка путей и ссылок, Оценка, Риски | + Задача и связи, Адреса и индекс | `case_min: 1`; `command: docs paths --check`; `command: validate --brief` |
| `research` | research / evidence | Вопрос, Выводы | Вопросы, Метод, Источники, Варианты и критерии, Выводы, Рекомендация, Ограничения, Открытые вопросы | недоступно (`complexity` ≤ medium) | `section_min_items: Источники ≥ 3`; `section_min_items: Варианты и критерии ≥ 2`; `section_present: Рекомендация` |
| `audit` | audit / findings | Объём, Findings | Объём и критерии, Метод, Findings, Отклонения, Границы покрытия, Рекомендации | + Задача и связи, Риски и приоритеты | `section_present: Findings`; `table_column: Findings/Severity`; `section_present: Границы покрытия` |
| `planning` | planning / decision | План, Варианты | Цель, Входные требования, Варианты и отклонённые, Решения, Декомпозиция, Зависимости, Критерии готовности, Риски | + Задача и связи, Контракты, Открытые вопросы и одобрения | `section_min_items: Варианты и отклонённые ≥ 2`; `section_present: Декомпозиция` |
| `jira-incoming` | intake / mapping | Источник, Требование | Источник и маппинг, Требование, Границы, План, Приёмка, Синхронизация с трекером, Риски | + Задача и связи, Полномочия записи | `section_present: Источник и маппинг`; внешняя запись только при `approvals` |
| `scaffold` | scaffold / structure | Каркас, Проверка | недоступно (`complexity` = low) | недоступно | `case_min: 1`; только структурная проверка, семантическая приёмка запрещена |
| `subtask` | implementation / behavior (legacy) | Изменение | Цель, Приёмка, Оценка, Проверка | как `feature` без декомпозиции | `case_min: 1`; `selectable: false` (UI-0030), чтение старых записей сохраняется |

Шаблоны: `types/<type>/plan/<tier>.md` для каждого tier из `complexity_allowed`. Итого 27 файлов: `scaffold` — 1, `research` — 2, остальные восемь типов — по 3.

### Выбираемые и legacy типы

`selectable` в конфиге типа отделяет типы, доступные для новой постановки, от legacy-чтения. Правило сверки с `paths.yaml project.task_types`:

- каждый каталог с `selectable: true` обязан быть в `task_types`, и каждая запись `task_types` обязана иметь каталог;
- каталог с `selectable: false` может отсутствовать в `task_types` и не считается расхождением, но не предлагается для новой постановки;
- карточка с legacy-типом читается и валидируется, а новая постановка с ним отвергается.

Так UI-0030 может убрать `subtask` из выбираемых типов, не удаляя каталог и не ломая старые записи.

## 5. Каталог правил приёмки

Правила декларативны и проверяются общим оценщиком; семантику оракула оценивает агент.

| Kind | Параметры | Машинная проверка |
|---|---|---|
| `section_present` | `section` | заголовок с этим текстом существует |
| `section_min_items` | `section`, `min` | в разделе ≥ `min` непустых пунктов (строки списка или строки таблицы) |
| `link_min` | `section`, `min` | в разделе ≥ `min` ссылок или inline-кода |
| `table_column` | `section`, `column` | в таблице раздела есть колонка |
| `case_min` | `min` | `planned_checks` покрывает ≥ `min` кейсов |
| `command` | `command` | команда присутствует в блоке «Проверка» плана |

Оценщик не выводит смысл из текста и не заменяет агента: он подтверждает только объявленную структуру. Ошибка правила называет файл, раздел и правило.

## 6. Новые типы: предложение

Правило: новый тип добавляется, только если у него **другой оракул** и другой набор обязательных разделов. Иначе это профиль существующего типа.

### Фаза 1 — предлагается добавить

| Тип | Результат | Оракул | Ключевые разделы | Правила |
|---|---|---|---|---|
| `spike` | Ответ на вопрос и решение о следующем шаге за фиксированное время | decision | Вопрос, Таймбокс, Метод, Эксперимент или прототип, Результат, Решение и следующие шаги | `section_present: Таймбокс`; `section_present: Решение`; прототип не считается production-кодом без отдельного ревью |
| `migration` | Данные или контракт переведены с проверяемой целостностью и откатом | integrity | Текущее состояние, Целевое состояние, План миграции, Идемпотентность и повтор, Откат и восстановление, Проверка целостности, Cutover | `case_min: 3` (успех, повтор, откат); `section_present: Проверка целостности` |
| `incident` | Инцидент локализован и разобран без обвинений | timeline | Влияние, Таймлайн, Митигация, Причина, Что сработало и что нет, Follow-ups | `section_present: Таймлайн`; `section_present: Follow-ups`; `case_min: 2` (митигация + повтор) |

### Фаза 2 — предложить владельцу после фазы 1

| Тип | Причина отложить |
|---|---|
| `release` | Пересекается с `feature`/`migration` по проверке; нужен отдельный оракул выката и наблюдаемости |
| `security` | Может быть профилем `audit` с другим каталогом правил; сначала проверить на практике |
| `decision` (ADR) | Уже покрывается `planning`; отдельный тип оправдан, если ADR станет отдельным артефактом |

### Явно не добавлять

| Кандидат | Решение |
|---|---|
| `chore` | Слить в `refactor` или `docs`; иначе тип скрывает значимую работу |
| `test` | Покрывается `feature`/`bugfix`; отдельный оракул не нужен |
| `experiment` | Пересекается со `spike` и `research` |
| `epic` | Родительская карточка уже выражается `feature` с детьми |
| `retrospective` | Покрывается `incident`/`docs` |
| `impediment` | Это фаза `blocked`, а не тип задачи |

Каждый новый тип требует `config.yaml`, `prompt.md`, flow с `prompt.md`, шаблоны по tier, записи в `paths.yaml`, проверки и тесты. Поэтому фаза 1 входит в UI-0032 как отдельный срез, а фаза 2 — только решение, без реализации.

## 7. Открытые решения

1. Добавлять ли фазу 1 (`spike`, `migration`, `incident`) в этой задаче или отдельной. Предлагается в этой, отдельным ребёнком с одобрением владельца (UI-0032-0005).
2. Порог `case_min` для `feature` при изменении контракта или хранения: 2 (принято в матрице) или 3.
3. Имена flow для новых типов: предлагается `spike-first`, `migration-first`, `incident-response`.

Решено: ключ `selectable` вводится; `subtask` получает `selectable: false` и остаётся legacy. Второй схемы конфигов не создаётся.

Ответы фиксируются в `open_questions` карточки до реализации соответствующего среза.
