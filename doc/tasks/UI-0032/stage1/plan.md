# UI-0032: Политика планов и правил приёмки по типам задач

## 1. Задача и связи

- Карточка: [task.json](../task.json)
- Стадия: `stage1`
- Родитель: нет
- Дети: `0001` конфиги и шаблоны всех типов, `0002` резолвер и оценщик правил, `0003` скилл и архитектура, `0004` совместимость и гейт, `0005` таксономия и новые типы
- Исследование: [plan-policy-and-type-taxonomy](../research/plan-policy-and-type-taxonomy.md) — матрица разделов, каталог правил, предложение по типам
- Связанные документы: `ARCH-contract`, `ENT-verification-evidence`, `SPEC-cli-implementation`, `REG-cli-validation-rules`, `VIEW-cli-package`, `REG-cli-command-map`, `FLOW-task-lifecycle`
- Смежные задачи: UI-0030 (политики типов и корпусный скан), UI-0029 (продуктовые flow), UI-0031 (paths.yaml и схемы, незакоммиченный срез)

## 2. Цель и границы

- Текущее поведение: tier'ы плана и их обязательные разделы заданы константами `doc/tools/arch/acceptance.py:15-27`, поэтому все десять типов проверяются одинаково; правил приёмки, кроме покрытия AC кейсами, нет; загрузчик типов молча пропускает каталог без `config.yaml`, а `paths.yaml project.task_types` не сверяется с каталогами.
- Требуемое поведение: `plan-defaults.yaml` задаёт совместимые дефолты и каталог правил приёмки, каждый тип объявляет свои разделы, шаблоны и правила, `acceptance_state` проверяет план по разрешённой политике `type → defaults`, а `task plan-policy` показывает её без записи. Таксономия фиксирует фазу 1 новых типов и решение по фазе 2.
- Сохраняется: имена tier'ов, маркер `<!-- plan-tier: ... -->`, правило «маркер обязателен при `estimate_hours`», поведение карточек без блока `plan`, формат `verification.json` и `acceptance_policy: case-coverage-v1`.
- Не входит: переклассификация задач, изменение evidence-хешей, внешняя запись, политика на уровне flow, реализация типов фазы 2, корпусный скан ссылок на удалённый тип.
- Ручной контроль: итоговый diff и приёмку проверяет владелец; агент не закрывает задачу самостоятельно.

## 4. Решения и альтернативы

| Решение | Причина | Отклонённые варианты |
|---|---|---|
| Одна общая JSON Schema `task-conf.schema.json` для дефолтов, конфига типа и ссылок на правила | Форма общая; UI-0030 добавит `children_policy`/`parent_policy` в ту же схему | Отдельные схемы на план, приёмку и типы |
| Дефолты и каталог правил в `plan-defaults.yaml`, переопределение в `types/<type>/config.yaml` | Сохраняет иерархию task-conf и обратную совместимость | Хранить политику только в типах и дублировать дефолты |
| Разрешение `type → defaults`, без слоя flow | Совпадает с правилом единственного источника UI-0030 | Цепочка `flow → type → defaults` |
| Слияние: скаляры переопределяются, обычные списки заменяются целиком, `required_sections` объединяются с дефолтными (safety floor), `plan_policy: replace` заменяет tier-набор с сохранением floor | Предсказуемый результат без неявной конкатенации | Конкатенация списков, глубокое слияние |
| Правила приёмки декларативны и имеют ограниченный набор kind | Правило либо проверяется структурно, либо остаётся смысловым у агента | Свободный текст правил, скрипты в YAML |
| Профильные разделы у каждого типа, шаблоны по разрешённым tier | Тип research/audit/bugfix проверяются своим оракулом | Один общий шаблон для всех типов |
| Имена tier'ов `micro|standard|full` не меняются | Сохраняет маркер, миграцию и понимание пользователя | Тип-специфичные имена tier'ов |
| Новый тип только при отдельном оракуле и отдельном наборе разделов | Иначе это профиль существующего типа | Добавлять типы по названию активности |
| Фаза 1 (`spike`, `migration`, `incident`) в этой задаче, фаза 2 — решение | У фазы 1 другой оракул и высокая польза; фаза 2 требует практики | Реализовать все кандидаты сразу |
| Обнаружение типов: каталог обязан иметь `config.yaml` и совпадать с `id`; список `paths.yaml` сверяется в обе стороны | Иначе удаление или добавление каталога молча включает и выключает проверки | Полагаться на молчаливый пропуск каталогов |

## 5. Риски, границы и откат

- Риск: `high` — меняется публичный контракт проверки плана и поведение `acceptance_plan_ready`, от которого зависит закрытие задач; добавляются новые типы.
- Смежные срезы: UI-0030 меняет `doc/config/task-conf/types/*`, `paths.yaml`, `doc/tools/arch/`, `doc/tests/` и `doc/skills/plan-task/`; UI-0031 уже изменил `paths.yaml` и схемы без коммита; UI-0029 добавляет свою схему и пути. Пересечение по файлам допустимо только последовательно, без отката чужих правок.
- Правила приёмки не должны превращаться во второй интерпретатор смысла: оценщик проверяет только объявленную структуру, иначе ложные отказы заблокируют закрытие.
- Новые типы не должны ослабить существующие: каждый проходит те же проверки схемы, шаблонов, правил и `plan-policy`.
- Обратимость: изменения локальны в CLI, конфигах, схемах, шаблонах и документации; существующие карточки не переписываются.
- Границы прерывания: запись конфигов и схем атомарна по файлу; `plan-policy` и `scan` не пишут состояние; частично записанная политика или набор шаблонов обнаруживается схемой и `validate`.
- Откат: вернуть `acceptance.py`, `validation.py`, `paths.yaml`, схемы, конфиги типов, шаблоны, скилл и архитектурные записи к снимку, удалить `plan-defaults.yaml`, шаблоны и файлы новых типов, пересобрать индекс; карточки, журналы и доказательства не откатывать, правки UI-0031 в `paths.yaml` сохранить.
