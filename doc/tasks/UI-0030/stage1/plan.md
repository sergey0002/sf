# UI-0030: Типы и политики дочерних задач

Карточка: [task.json](../task.json). Стадия `stage1`. Родителя нет.

## Цель и границы

Тип описывает результат, источник описывает происхождение запроса, а связь с родителем задаётся структурой карточек. Выбор типа принадлежит агенту; CLI проверяет выбранную форму. Формат ключей, жизненный цикл существующих карточек и доступная глубина команд остаются прежними.

## Правила проекта

| Источник | Правило | Дельта |
|---|---|---|
| `ARCH-contract`, «Поля task.json, добавляемые структурой task-conf» | Канонический тип/flow и требования к полям задаёт YAML | Сохранить; добавить явные политики положения и исходящих связей, AC-1–2 |
| `FLOW-cli-subtask-lifecycle`, команды `init/validate/status` | Роль следует из контекста родителя; `init` не заменяет регистрацию пакета | Сохранить пути и ключи; заменить дефолт типа, AC-1–2 |
| `ENT-task-record`, «Хранение» и «Инварианты» | Не переписывать подписанный intent, поток и журнал существующей записи | Сохранить, AC-3–4 |
| `FLOW-create-task`, «Основные и альтернативные пути» и «Приёмка постановки» | Внешний/пользовательский запрос поступает на вход; смысл и декомпозицию определяет агент | Сохранить, уточнить выбор типа ребёнка, AC-4 |
| `REG-cli-command-map`, `scan` | Публичный вход для диагностики задач и конфигов | Проверять связи task-conf со всем корпусом, AC-5–6 |

## Решения

| Решение | Правило |
|---|---|
| `children_policy: forbidden / optional / required-at-root` | `scaffold` запрещает детей; `feature` и `jira-incoming` требуют детей для корня; остальные рабочие типы разрешают. `required-at-root` у ребёнка допускает лист и не добавляет поддержку рекурсивной записи. |
| `parent_policy: allowed / forbidden` | `jira-incoming` только корневой. Рабочие типы разрешены как дочерние, включая `scaffold` для совместимости; скилл не использует `scaffold` как замену содержательной работе. Другие типы входящих запросов, если заведены позднее, объявляют запрет в YAML. |
| Источник не равен роли | Самостоятельный запрос пользователя регистрируется корнем; техническая подзадача к нему создаётся отдельно. Не запрещать `source.type: ui` у детей: так уже маркируются локальные дочерние карточки. Не вводить новый тип только для чата и не превращать зарегистрированный запрос в ребёнка. |
| Нет наследования типа | Для нового пакета и одиночного каркаса агент передаёт конкретный тип. Flow по умолчанию берётся из выбранного типа; явный flow проверяется. Сложность, если опущена, берётся из выбранного типа, а не из несовместимой сложности родителя; оценка не наследуется. |
| Один источник политики | Политики иерархии объявляются на уровне типа, не переопределяются flow. Сначала нормализовать старый `subtask_policy` при чтении; дубли из flow удалять только если сохраняется проверка старых `flow_version`, иначе оставить их как инертные данные. |
| Legacy только для совместимости | `subtask` перестаёт быть доступным типом постановки. Не удалять совместимое чтение или точное возобновление старого журнала: это не создание нового пакета. После миграции он не фигурирует среди выбираемых типов. |
| Контроль конфигов | Расширить `arch scan --scope tasks --fix-hints` (текст и `--json`); включить проверку в `scan --scope all` и обязательный прогон `doc/tests/run.sh --brief`. Сканировать актуальное дерево независимо от Git и фазы. Для планируемой правки запускать до/после в рабочей или изолированной копии; перехват ручного сохранения YAML не входит в scope. |
| Исправление по подсказке | Для открытой редактируемой карточки указать подходящие по конфигу варианты и зеркало, не выбирать предметный тип за агента. Для завершённой или защищённой дайджестом записи указать, как восстановить контракт для чтения или подготовить отдельную контролируемую миграцию. Никакой автоматической записи. |

## Риски, границы и откат

- Риск высокий: публичные команды, сохранённые карточки и незавершённые записи. Заранее сохранить baseline в изолированной копии с текущими пользовательскими изменениями. Не заменять файлы версией из `HEAD`.
- Проверять политику до первой записи под существующей блокировкой, не менять формат и границы журнала без необходимости. Возобновление разрешено только для совпадающего записанного пакета.
- Миграцию четырёх карточек включить одним согласованным набором изменений, применять без параллельной записи в `UI-0029`. При прерывании остановиться, сравнить с исходным снимком, восстановить согласованность до дальнейшего использования. Не вводить команду массовой миграции.
- Откатить собственные правки CLI и конфигов вместе с четырьмя карточками из baseline; историю и чужие правки сохранить. Не менять версионированную карточку напрямую при неожиданной смене формата; остановить соответствующую миграцию.

## Артефакты и порядок

1. `0001`: `doc/config/task-conf/types/*`, `doc/config/paths.yaml`, `doc/tools/arch/` и контрактные тесты `doc/tests/test_task_identity.py`. Общий preflight для `task decompose` и `task subtask init`; одинаковая политика в диагностике существующей связи и при валидации ребёнка. Не менять нынешний факт, что одиночный `init` создаёт каркас, а не запись у родителя.
2. `0002`: четыре `task.json` в `doc/tasks/UI-0029/`, актуальные `create-task`, `plan-task` (включая estimation), `go-to-task`, `arch-cli`, связанные flow/prompts и архитектурные записи. Примеры: исследование с отдельным сравнимым результатом → `research/research-first`, исправление дефекта с регрессией → `bugfix`, документация → `docs`, новое наблюдаемое поведение → `feature`. Шаг без отдельного результата остаётся в плане.
3. `0003` после `0001`: `doc/tools/arch/` (scan), `doc/tests/test_task_conf_scan.py`, `doc/tests/run.sh`, справка CLI и `doc/architecture/system/runbook.md`. С `0002` согласовать инструкции; реальные карточки в этом срезе не менять.
4. Родитель: интеграционная сверка корпуса в изолированном корне, сравнение до/после, проверка планов, docs paths и общий прогон.

## Контракты данных

Миграция по смыслу артефакта (совпадает с `kind` в карточках; тесты классификацию не выводят из `kind`):

| Ребёнок | Новый тип и flow | Основание |
|---|---|---|
| `UI-0029-0001` | `docs / docs-only` | Контракт, описание формата и независимая тестовая модель; без реализации CLI. |
| `UI-0029-0002` | `feature / standard-implementation` | Новый CLI и анализ влияния. |
| `UI-0029-0003` | `feature / standard-implementation` | Новое поведение проверки при закрытии и интеграция в рабочие маршруты. |

Обновить `task_type` и `flow` ребёнка и зеркальные поля родителя. Не менять `kind`, оценки, зависимости, пути, статус, фазу, AC, этапы, evidence, реестр или историю. Перед переключением проверить, что все три карточки всё ещё legacy и в исходном состоянии; не выдумывать поля или результаты верификации для прохождения валидации.

Инцидент скана содержит стабильный код, ключ, эффективную фазу (из `state.json` для версионированной записи), путь и указатель поля, ID типа/flow, источник правила или ожидаемый путь удалённого конфига, безопасное действие и команду повторной проверки. Группировка текста по типу или причине не теряет ключи; `--json --brief` не урезает данные. Скан учитывает совместимое legacy-чтение и закреплённую версию flow; одна смена дефолта или шаблона для новых записей не конфликт, пока сохранённый контракт работает. Недоступность закреплённого контракта диагностировать отдельно, не подставляя актуальный шаблон.

## Границы прерывания

В тестовой копии обрывать `decompose` после журнала, после первого ребёнка и после публикации списка родителя до удаления журнала. Каждый раз повторять с тем же вводом: один экземпляр каждой карточки и строки у родителя, журнал удалён только после согласованной записи. Повреждённый или конфликтующий журнал и занятый писатель: отказ без изменения всего дерева задач, включая журнал и стадии. Конкуренцию тестировать с управляемым барьером, не `sleep`.

## Приёмка
