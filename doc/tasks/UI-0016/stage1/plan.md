## Правила проекта

- `ENT-task-input`: `task.json` остаётся единственным каноническим входом;
  записи стадий дополняют его, а не заменяют.
- `ARCH-contract` §1, §5: `task.json` — canonical input; предложения и
  результаты живут в `stageN/`; CLI детерминирован и не принимает смысловых
  решений.
- `nextplan.md` §6.2, §7 Этап 1: immutable intent + `state.json` +
  append-only `events.jsonl`, CAS/revision conflicts, idempotency keys,
  migration/validate/replay, recovery после обрыва записи.
- `nextplan.md` §21.4: повтор того же события с тем же ключом и содержимым
  возвращает исходный результат; другое содержимое или несовпадающая ревизия —
  конфликт; flow version фиксируется в запущенной задаче.
- `doc/AGENTS.md`: исходный intent и критерии меняются только явным
  уточнением; технические результаты пишутся в стадию.
- `paths.yaml`: новые файлы записи должны быть объявлены в `allowed_paths`.

## Решение

- Legacy-запись (без `record_version`) читается как раньше: `phase` остаётся в
  `task.json`.
- `task migrate` добавляет в `task.json` только `record_version`,
  `flow_version` и `intent_digest`, создаёт `state.json` и `events.jsonl`.
  Исходные intent-поля не переписываются.
- `intent_digest` — SHA-256 канонического подмножества intent-полей.
  `flow_version` — SHA-256 содержимого `flows/<flow>/config.yaml`, поэтому
  правка шаблона не меняет уже запущенную запись.
- `state.json` хранит изменяемую фазу, ревизию и счётчик событий.
  `events.jsonl` — журнал с цепочкой `prev_digest`, монотонной ревизией и
  ключом идемпотентности `event_id`.
- `task event` отклоняет конфликт ожидаемой ревизии, повтор с тем же ключом и
  содержимым возвращает исходный результат без второй записи, а иное
  содержимое того же ключа — конфликт.
- `task replay` пересобирает `state.json` из журнала, проверяя цепочку
  дайджестов; повреждённое событие не материализуется.
- `diagnose`, `status`, `close` и проверка зависимостей читают действующую фазу
  из `state.json`, если запись версионирована.

## Приёмка → проверка

| AC | Fixture / действие | Наблюдаемый исход |
|---|---|---|
| AC-1 | Legacy `task.json` → `task migrate`, затем повторный `task migrate` | `validate`/`diagnose` читают запись; intent-поля и `intent_digest` не меняются; второй запуск не создаёт новых событий |
| AC-1 | `task migrate --dry-run` | Ни один файл не изменён, предпросмотр перечисляет создаваемые поля и файлы |
| AC-2 | `task event` с `--expected-revision 0`, затем повтор того же `--id`/содержимого | В журнале одна запись, повтор возвращает `duplicate: true` |
| AC-2 | `task event` с устаревшей `--expected-revision` или тем же `--id` и другим содержимым | Exit 5, `state.json` и журнал не изменены |
| AC-2 | Удалить/откатить `state.json`, затем `task replay` | `state.json` восстановлен, ревизия и фаза совпадают с журналом |
| AC-2 | Повредить строку журнала, затем `task replay` | Exit 1, `state.json` не перезаписан |

Перед изменениями зафиксировать исходный результат. Для каждого AC записать фактическую проверку и проверенный снимок в `verification.json`.

## Ревью реализации

- Проверены границы `task.json` / `state.json` / `events.jsonl` и совместимость
  legacy-записи: `phase` в `task.json` остаётся, действующая фаза версионированной
  записи читается из `state.json`.
- Найден и исправлен контрпример: обрыв между записью события и `state.json`.
  Повтор того же `event_id` теперь не только возвращает исходный результат, но и
  материализует состояние из проверенного журнала. Явное восстановление —
  `task replay`.
- Проверены отказы: устаревшая `expected_revision`, тот же `event_id` с другим
  payload, изменённый intent, повреждённая строка журнала. Во всех случаях запись
  не меняется (кроме успешного восстановления состояния из валидного журнала).
- Остаточное ограничение: повторный `close` идемпотентен только для завершённой
  записи; сценарий повторного открытия задачи в этом срезе не реализован.
