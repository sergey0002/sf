## CLI quickstart (завод)

CLI живёт в `/home/user/doc/tools/arch.py`. Детерминированные операции только — смысловые решения принимает агент.

```bash
# Сделать исполняемым (однократно)
chmod +x /home/user/doc/tools/arch.py

# Валидация всех документов архитектуры
/home/user/doc/tools/arch.py validate

# Проверить актуальность сгенерированного индекса
/home/user/doc/tools/arch.py index check

# Пересобрать index.json
/home/user/doc/tools/arch.py index build

# Список документов (id, type, domain, path, summary)
/home/user/doc/tools/arch.py list

# Показать один документ по стабильному ID
/home/user/doc/tools/arch.py show <ID>   # например: show SYS-simple-factory
```

## Создание задачи (механика завода)

1. Единственный canonical input задачи — `task.json`. **Не создавать `task.md`.** Не копировать корневой манифест в `doc/`.
2. Новая задача размещается в `/home/user/doc/tasks/<task_key>/`, например `UI-0002/`.
3. `task_number` — ровно 4 десятичные цифры (`0000`–`9999`).
4. `task_key` детерминирован:
   - Jira: bare number, без префикса (`1234`)
   - Пользовательский ввод (source.type: ui): `UI-` + цифры (`UI-0002`)
   - Любой другой источник: явный зарегистрированный префикс + цифры (`GH-0001`)
5. CLI валидирует ключи, но **никогда не выделяет номер сам**. Номер берётся из реестра `/home/user/doc/architecture/system/task-number-registry.md` или у владельца.
6. Внутри задачи создаётся `stage1/plan.md` и `stage1/verification.json` перед началом выполнения.

## Как работать с data/

`/home/user/data/` — это внешний справочник (Obsidian-организованные энциклопедии с MOC), **вне репозитория завода**. Правила:

- **Только чтение.** Не правьте файлы в `data/` как проектные файлы завода. Энциклопедии — справочный материал для ресерча, не часть фабрики.
- **Навигация через MOC/Оглавления.** Начинайте с `data/README.md` (корневой MOC), затем переходите к `Главная.md` / `Индекс.md` конкретной энциклопедии, а затем к целевым страницам. Не читайте файлы по линейному обходу — это вызывает лишние токены.
- **Читать MOC первым, затем целевые страницы.** МOC-first navigation подтверждена как правильный подход для `data/`.
- **Ссылки на корневой манифест.** Если в материалах `data/` упоминается манифест — ссылка ведёт на `/home/user/Манифест агентной software factory.md`, копии манифеста в `data/` не создаются.
- **data/ можно пополнять интернет-ресерчем**, но это остаётся справочником, не проектными файлами фабрики.

## Порядок работы через механику завода

```
Запрос от пользователя
    ↓
Создать task.json (UI-プレфикс или явный префикс источника, 4 цифры)
    ↓
Создать stage1/plan.md + stage1/verification.json
    ↓
Выполнить шаги плана (CLI, правки doc/, тесты)
    ↓
Прогнать arch.py validate + index check + doc/tests/run.sh
    ↓
Обновить stage1/verification.json фактическими результатами
    ↓
При необходимости — architecture delta в stageN/architecture-delta/
    ↓
Представить результат в чате
```

## Запуск тестов

```bash
# Все приёмочные тесты завода (13 тестов)
bash /home/user/doc/tests/run.sh

# Только тесты CLI архитектуры (5 тестов)
python3 -m unittest discover -s /home/user/doc/tools/tests
```

Ожидается 13/13 проходят.

## Границы ответственности

- Агент интерпретирует намерения, выбирает документы, планирует и судит о релевантности.
- CLI делает только детерминированные операции (валидация, индекс, список, показ). CLI не принимает смысловых решений.
- Человеческое approval требуется перед любым push/merge/deploy. Selbst-отчёт агента не является доказательством.
- Не пушат, не мерджат, не деплоят без явного разрешения.
