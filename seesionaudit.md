Kilo нашёл реальную ошибку и исправил основной сценарий отсутствующей объявленной подзадачи. Он также добавил `close --dry-run`. Cache write равен нулю, в SQLite сохранён `cost = 0`. `total` совпадает с суммой отдельных полей для этого прогона. Около 95,9% суммы входных счётчиков приходятся на cache read. Это повторённый по вызовам объём контекста, поэтому 8,16 млн нельзя интерпретировать как объём уникального текста или счёт за использование. `total` последнего ответа — 117 093, из них 113 984 cache read. Между запросами кэш повёл себя по-разному: запись 23 получила 51 838 input и нулевой cache read. Причину промаха данные сессии не объясняют.

- **Крупные чтения.** `nextplan.md` в записи 8 вернул 54 169 Б, первый `builtin.py` в записи 28 — 57 464 Б, `validation.py` в записи 30 — 32 628 Б. Вместе это около **53%** выходов всех инструментов по байтам. Узкие срезы тех же Python-файлов в записях 44, 46, 52, 69 и 71 показывают, что агент уже умел читать точечно. Весь выход инструментов — 271 398 Б, из них 234 740 Б составили операции `read`. Это размеры сохранённых ответов, включая обёртки Kilo.
- **Связь с ростом контекста.** Следующие шаги после этих трёх чтений получили соответственно 13 350, 18 028 и 13 078 input. Это корреляция соседних записей. Поля Kilo не позволяют разнести токены по каждому файлу с точностью до токена.
- **Временная копия.** 20 команд имели `workdir=/tmp/test_ui_0011`. Отдельно зафиксированы 8 записей во временную область и 13 команд подготовки, копирования либо пересоздания. Операции могут принадлежать одному сценарию и не должны складываться с общим числом вызовов как независимые категории.
- **Четыре полных прогона.** По временам инструментов суммарно около 71 с. Часть повторов объясняется добавлением dry-run, часть выполнена после обновления записей. После финального полного прогона ещё раз запущена группа структурных команд. Понять выгоду от сокращения можно на повторном прогоне с теми же AC.
- **Краткие сообщения о прогрессе.** После поручения были 17 промежуточных текстовых частей и финальный ответ. Эти сообщения полезны на смене этапа. Сообщения о каждом чтении, копировании и рутинном ретесте можно объединить в обновления по результату.

## 6. Что изменить перед следующими задачами

### P0. Сделать регрессию частью результата багфикса

- В `go-to-task` и prompt багфикса добавить правило для изменений CLI. Сначала запустить существующий CLI на **валидной** fixture. Для отказа отдельно утверждать код процесса, формат stdout/stderr и отсутствие записи. После правки повторить ту же fixture и зафиксировать ревизию. Если старый код не показал ожидаемый дефект, проверить, какой entry point был исполнен.
- Переиспользовать существующую тестовую инфраструктуру `_cli_at(root, ...)` и временные корни. Исходный CLI запускать по абсолютному пути с `--root` на данных fixture. Это позволяет использовать актуальную реализацию без копирования исходников. Для завершённого и незавершённого сценария нужны разные экземпляры данных.
- Для UI-0011 закрыть четыре проверки одним автоматизированным набором. Нужны отсутствующий ребёнок, штатная валидная карточка без детей, совместимость поведения при расхождении списка и диска, а также побайтовое сохранение для отказа и dry-run. Для неуспешного фактического закрытия проверить обещанный JSON-контракт, затем обновить документацию команды и evidence.
- В ручной процедуре сначала целевая проверка, после стабилизации — полный прогон. Повтор полного прогона оправдан после изменения проверяемого кода или конфигурации. Для записи статуса сначала `task validate`, чтобы ошибка фазы не обнаруживалась после длительного прогона.
