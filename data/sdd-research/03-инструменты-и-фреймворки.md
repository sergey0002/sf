# Инструменты и фреймворки SDD

К 2026 году spec-driven development стал стандартным режимом AI-агентов: GitHub, AWS,
Anthropic, Cursor и другие вендоры независимо пришли к одной форме workflow —
**specify → plan → tasks → implement**. Ниже — разбор основных инструментов.

## 1. GitHub Spec Kit

**Что это:** open-source toolkit (MIT) от GitHub (открыт в сентябре 2025). Устанавливает
slash-команды в 30–40+ AI-агентов (Copilot, Claude Code, Codex, Cursor, Gemini CLI, Kiro CLI…).
Не агент, а конвейер команд.

**Workflow (команды и артефакты):**

| Команда | Артефакт | Назначение |
|---|---|---|
| `/speckit.constitution` | `.specify/memory/constitution.md` | Принципы проекта (один раз на репозиторий) |
| `/speckit.specify` | `specs/NNN-short-name/spec.md` | Требования и пользовательские истории |
| `/speckit.clarify` | Дополнения в spec.md | 5–10 целевых вопросов агента, ответы вносятся в спеку |
| `/speckit.plan` | `plan.md`, `data-model.md`, `contracts/`, `research.md`, `quickstart.md` | Технический план |
| `/speckit.checklist` | Чек-листы в spec.md или отдельным файлом | Контроль качества требований |
| `/speckit.tasks` | `tasks.md` | Упорядоченные по зависимостям задачи, маркеры `[P]` |
| `/speckit.analyze` | Отчёт (read-only) | Соответствие конституции, покрытие, противоречия |
| `/speckit.implement` | Код, тесты | Выполнение задач по фазам с checkpoint'ами |
| `/speckit.converge` | Дополнения (append-only) | Сверка кода со спекой |

**Структура репозитория:**
```
project/
├── .specify/
│   ├── memory/constitution.md
│   ├── templates/          # spec, plan, tasks, checklist, constitution
│   └── scripts/            # .sh / .ps1 автоматизация
├── specs/
│   └── 001-model-routing/
│       ├── spec.md, plan.md, tasks.md
│       ├── data-model.md, research.md, quickstart.md
│       ├── contracts/      # OpenAPI, спецификации событий
│       └── checklists/
└── .github/prompts/        # промпт-шаблоны по фазам
```

**Особенности:** конституция проверяется на фазе plan (механизм «constitutional check» —
агент в роли compliance officer сверяет план с принципами); immutable checkpoints;
двунаправленная трассируемость. Накладные расходы: 1–3+ часа на фичу с ревью.

**Сильные стороны:** портативность (любой агент), самый полный набор команд, конституция
как механизм организационных правил. **Слабые:** много Markdown-файлов для ревью; нумерация
спек по умолчанию последовательная — возможны коллизии при параллельной работе.

## 2. Kiro (AWS)

**Что это:** коммерческая agentic IDE от AWS (запуск — июль 2025, GA — ноябрь 2025),
построенная на Code OSS; также CLI, web и mobile приложения. Приемник Amazon Q Developer.
Спецификации встроены в продукт.

**Спека = три файла** в `.kiro/specs/<name>/`:
- `requirements.md` — пользовательские истории + критерии приёмки в **EARS-нотации**
  (для багов — `bugfix.md`)
- `design.md` — архитектура, sequence-диаграммы, структуры данных, обработка ошибок,
  стратегия юнит-тестирования (шесть разделов: Architecture, Data Flow, Interfaces,
  Data Models, Error Handling, Unit Testing Strategy)
- `tasks.md` — задачи с графом зависимостей; независимые выполняются параллельными волнами

**Режимы:** Feature Spec (requirements-first или design-first, с гейтами утверждения между
фазами) и Quick Spec (без гейтов). Есть опция Analyze Requirements — проверка требований
на несогласованности и пробелы до дизайна.

**Контекст проекта:** steering-файлы в `.kiro/steering/` + чтение `AGENTS.md`.
**Hooks:** автоматический запуск тестов, линтеров, security-сканов по событиям (сохранение
файла, завершение задачи).

**Цены (окт. 2026):** бесплатный tier 50 кредитов/мес, платные планы $20–$200.
**Сильные стороны:** структурированные требования (EARS), трассируемость требование→задача,
нативная интеграция с AWS (Lambda, CDK, IAM). **Слабые:** vendor lock-in (собственная IDE),
кредитная модель, избыточен для мелких изменений.

## 3. OpenSpec

**Что это:** open-source CLI (MIT, Fission AI) для spec-driven изменений в существующих
кодовых базах (brownfield-first). ~73 000 звёзд GitHub. Работает с 20–40+ ассистентами.

**Ментальная модель — два каталога:**
```
openspec/
├── specs/                  # источник истины: как система ведёт себя СЕЙЧАС
│   └── <domain>/spec.md
├── changes/                # предлагаемые изменения (по одному на фичу)
│   └── <change-name>/
│       ├── proposal.md     # почему и что
│       ├── design.md       # как (опционально)
│       ├── tasks.md        # чек-лист реализации
│       └── specs/<domain>/spec.md   # дельта: ADDED/MODIFIED/REMOVED
└── config.yaml
```

**Workflow:** `/opsx:explore` (думаем, ничего не пишем) → `/opsx:propose` (черновик плана) →
`/opsx:apply` (реализация по tasks.md) → `/opsx:verify` (сверка кода с изменением) →
`/opsx:archive` (дельты сливаются в `specs/`, изменение уходит в `changes/archive/` с датой).
Расширенные команды: `/opsx:new`, `/opsx:continue`, `/opsx:ff`, `/opsx:sync`, `/opsx:bulk-archive`, `/opsx:onboard`.

**Ключевая идея — delta specs:** вместо переписывания всей спеки описывается только то, что
движется. При архивировании ADDED добавляются, MODIFIED заменяют полные версии требований,
REMOVED удаляются (удаление последнего требования домена удаляет файл спеки — требует
флага `retire_capabilities: true`).

**Сильные стороны:** лёгкий вес (ревью средней фичи 30–60 мин), параллельные изменения без
конфликтов, история аудита. **Слабые:** нет гейтов между фазами; validate проверяет структуру,
а не поведение; главная жалоба сообщества — ручной дрейф спек.

## 4. BMAD Method

**Что это:** полноценная agile-методология (MIT), реализованная через именованных агентов
с ролями: product, architecture, UX, development, testing. Фазы: clarify → plan → build and
verify → learn and adjust.

**Артефакты:** briefs, PRD, architecture-документы, initiative → epic → story tickets.
Quick Flow для мелких задач — tech spec. Самая «тяжёлая» методология из списка: каждая фаза —
это вызовы модели, т.е. расходы на API.

**Когда подходит:** крупные инициативы, где продуктовое и архитектурное мышление весит не
меньше кода.

## 5. Прочие инструменты

| Инструмент | Идея | Артефакты | Лицензия |
|---|---|---|---|
| **Agent OS** | Стандарты кодирования, инжектируемые в планы | standards + index.yml, mission, roadmap, spec folders | MIT |
| **Task Master** | Разбор PRD в очередь задач | prd.txt, tasks.json | MIT + Commons Clause |
| **Tessl** | Spec-as-source: спека регенерирует код | Спеки на реестре | Закрытая бета |
| **C²** | Контекст, накапливающийся по всему репозиторию | router, docs/contextbase, PRD→prompt cascade | CC BY-NC-SA |
| **Claude Code plan mode** | Лёгкий spec-first без инструмента | План в сессии (сохраняется вручную) | В составе Claude Code |
| **AGENTS.md / CLAUDE.md** | Постоянные инструкции проекта | Markdown в корне репозитория | Стандарт сообщества |

## 6. Сравнение

| Ось | GitHub Spec Kit | Kiro | OpenSpec | BMAD |
|---|---|---|---|---|
| Тип | Toolkit (MIT) | Коммерческая IDE | CLI (MIT) | Методология (MIT) |
| Нотация требований | Свободный Markdown | EARS | RFC 2119 + Gherkin | PRD/шаблоны |
| Где спеки | `specs/NNN-name/` | `.kiro/specs/` | `openspec/specs/` + `changes/` | Файлы проекта |
| Гейты | clarify/checklist/analyze (опц.) | Утверждение между фазами | Нет | Процессные (handoffs агентов) |
| Верификация | analyze, converge | Analyze Requirements, hooks | verify (не блокирует) | Не встроена |
| Lock-in | Нет (30–40+ агентов) | Высокий (своя IDE) | Нет (20–40+ ассистентов) | Нет |
| Церемония | Средняя | Средняя | Низкая | Высокая |
| Лучший сценарий | Новая фича, смешанные агенты | AWS-команды, интегрированный продукт | Существующий код, итерации | Крупные инициативы |

## 7. Бенчмарк 2026 (50 production Python tickets)

Независимый бенчмарк (uvik.net, Q4 2026) сравнил Spec Kit, Kiro, BMAD, OpenSpec и «без спеки»:

| Arm | Merge rate | Стоимость/тикет | Медиана времени до merge | Spec overhead |
|---|---|---|---|---|
| Kiro | 82% | $2.35 | 41 мин | 16 мин |
| OpenSpec | 84% | $2.71 | 36 мин | 12 мин |
| Spec Kit / BMAD / No spec | ниже | — | — | — |

Выводы: полнота спеки ≥6/8 коррелирует с merge rate ~90%+; OpenSpec дал наименьший дрейф
(2.4%) и наименьший overhead; «без спеки» проигрывает на фичах и пайплайнах (60% merge rate).

## 8. Как выбрать

- **Большой существующий код, хотите описывать контракты без реорганизации** → OpenSpec.
- **Команда в экосистеме AWS, нужен интегрированный продукт** → Kiro.
- **Смешанные агенты, нужны гейты и конституция** → Spec Kit.
- **Крупная инициатива с продуктовой/архитектурной проработкой** → BMAD.
- **Только Claude Code и минимум церемонии** → CLAUDE.md + skill + plan mode.

Критерий выбора — не мощность фреймворка, а церемония, которую команда реально выдержит.
