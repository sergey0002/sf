# BDD и исполняемые спеки: от примеров к живой документации

Behavior-Driven Development — ближайший предок SDD и его исполняемое ядро.
Gherkin Given/When/Then был первой широко принятой попыткой executable-спецификаций,
читаемых на обычном языке. SDD расширяет эту идею с уровня сценариев на уровень
архитектуры всей системы.

## 1. Суть BDD

BDD = разговор о поведении + примеры + автоматизация. Цель — строить **правильную вещь**
(вопрос «are we building the right thing?»), тогда как TDD отвечает «are we building it right?».
ATDD (Acceptance Test-Driven Development) и BDD — две стороны одной практики:
слой приёмки ведётся от примеров, внутренняя логика — test-first.

**Ключевая идея:** критерии приёмки, тест-кейсы и документация — один артефакт.
Файл `.feature` одновременно является:
- требованиями для product owner'а;
- критериями приёмки для разработчика;
- тест-кейсами для тестера;
- скриптами для автоматизатора;
- описанием для остальных стейкхолдеров.

## 2. Discovery: Three Amigos и Example Mapping

### Three Amigos
Встреча трёх **перспектив** (не обязательно трёх людей): бизнес/продукт, разработка,
тестирование. Цель — развенчать неверные допущения до кода. В SDD-эквиваленте это
фаза clarify + ревью spec.md.

### Example Mapping (Matt Wynne)
Низкотехнологичный метод визуализации разговора — цветные стикеры:

| Цвет | Карточка | Смысл |
|---|---|---|
| 🟡 Жёлтая | Story | Пользовательская история |
| 🔵 Синяя | Rule | Правило (критерий приёмки) |
| 🟢 Зелёная | Example | Пример (Gherkin-сценарий) |
| 🔴 Красная | Question | Открытый вопрос |

Зелёные карточки превращаются в feature-файлы. Метод показывает scope и пробелы:
правило без примеров — недоопределено; вопрос без ответа — риск.

## 3. Gherkin: структура и стиль

```gherkin
Feature: [Название фичи]
  Как [роль], я хочу [цель], чтобы [польза]

  Background:
    Given [общий контекст]

  Scenario: [Название сценария]
    Given [начальное состояние]
    When [действие/триггер]
    Then [ожидаемый результат]
    And [дополнительный результат]

  Scenario Outline: [параметризованный сценарий]
    Given a cart totalling <total>
    When the user applies code "<code>"
    Then the order total shows "<expected>"

    Examples:
      | total | code   | expected |
      | 50.00 | SAVE10 | 45.00    |
      | 80.00 | SAVE10 | 72.00    |
```

**Стиль шагов:**
- **Декларативные**, а не императивные: «Then the order total shows 45.00», а не
  «click button X, type Y» — шаги описывают намерение, а не UI-механику.
- 2–5 сценариев на правило; исчерпывающие случаи — юнит-тестами (tdd-guide).
- Не гнаться через UI/браузер: медленные, волатильные тесты; внешние сервисы стабить,
  доменную логику тестировать напрямую.
- Given/When/Then — рекомендуемый шаблон, а не цель сама по себе; главное — конкретные
  согласованные примеры.

## 4. Specification by Example и Living Documentation

**Specification by Example (Gojko Adzic):** детализация фичи сценариями для улучшения
качества, сокращения переделок и коллаборации. Семь паттернов SBE включают
specs-as-tests и trustworthy living documentation.

**Living documentation:** если сценарии автоматизированы (Cucumber, SpecFlow, Behave,
Reqnroll, Karate), инструменты (Pickles, SpecFlow+ LivingDoc, Halo Reporting) генерируют
HTML-отчёты: что прошло, что упало, что покрыто — всегда актуальная документация
текущей функциональности.

**Эволюция команды** (Alister Scott): ATDD (автоматизированные acceptance-проверки) →
BDD (Gherkin-сценарии) → living documentation (публикуемые отчёты).

## 5. BDD в agile-процессе

1. **Grooming:** критерии приёмки пишутся в Gherkin; Example Mapping делает коллаборацию
   лёгкой и быстрой (20–30 мин на историю окупаются отсутствием недопониманий).
2. **Planning:** все стейкхолдеры понимают поведение; уточнения вносятся прямо в feature-файлы.
3. **Новые правила:** формализовать ВСЕ критерии приёмки как Gherkin. Странно, что story
   формализована («As a…»), а критерии — нет.
4. **QA-led BDD:** QA организует Three Amigos, демонстрирует написание критериев в Gherkin,
   ускоряя тестирование.

## 6. BDD vs TDD vs ATDD vs SDD

| Подход | Источник истины | Сильная сторона | Слабая сторона |
|---|---|---|---|
| **TDD** | Тесты до реализации | Корректность юнитов, быстрый фидбек | «Unit» расплывчато; агент, пишущий и тесты, и код, может закодировать одно заблуждение |
| **BDD** | Общие сценарии | Выравнивание бизнеса и инженерии | Становится слоем документации, если сценарии пишет одна роль |
| **ATDD** | Acceptance-тесты | Приёмочный слой от примеров | Без discovery — автоматизация неверных ожиданий |
| **SDD** | Версионированная спека + конституция | Мультифайловая работа агентов, кросс-командные фичи, регулируемые изменения | Переспецификация, нагрузка ревью, дрейф спека↔код |

BDD не заменяет TDD/ATDD — дополняет: правильные разговоры до кода + живая документация
и исполняемые тесты как результат.

## 7. Связь BDD и SDD

| BDD | SDD-эквивалент |
|---|---|
| Feature file | spec.md (раздел сценариев приёмки) |
| Scenario | Критерий приёмки / EARS-требование |
| Three Amigos | Clarify-фаза + ревью spec.md |
| Example Mapping | Структурирование spec.md: истории → правила → примеры |
| Living documentation | Verify-фазы + публикуемые отчёты тестов |
| Step definitions | Тесты, сверяемые со спекой (converge/verify) |

**Комбинированный стек:** EARS-требование (правило) → Gherkin-сценарии (примеры правила) →
автоматизированные тесты (исполнение). Ожидаемые затраты — 1.5–2× от одного формата,
но трассируемость максимальна.

## 8. Антипаттерны BDD

- Сценарии пишет одна роль в одиночку → BDD вырождается в документацию.
- Императивные шаги («click button X») → хрупкие тесты, привязанные к UI.
- Сквозные тесты через браузер для доменной логики → медленные и волатильные.
- Сценарии без discovery (без Three Amigos) → автоматизация неверных ожиданий.
- Слишком много сценариев на правило → иллюстрировать правилом, остальное — юнит-тестами.
