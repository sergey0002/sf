# Качество требований и спецификаций, трассируемость

Спека бесполезна, если ей нельзя доверять. Этот файл — о критериях качества требований,
методах верификации, трассируемости и жизненном цикле спеки.

## 1. Восемь характеристик качества SRS (IEEE 830)

| Характеристика | Что означает | Как проверить |
|---|---|---|
| **Correctness** (корректность) | Каждое требование точно описывает нужную функцию | Ревью со стейкхолдерами |
| **Unambiguity** (однозначность) | Требование допускает только одну интерпретацию | EARS-нотация, глоссарий, запрет «appropriate», «fast» без чисел |
| **Completeness** (полнота) | Покрыты все ситуации, включая невалидный ввод | Чек-лист сценариев, happy path + error path; TBD только с ответственным и сроком |
| **Consistency** (согласованность) | Нет противоречий внутри и между требованиями | `/speckit.analyze`, ручное ревью |
| **Ranking** (приоритезация) | Важность и стабильность требований указаны | MoSCoW, P1/P2/P3 |
| **Verifiability** (верифицируемость) | Каждое требование можно проверить | Метод верификации у каждого требования (см. §3) |
| **Modifiability** (модифицируемость) | Структура позволяет изменения без переписывания | Атомарные требования, дельты (OpenSpec), стабильные ID |
| **Traceability** (трассируемость) | Каждое требование связано с источником и реализацией | Матрица трассируемости (см. §2) |

## 2. Матрица трассируемости (Traceability Matrix)

Связывает требования с дизайном, задачами, тестами и кодом. В SDD это делается
ссылками в артефактах (FR-001 в tasks.md, требование в design.md) или отдельной таблицей.

| Требование | Дизайн | Задачи | Тесты | Код |
|---|---|---|---|---|
| FR-001 (логин) | plan.md §Архитектура | T005, T006 | tests/auth.test.js | src/services/AuthService.js |
| FR-002 (2FA) | design.md §Interfaces | T008 | tests/2fa.test.js | src/services/TwoFactor.js |
| NFR-001 (≤200 мс) | plan.md §Контекст | T010 | tests/perf/ | src/api/... |

**Направления трассировки:**
- **Forward:** требования → план → задачи → код (всё требуемое спроектировано и реализовано)
- **Backward:** код → задачи → план → требования (нет «лишнего» кода без требования)

**Покрытие:** каждое требование имеет хотя бы одну задачу и один тест; каждая задача
ссылается на требование. `/speckit.analyze` и Kiro Analyze Requirements автоматизируют
проверку пробелов.

## 3. Методы верификации (ISO/IEC/IEEE 29148)

Каждое требование помечается методом верификации:

| Метод | Когда | Пример |
|---|---|---|
| **Test** | Поведение можно выполнить и наблюдать | «WHEN пользователь вводит неверный пароль, система показывает ошибку» |
| **Demonstration** | Функция без инструментального измерения | UI-поток, который можно показать |
| **Inspection** | Проверка артефакта без исполнения | «Контракт OpenAPI содержит все эндпоинты» |
| **Analysis** | Расчёт, моделирование, сравнение | Производительность по модели нагрузки |

Правило: требование без метода верификации — не требование, а пожелание.

## 4. Правила написания требований (INCOSE + практика)

1. **Одно требование — одно обязательство.** Два поведения в одном предложении → разделить
   на два требования (иначе нельзя выставить один pass/fail).
2. **Одно условие на клаузу.** Каждое условие/квалификация — отдельная клауза.
3. **Позитивные формулировки, активный залог.** «Система отображает…», а не «отображение
   должно производиться». Избегать «shall not».
4. **Измеримые значения.** «Быстро» → «в течение 2 секунд»; «под нагрузкой» → «при ≤5000
   одновременных пользователей».
5. **Один provision на требование** (shall/must), единообразно по документу.
6. **Наблюдаемый отклик.** Каждое THEN называет экран, сообщение, отчёт или измерение —
   то, что проверяет тестер.
7. **Без деталей реализации.** «Система восстанавливает корзину через 7 дней», а не
   «система использует Redis для кэша корзин».
8. **Стабильные ID.** REQ-CART-01, FR-001 — идентификаторы переживают переформулировки
   и позволяют ссылаться из тестов и кода.
9. **Rationale отдельно.** Зачем требование существует — в поле Rationale, а не в тексте
   требования (ISO 29148).

## 5. Review gates: где человек проверяет

| Гейт | Что проверяется | Инструмент |
|---|---|---|
| После конституции | Принципы реалистичны и тестируемы | Ревью мейнтейнерами, PR |
| После spec.md | Требования полны, однозначны, без дизайна | Ревью PO/техлида |
| Clarify | Вопросы агента закрыты, ответы внесены | Ответы в spec.md |
| После plan.md | Дизайн соответствует спеке и конституции | Constitution check + ревью |
| После tasks.md | Задачи покрывают требования, порядок верный | Агент сверяет с планом |
| После реализации | Код соответствует спеке | analyze / converge / verify |
| Перед archive | Дельты корректны, тесты зелёные | OpenSpec verify |

Принцип: **артефакт ревьюится между фазами**, а не после всего конвейера. Это дешевле,
чем переделывать код.

## 6. Жизненный цикл спеки: static → living

По исследованиям 2026 года спеки делятся по жизненному циклу:

| Тип | Описание | Инструменты |
|---|---|---|
| **Static** | Спека пишется раз и замораживается; дрейф от кода — ручная проблема | Kiro, Spec Kit (по умолчанию) |
| **Semi-living** | Дельты отслеживают изменения; sync/archive держат спеку в курсе | OpenSpec |
| **Living** | Спека непрерывно синхронизируется с кодом (тесты, генерация) | Tessl (аспирантски), BDD-подходы |

Главная жалоба сообщества на static-спеки — дрейф: документ устаревает за часы.
Противоядия: executable specs (Gherkin-тесты как часть спеки), verify-фазы,
регулярный analyze, archive-механика OpenSpec.

## 7. Антипаттерны

| Антипаттерн | Почему вреден | Противоядие |
|---|---|---|
| «Система должна быть быстрой» | Неверифицируемо | Измеримая цель + метод верификации |
| Спека с деталями реализации | Смешивает ЧТО и КАК; дизайн нельзя менять | Изоляция фаз: spec без стека |
| Два поведения в одном требовании | Нельзя выставить pass/fail | Одно SHALL на требование |
| Конституция из аспираций | Каждое ревью превращается в спор | Только уже принятые правила |
| Переписывание spec.md задним числом | Потеря истории | Аддитивные изменения |
| Спека без владельца | Никто не поддерживает актуальность | Owner в атрибутах требования |
| Игнорирование error path | Happy path работает, прод падает | IF/THEN-паттерны EARS, негативные сценарии |
| Слишком тяжёлый процесс для мелких задач | Команда бросит SDD | Quick Spec / vibe-режим для мелких изменений |

## 8. Чек-лист качества спеки (перед implement)

- [ ] Каждое требование имеет ID, метод верификации и приоритет
- [ ] Нет слов без чисел: «быстро», «удобно», «appropriate» отсутствуют
- [ ] Error/edge cases покрыты IF/THEN-требованиями и сценариями
- [ ] NFR имеют измеримые целевые значения
- [ ] Out of scope явно перечислен
- [ ] Конституция проверена (constitution check пройден)
- [ ] Задачи трассируются к требованиям; требования покрыты задачами
- [ ] Контракты (OpenAPI) согласованы с планом
- [ ] Открытых вопросов не осталось (clarify завершён)
- [ ] Спека закоммичена в репозиторий и заревьюена
