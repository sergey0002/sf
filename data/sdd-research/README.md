# Исследование: SDD и стандарты документации программных проектов

Глубокое исследование Specification-Driven Development (SDD) — методологии, в которой
спецификация является первичным артефактом, а код — производным результатом.
Материал собран по состоянию на ноябрь 2026 года: стандарты IEEE/ISO, современные
инструменты (GitHub Spec Kit, Kiro, OpenSpec, BMAD), практики docs-as-code,
нотации требований (EARS, Gherkin, RFC 2119) и шаблоны.

## Краткий вывод исследования

1. **SDD — это инверсия источника истины.** В классической разработке источник истины —
   код, а документация дрейфует. В SDD спецификация версионируется вместе с кодом и является
   источником истины; код может «дрейфовать», потому что его можно перегенерировать.
   Формула, циркулирующая в документации GitHub и AWS с конца 2025 года: **«спека — это промпт»**
   (the spec is the prompt).

2. **Канонический набор сущностей** (конвергенция Spec Kit, Kiro, OpenSpec):
   конституция/steering (правила проекта) → спецификация/требования (что и зачем) →
   план/дизайн (как) → задачи (в каком порядке) → реализация → верификация.

3. **Стандарты требований не исчезли — они переиспользуются.** EARS (Rolls-Royce, 2009)
   стал нотацией требований в Kiro; RFC 2119 даёт силу модальным словам (MUST/SHOULD/MAY);
   IEEE 830 и ISO/IEC/IEEE 29148 задают структуру SRS и характеристики качества;
   Gherkin/BDD даёт исполняемые сценарии приёмки.

4. **Хранение — docs-as-code.** Markdown в Git-репозитории рядом с кодом, PR-ревью,
   версионирование, генерация сайта (MkDocs/Docusaurus), диаграммы как код
   (Mermaid/PlantUML/C4).

5. **Выбор инструмента зависит от контекста:** Spec Kit — портативность и гейты;
   Kiro — интегрированная среда (AWS); OpenSpec — brownfield-проекты и лёгкий вес;
   BMAD — полные agile-процессы с ролями агентов.
