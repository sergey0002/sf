# Безопасность в спеках: security requirements, abuse cases, threat modeling

Безопасность — классический пример NFR, который «забывают» в спеках и который потом
стоит дороже всего. В SDD безопасность должна быть встроена в каждый артефакт:
требования, дизайн, задачи.

## 1. Что куда принадлежит

| Артефакт | Security-содержимое |
|---|---|
| **Requirements** (spec.md / requirements.md) | Ссылки на ASVS-требования, abuse cases как «If…then…shall» критерии, классификация данных, compliance-ограничения |
| **Design** (plan.md / design.md) | Trust boundaries, заметки threat model, выбранные библиотеки с pinned-версиями и лицензиями, где происходит валидация и авторизация |
| **Tasks** (tasks.md) | Задачи на security-тесты, dependency review, обновление SBOM, CI-сканы — каждая с done-условием |

## 2. Abuse cases как критерии приёмки

Злоумышленник — тоже «пользователь» со своими сценариями. Abuse case пишется как
EARS-требование нежелательного поведения:

```
IF an unauthenticated request attempts to access /admin, THEN the API shall return HTTP 403
and shall log the attempt with source IP and timestamp.
```

**Типовые abuse cases:**
- Brute force на аутентификацию → lockout + rate limiting (EARS: IF…THEN)
- IDOR: доступ к чужим ресурсам по перебору ID → проверка владения на каждый доступ
- Injection (SQL/NoSQL/command) → параметризованные запросы, валидация на границе
- Replay атак → nonce/timestamp, идемпотентность
- Privilege escalation → deny-by-default, проверка роли на сервере
- Data exfiltration → классификация данных, маскирование в логах

## 3. OWASP ASVS как источник требований

Application Security Verification Standard (OWASP ASVS) — каталог проверяемых
security-требований по уровням (L1/L2/L3). В спеке — ссылки вида:

```
SEC-AUTH-01: Система ДОЛЖНА блокировать учётную запись после 5 неудачных попыток
в течение 15 минут (ASVS 2.2.1, уровень L2).
```

Преимущества: требования проверяемы, уровни соответствуют критичности, аудит
проходит по тому же каталогу.

## 4. Threat modeling в design.md

Минимальный threat model на фазе дизайна:

| Элемент | Пример |
|---|---|
| **Trust boundaries** | Client ↔ API ↔ DB; где заканчивается доверенная зона |
| **Активы** | Данные, ключи, сессии — что защищаем |
| **Акторы угроз** | Внешний атакующий, аутентифицированный пользователь, insider |
| **Векторы** | Injection, IDOR, SSRF, replay, supply chain |
| **Митигации** | Где валидация/авторизация, какие библиотеки, pinned-версии |
| **Остаточные риски** | Что принимаем осознанно (фиксируем в ADR) |

Диаграмма: trust boundaries на sequence-диаграмме плана; каждый переход границы —
точка валидации и авторизации.

## 5. Security-задачи в tasks.md

Каждая security-задача — с done-условием, как обычная задача:

```markdown
- [ ] T012 [P] Добавить security-тесты: brute force lockout (SEC-AUTH-01)
- [ ] T013 Обновить SBOM и проверить лицензии зависимостей
- [ ] T014 Добавить OWASP ZAP скан в CI (блок при high/critical)
- [ ] T015 Проверить: логи не содержат секретов и PII (конституция, ст. II)
```

## 6. Конституция и security

Типовые статьи конституции по безопасности (проверяемые, не аспирационные):
- Секреты никогда не коммитятся; только secret manager.
- Все внешние вызовы — timeout + circuit breaker.
- Логи не содержат сырых промптов и персональных данных (хэши и счётчики).
- Зависимости пиннятся; новые зависимости — с approval.
- Security-скан обязателен в CI; high/critical блокируют merge.

## 7. Supply chain в спеках

- **Pinned-версии** библиотек фиксируются в plan.md/research.md.
- **Лицензии** проверяются до включения зависимости.
- **SBOM** обновляется как часть задач фичи.
- **Dependency review** в CI (GitHub dependency review, Dependabot).

## 8. Compliance-ограничения как требования

Регуляторные требования — это тоже требования (constraints по ISO 29148):

| Регуляция | Что фиксируется в спеке |
|---|---|
| GDPR / 152-ФЗ | Классификация данных, сроки хранения, права субъектов, регион хранения |
| PCI DSS | Требования к данным карт, шифрование, аудит |
| HIPAA | Защита PHI, доступы, аудит-след |
| SOC 2 | Контроли доступа, change management, мониторинг |

Формат: `SEC-COMP-01: Персональные данные ДОЛЖНЫ храниться в регионе EU и удаляться
по запросу субъекта в течение 30 дней (GDPR Art. 17).`
