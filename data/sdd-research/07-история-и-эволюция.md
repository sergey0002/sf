# История и эволюция SDD

Specification-Driven Development в современном виде возник в 2025 году, но его корни —
в полувеке инженерии требований. Ниже — хронология и ключевые поворотные моменты.

## 1. Хронология

| Год | Событие |
|---|---|
| 1978–1990 | Серия **ГОСТ 19** (ЕСПД): ТЗ, описание программы, руководства пользователя и оператора |
| 1993/1998 | **IEEE 830** — стандарт структуры SRS (Software Requirements Specification) |
| 1997 | **RFC 2119** — нормативные ключевые слова MUST/SHOULD/MAY |
| 2008 | **Gherkin/Cucumber** — BDD: исполняемые сценарии Given/When/Then |
| 2009 | **EARS** — Alistair Mavin и коллеги (Rolls-Royce) на IEEE RE'09: нотация требований для авиационных систем |
| 2011 | **ADR** — Michael Nygard: лёгкие записи архитектурных решений; **ISO/IEC/IEEE 29148** заменяет IEEE 830 |
| 2017 | **Diátaxis** — Daniele Procida: фреймворк структуры документации; **RFC 8174** уточняет RFC 2119 |
| 2018 | **MADR** — Markdown Architectural Decision Records (Kopp et al., ZEUS 2018) |
| 2025, июль | **Kiro** — AWS запускает agentic IDE со spec-first workflow (requirements/design/tasks, EARS) |
| 2025, сентябрь | **GitHub Spec Kit** — open-source toolkit: constitution → specify → plan → tasks → implement |
| 2025 | **Sean Grove, «The New Code»** (AI Engineer World's Fair) — интеллектуальный импульс движения |
| 2025, октябрь | **Thoughtworks Technology Radar** — SDD переходит из curiosity в Assess; анализ Böckeler |
| 2025–2026 | Конвергенция: Anthropic (CLAUDE.md, plan mode), Cursor, Codex, Tessl, OpenSpec, BMAD |
| 2026 | SDD — дефолтный режим серьёзных AI-агентов; бенчмарки эффективности; критика дрейфа спек |

## 2. Откуда взялась идея «спека — источник истины»

Классическая разработка: источник истины — код; документация — вторична и дрейфует.
SDD инвертирует это: **исполняемые, версионируемые спецификации — первичный артефакт,
код — производный результат.** Формула эпохи: «the spec is the prompt» — вы не промптите
модель на код, а авторуете долговечный артефакт, чей основной потребитель — LLM,
а вторичный — следующий человек, который должен понять систему.

**Почему именно в 2025:** AI-агенты стали достаточно хороши, чтобы производить большие
объёмы правдоподобного кода, — и правдоподобный ≠ правильный. «Vibe coding» дал
галлюцинированные API, дрейф от намерения и распад при масштабировании. Спека стала
недостающим слоем между человеческим намерением и машинным исполнением.

## 3. Таксономия Böckeler (Thoughtworks): три уровня амбиций

| Уровень | Суть | Пример |
|---|---|---|
| **Spec-first** | Спека пишется до кода и направляет генерацию | Spec Kit, Kiro, OpenSpec |
| **Spec-anchored** | Спека остаётся якорем: тесты и код сверяются с ней непрерывно | BDD/Gherkin-подходы, verify-фазы |
| **Spec-as-source** | Код регенерируется из спеки; спека — единственный источник | Tessl (аспирантски) |

Большинство инструментов 2026 года — spec-first с элементами spec-anchored.
Spec-as-source остаётся радикальным крылом: недетерминированность генерации делает
полную замену кода рискованной.

## 4. Что SDD унаследовал от предшественников

| Предшественник | Что унаследовано |
|---|---|
| IEEE 830 / ISO 29148 | Структура SRS, характеристики качества, трассируемость, методы верификации |
| EARS (Rolls-Royce) | Нотация требований в Kiro; дисциплина формулировок |
| BDD / Gherkin | Исполняемые сценарии приёмки; «живая документация» |
| ADR (Nygard) | Долгоживущий слой решений; docs-as-code практика |
| RFC-процесс (IETF, Google, Amazon) | Ревью дизайна сообществом; proposal → discussion → accepted |
| Docs-as-code | Markdown + Git + PR-ревью + генерация сайта |
| Diátaxis | Организация документации по потребностям читателя |
| ГОСТ 19 (ЕСПД) | Культура формализованной программной документации в русскоязычной практике |

## 5. Критика и открытые проблемы

1. **Дрейф спек.** Static-спеки устаревают за часы; ручная синхронизация — главная жалоба
   сообщества. Ответы: semi-living дельты (OpenSpec), executable specs, verify-фазы.
2. **Церемония.** Полный цикл Spec Kit добавляет 1–3+ часа на фичу. Для мелких изменений —
   Quick Spec / vibe-режим.
3. **Избыточность для багов.** Kiro превращал маленький баг в 4 истории и 16 критериев
   приёмки (наблюдение Böckeler). Нужны лёгкие режимы (bugfix.md).
4. **Неверифицируемость.** Validate проверяет структуру, а не поведение; verify в OpenSpec
   явно не блокирует. Спека без исполняемых тестов — декларация намерений.
5. **Коллизии нумерации.** Последовательные номера спек Spec Kit конфликтуют при
   параллельной работе нескольких разработчиков.
6. **Спека как scaffold.** Изменение спеки — это изменение политики поведения системы,
   эквивалентное смене модели: требует governance, версионирования и ревью, как код.

## 6. Куда движется SDD (тренды 2026)

- **Executable intent:** спеки, из которых генерируются тесты, а тесты непрерывно доказывают
  намерение (Playwright-совместимые тесты, self-healing в браузере).
- **Fleet-scale:** спеки как поведение, распространяющееся на организации (shared memory,
  cross-team orchestration — Cosmos, C²).
- **Конвергенция форматов:** EARS + RFC 2119 + Gherkin складываются в единый стек
  «требование → сценарий → тест».
- **Governance спек:** спеки версионируются, ревьюятся и аудируются как код; конституции
  становятся механизмом организационных правил.
- **Сокращение церемонии:** лёгкие режимы для мелких задач, тяжёлые — для регулируемых
  и кросс-командных изменений.

## 7. Практический вывод

SDD — не мода, а возвращение к классической инженерии требований в форме, удобной
AI-агентам: Markdown вместо Word, Git вместо архивов, EARS/Gherkin вместо свободного текста,
конституция вместо устных договорённостей. Команды, которые внедряют SDD, фактически
внедряют дисциплину требований — просто с современным инструментарием.
