# Внедрение SDD в команду: brownfield, rollout, метрики

Как внедрить spec-driven development в существующую команду и кодовую базу.
Главный принцип: **инкрементальность**. Попытка ретроспективно специфицировать всю
legacy-систему неработоспособна — покрытие растёт органично, с каждым изменением.

## 1. Предусловия для brownfield SDD

1. **Базовая линия DORA-метрик:** текущий lead time for changes и change failure rate.
   Без baseline нельзя доказать, что SDD ускоряет merge и снижает регрессии.
2. **Хотя бы один инженер**, хорошо знающий архитектуру, — для ревью и коррекции
   dependency-карт, которые строит инструмент. Tribal knowledge структурируется,
   но не автоматизируется полностью.
3. **Оценка применимости:** некоторые legacy-системы требуют архитектурной модернизации
   до того, как инфраструктура спецификаций применима (опыт миграции GitHub SAML).

## 2. Пять шагов brownfield-внедрения

### Шаг 1. Зафиксировать baseline
DORA-метрики, defect density (ориентир из литературы: ~1 дефект / 1000 строк,
реальные значения сильно варьируются), текущее время ревью.

### Шаг 2. Scope каждой спеки — только изменение (delta)
Парадигмальный сдвиг: спека покрывает **дельту** намеренного изменения, а не всю систему.
Вместо ретроспективной документации legacy-кода — узкие спеки на то, что трогает изменение.
Покрытие растёт с каждой модификацией, концентрируясь в модулях активной разработки.
Аналогия: characterisation tests перед рефакторингом legacy-кода.

### Шаг 3. Записать текущее поведение рядом с изменением
Спека фиксирует: текущее поведение, целевое поведение, инварианты, границы scope.
Спецификации можно бутстрэпить из production-трафика, а не только из документации
(пример: hardening SAML в GitHub).

### Шаг 4. Машиночитаемые контракты
Ответы/контракты в спеках должны быть машиночитаемыми (схемы, OpenAPI): валидация
в CI до merge превращает спеку из неформальной прозы в проверяемый контракт.
Отсутствие ответов в схеме → schema validation error с указанием пути.

### Шаг 5. Верификация против спеки и существующих тестов
Каждый AI-assisted change обновляет соответствующую спеку — иначе разрыв вернётся
при следующей генерации и поддержке. Дисциплина важнее инструмента.

## 3. Rollout по организации (5 стадий)

| Стадия | Что делается |
|---|---|
| **1. Pick the corner** | Один high-stakes сервис с множеством ограничений, принадлежащий команде с лучшей дисциплиной бэклога |
| **2. Train the people** | Инженеры и PO практикуют написание/ревью/валидацию спек на реальном бэклоге, еженедельные сессии несколько недель |
| **3. Stand up the gates** | Общая конституция, spec review gate перед генерацией, независимые доказательства приёмки |
| **4. Make drift visible** | Версионированные baseline'ы, автоматические drift-проверки, рутина reconciliation |
| **5. Centralise and automate** | Общие спеки и контекст между командами, model tiering по шагам, agent pre-screening дрейфа |

**Пилотный рецепт (практика):**
1. Одна команда, greenfield-работа.
2. Spec Kit end-to-end на 4 недели. Без срезов углов — slash-команды как есть.
3. На 4-й неделе — ретро по **слою плана**, а не кода: захватил ли план важные ограничения?
   Где агенты дрейфовали от плана?
4. Если да — расширение на brownfield-команды через OpenSpec. Если нет — вы узнали,
   что должна говорить конституция.

## 4. Governance: AI пишет спеки, люди утверждают гейты, CI исполняет контракты

Принцип: **AI drafts, humans approve, CI enforces.** Три вещи никогда не уходят AI:
approval, implementation (ответственность) и accountability.

**Фазы и гейты (пример brownfield multi-stack системы):**

| Гейт | Что верифицирует |
|---|---|
| Baseline | Discovery coverage классифицирован и утверждён (только brownfield) |
| DoR (Definition of Ready) | Требования полны, дизайн заревьюен, impact классифицирован |
| Build-Ready | Цепочка трассируемости цела, все артефакты на месте |
| Implementation Handoff | Трекер и handoff-заметки полны до валидации |
| Closure | Спека и код выровнены, дрейф разрешён |

**CI-валидаторы (блокирующие, без уровня warn):**
1. Artifact presence checker — все артефакты на месте.
2. Traceability validator — цепочка требование→дизайн→задача→код цела.
3. Contract hygiene checker — контракты валидны и версионированы.
4. Drift detector — спека vs код.
5. Implementation closure checker — соответствие при закрытии.

**Иерархия при конфликте:** конституция → правила проекта → промпты агента → сообщение
в чате. Если агент и Slack конфликтуют — побеждает конституция.

## 5. Метрики эффективности

| Метрика | Что показывает |
|---|---|
| **Drift rate** | Расхождение спек и реального поведения: schema validation failures/sprint, contract-test failures, частота ревизий спек |
| **Regression rate** | Плотность дефектов в спечённых vs неспечённых областях; AI-изменения с формальными спеками должны трендировать ниже baseline |
| **Specification coverage growth** | Спеки добавлены за спринт (не % от total): critical-path компоненты, API с контрактами, модули активной разработки |
| **Lead time spec→production** | Ускоряет ли workflow доставку, включая ревью и переделки |
| **Defects by origin** | Intent→spec vs spec→implementation: куда инвестировать — в спеки или в валидацию |
| **Review time** | Не переехал ли bottleneck из ревью кода в ревью спек |
| **Cost per accepted change** | Токены и стоимость модели на принятое изменение |
| **Spec/code context ratio** | Доля контекста агента из версионированных спек vs сырого кода; высокий ratio = агент работает по контракту |

## 6. Типичные ошибки внедрения

- **Ретроспективная спецификация всей системы** — неработоспособно; только дельты.
- **Внедрение во все команды сразу** — начинать с одной команды и одного сервиса.
- **Спека без гейтов** — без review gate спека не становится baseline'ом.
- **Игнорирование дрейфа** — дрейф — естественное состояние; нужна рутина reconciliation.
- **Ожидание полного восстановления спеки** для продуктов с десятилетиями истории —
  практический scope: только новое поведение. Но помните: каждый greenfield становится
  brownfield — планируйте spec-anchored maintenance с первого коммита.
- **Спека как единственный вход** — без независимых доказательств приёмки (тесты, ревью)
  спека не защищает от неверного понимания.
