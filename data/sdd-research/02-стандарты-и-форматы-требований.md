# Стандарты и форматы документации требований

SDD не изобрёл требования с нуля — он переиспользовал полвека наработок в области
requirements engineering. Ниже — нормативная база: международные стандарты, нотации
формулировок и фреймворки организации документации.

## 1. Международные стандарты

### 1.1. IEEE 830-1998 — Recommended Practice for Software Requirements Specifications

Классический стандарт структуры SRS (Software Requirements Specification). Формально заменён
ISO/IEC/IEEE 29148, но его шаблон и принципы до сих пор — де-факто база в регулируемых
отраслях, госзаказах и академических программах.

**Структура документа (3 раздела):**

1. **Introduction** — назначение, область, определения/аббревиатуры, ссылки, обзор
2. **Overall Description** — перспектива продукта, функции, характеристики пользователей,
   ограничения, допущения и зависимости
3. **Specific Requirements** (60–70% объёма):
   - 3.1 External Interface Requirements (UI, hardware, software, communications)
   - 3.2 Functional Requirements
   - 3.3 Performance Requirements
   - 3.4 Design Constraints
   - 3.5 Software System Attributes (надёжность, безопасность, сопровождаемость…)
   - 3.6 Other Requirements
4. **Appendices** — глоссарий, матрица трассируемости, история изменений

**8 характеристик качества SRS по IEEE 830:** correctness (корректность), unambiguity
(однозначность), completeness (полнота), consistency (согласованность), ranking
(приоритезация), verifiability (верифицируемость), modifiability (модифицируемость),
traceability (трассируемость).

### 1.2. ISO/IEC/IEEE 29148:2018 — Requirements Engineering

Действующий стандарт (заменил IEEE 830 в 2011/2018). Охватывает весь жизненный цикл
инженерии требований, а не только документ. Вводит три типа спецификаций:

| Спецификация | Содержимое |
|---|---|
| **BRS** (Business Requirements Specification) | Бизнес-/миссионные требования: зачем проект существует |
| **StRS** (Stakeholder Requirements Specification) | Требования заинтересованных сторон |
| **SyRS** (System Requirements Specification) | Требования к системе в целом |
| **SRS** (Software Requirements Specification) | Требования к программному обеспечению |

Стандарт задаёт атрибуты требования: Id, Heading, Text, Owner, Priority, Source,
Rationale, Difficulty, Type, Status, Verification Method (Test / Demonstration /
Inspection / Analysis). Также: требования должны быть в позитивной форме, в активном
залоге, без «shall not», без «must» (из-за двусмысленности), с одним provision на требование.

**Типы требований по 29148:** Functional, Performance, Usability/Quality-in-Use,
Interface, Design Constraints, Non-Functional/Quality («-ilities»: reliability,
maintainability, security, portability…), Human Factors.

Структура ТЗ по ГОСТ 19.201-78: введение; основания для разработки; назначение разработки;
требования к программе/программному изделию; требования к программной документации;
технико-экономические показатели; порядок контроля и приёмки. По духу это аналог SRS:
функциональные требования, ограничения, критерии приёмки.

## 2. Нотации формулировок требований

### 2.1. RFC 2119 / RFC 8174 — сила модальных слов

RFC 2119 (1997) определяет точные значения ключевых слов в спецификациях:

| Ключевое слово | Значение |
|---|---|
| **MUST / SHALL / REQUIRED** | Абсолютное требование |
| **MUST NOT / SHALL NOT** | Абсолютный запрет |
| **SHOULD / RECOMMENDED** | Рекомендуется; допустимо отклонение при обоснованной причине |
| **SHOULD NOT / NOT RECOMMENDED** | Не рекомендуется |
| **MAY / OPTIONAL** | На усмотрение |

RFC 8174 (2017) уточняет: ключевые слова имеют нормативную силу только в верхнем регистре.
В практике требований: **SHALL** — для функциональных требований, **MUST** — для
нефункциональных (качественных) требований с методом верификации. Агент, читающий SHOULD,
трактует это как «можно пропустить» — поэтому сила слова должна выбираться осознанно.

### 2.2. EARS — Easy Approach to Requirements Syntax

Нотация, созданная Alistair Mavin и коллегами в Rolls-Royce (публикация на IEEE RE'09, 2009).
Принята как нотация требований в Kiro. Грамматика: фиксированный порядок клауз,
один системный субъект и один триггер на требование.

**Канонический шаблон:**
```
WHILE <предусловие>, WHEN <триггер>, the <система> SHALL <ответ>
```

**Пять паттернов:**

| Паттерн | Ключевое слово | Пример |
|---|---|---|
| Ubiquitous (всегда активно) | — | The checkout page shall display prices in the store's currency. |
| Event-driven | WHEN | WHEN the user applies code SAVE10 to a 50.00 cart, the checkout page shall show a total of 45.00. |
| State-driven | WHILE | WHILE the cart is empty, the checkout page shall disable the Pay button. |
| Unwanted behaviour | IF … THEN | IF the payment provider declines the card, THEN the checkout page shall show «Payment declined» and keep the cart unchanged. |
| Optional feature | WHERE | WHERE gift wrapping is enabled, the checkout page shall show a gift-wrap option. |
| Complex | комбинации | WHILE the user is signed out, WHEN they select Pay, the checkout page shall redirect to sign-in. |

**Правила:** 0+ предусловий, 0–1 триггер, ровно 1 имя системы, 1+ отклик; ответ должен быть
наблюдаемым (сообщение, значение, страница, состояние); одно поведение на SHALL — иначе
разделить на два требования.

**EARS vs Gherkin:** EARS формулирует правило (общее: «валидный код»), Gherkin — конкретный
пример правила («SAVE10», «45.00»). Комбинация: EARS-требование + Gherkin-сценарии под ним.

### 2.3. Gherkin / BDD — исполняемые сценарии

Язык Cucumber (Aslak Hellesøy, ~2008), выросший из Behavior-Driven Development.
Структура: Feature → Scenario → Given/When/Then. Сценарии исполнимы через step definitions
(Cucumber, Reqnroll, Behat, behave, Karate) — «живая документация».

```gherkin
Scenario: Apply SAVE10 to a 50.00 cart
  Given a cart totalling 50.00
  When the user applies code "SAVE10"
  Then the order total shows "45.00"
```

В OpenSpec сценарии Given/When/Then — часть delta specs; в Spec Kit — критерии приёмки
пользовательских историй.

### 2.4. User Stories и INVEST

Формат «Как <роль>, я хочу <цель>, чтобы <польза>». Критерии качества INVEST:
Independent, Negotiable, Valuable, Estimable, Small, Testable. Недостаток — двусмысленность
без дополняющих критериев приёмки; поэтому user story обычно дополняется EARS-требованиями
или Gherkin-сценариями.

### 2.5. INCOSE Guide to Writing Requirements

Стандарт де-факто качества формулировок (INCOSE RWG). Ключевые правила:
- одно требование — одно обязательство (C5);
- отдельная клауза на каждое условие/квалификацию (R11);
- позитивные формулировки, активный залог;
- измеримые значения вместо прилагательных («быстро» → «в течение 2 секунд»);
- проверка на «shall»-тест: каждое требование должно иметь метод верификации.

### 2.6. Приоритезация: MoSCoW

Must / Should / Could / Won't — стандарт приоритезации требований в agile-контексте.
В Spec Kit приоритеты пользовательских историй выражаются как P1/P2/P3.

## 3. Типы требований (сводно)

| Тип | Вопрос | Пример |
|---|---|---|
| **Business** | Зачем строим? | Сократить время обработки заказов на 40% |
| **User / Stakeholder** | Что нужно человеку? | Менеджер склада видит остатки по трём площадкам |
| **Functional** | Что должна делать система? | Система отображает остаток по SKU и локации |
| **Non-Functional** | Как хорошо? | Данные обновляются в течение 3 секунд после изменения |
| **Interface** | Как взаимодействует? | REST API, OpenAPI-контракт, события WebSocket |
| **Constraint** | Какие ограничения? | Только PostgreSQL; данные не покидают регион EU |

Самая частая причина провалов SRS — отсутствие или неизмеримость NFR: «система должна быть
быстрой» нельзя протестировать; «страницы загружаются в течение 3 секунд при ≤5000
одновременных пользователей» — можно.

## 4. Форматы документов по уровням

| Документ | Отвечает на вопрос | Кто пишет / читает |
|---|---|---|
| **BRD** (Business Requirements Document) | Зачем делаем? | Бизнес-аналитик / руководители |
| **PRD** (Product Requirements Document) | Что строим и для кого? | Продакт / команда |
| **SRS** (Software Requirements Specification) | Что должно делать ПО? | Аналитик + тех. вход / разработчики, QA |
| **FRD** (Functional Requirements Document) | Как ведёт себя каждая функция? | Аналитик / разработчики, QA |
| **RFC / Design Doc** | Как построим и почему так? | Архитектор / сообщество ревьюеров |
| **ADR** | Почему принято это решение? | Архитектор / будущие разработчики |
| **ТЗ (ГОСТ 19.201-78)** | Что заказано и как принимается? | Заказчик / исполнитель |

## 5. Как стандарты сочетаются в SDD-практике 2026

- **Kiro** = EARS (требования) + RFC 2119 (сила слов) + design.md (архитектура по ISO 42010).
- **Spec Kit** = свободный Markdown + user stories с приоритетами + Gherkin-сценарии;
  конституция выполняет роль design constraints из IEEE 830.
- **OpenSpec** = RFC 2119 (MUST/SHALL в требованиях) + Given/When/Then сценарии + дельты.
- **Регулируемые отрасли** = ISO/IEC/IEEE 29148 как каркас, EARS как нотация, матрица
  трассируемости как обязательный артефакт.
