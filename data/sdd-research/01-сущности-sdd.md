# Сущности SDD: что существует и как документируется

В Specification-Driven Development спецификация — не «бумага для отчёта», а структурированный
набор артефактов (сущностей), каждый из которых отвечает на свой вопрос и служит входом для
следующего этапа. Ниже — полный каталог сущностей, встречающихся в Spec Kit, Kiro, OpenSpec,
BMAD и классических методологиях (IEEE/ISO).

## 1. Карта сущностей и их связей

```
Конституция / Steering / AGENTS.md   (правила проекта, неизменяемые принципы)
        │
        ▼
Спецификация / Требования              (ЧТО и ЗАЧЕМ — поведение, без реализации)
        │  ├─ Пользовательские истории (user stories)
        │  ├─ Требования (FR/NFR, EARS-формулировки)
        │  ├─ Сценарии приёмки (Given/When/Then)
        │  └─ Критерии успеха (success criteria)
        ▼
План / Дизайн                        (КАК — архитектура, стек, модель данных)
        │  ├─ data-model.md
        │  ├─ contracts/ (OpenAPI, события)
        │  ├─ research.md
        │  └─ quickstart.md
        ▼
Задачи (tasks.md)                    (В КАКОМ ПОРЯДКЕ — декомпозиция с зависимостями)
        ▼
Код + тесты                          (реализация)
        ▼
Верификация / Анализ                 (соответствие спеке: analyze, converge, verify)
        │
        ▼
ADR (Architecture Decision Records)  (ПОЧЕМУ — решения и их обоснование, долгоживущий слой)
```

Ключевой принцип: **двунаправленная трассируемость** — вперёд (требования → план → задачи → код)
и назад (код → задачи → план → требования). Каждый артефакт — вход для следующего этапа.

## 2. Конституция (Constitution)

**Назначение:** неизменяемые принципы проекта, которые агент обязан соблюдать на всех этапах.
Решает проблему потери нефункциональных требований (NFR) при AI-генерации: «напиши страницу
логина» без конституции даст код, игнорирующий принятые в проекте стандарты.

**Где живёт:**
- Spec Kit: `.specify/memory/constitution.md`
- Kiro: steering-файлы в `.kiro/steering/` (+ `AGENTS.md`)
- Claude Code: `CLAUDE.md`
- OpenSpec: `openspec/config.yaml` (context и rules)

**Содержимое:** 5–10 проверяемых правил: стиль кода, покрытие тестами, требования безопасности,
производительность, запрещённые паттерны. Каждое правило должно быть **тестируемым**
(«каждая миграция поставляется с откатом», а не «код должен быть чистым»).

**Жизненный цикл:** версионируется; изменения — только через PR с обоснованием, ревью
мейнтейнерами и увеличением номера версии. Пишется один раз на репозиторий, а не на фичу.

## 3. Спецификация (Spec / Requirements)

**Назначение:** ЧТО строим и ЗАЧЕМ. Без деталей реализации (изоляция требований от дизайна —
принцип чистоты архитектурных решений).

**Где живёт:**
- Spec Kit: `specs/NNN-short-name/spec.md`
- Kiro: `.kiro/specs/<name>/requirements.md` (или `bugfix.md` для багов)
- OpenSpec: `openspec/specs/<domain>/spec.md` (текущее состояние) + дельты в `changes/`
- BMAD: PRD (Product Requirements Document)

**Содержимое:**
- Пользовательские истории с приоритетами (P1, P2, P3)
- Функциональные требования (FR) — в нотации EARS или свободном Markdown
- Нефункциональные требования (NFR) — с измеримыми целевыми значениями
- Сценарии приёмки в формате Given/When/Then
- Критерии успеха (измеримые, не зависящие от реализации)
- Out of scope — что явно НЕ входит
- Открытые вопросы / уточнения (результат фазы clarify)

**Правило неизменности:** после генерации spec.md и plan.md считаются историческими записями;
изменения — аддитивные (уточнения, дополнения), а не деструктивные.

## 4. План / Дизайн (Plan / Design)

**Назначение:** КАК реализуем. Переводит бизнес-требования в технический чертёж.

**Где живёт:**
- Spec Kit: `specs/NNN-short-name/plan.md` + сопутствующие файлы
- Kiro: `.kiro/specs/<name>/design.md`
- OpenSpec: `openspec/changes/<name>/design.md` (опционально)

**Содержимое:**
- Технический контекст: язык, фреймворк, зависимости
- Архитектура: компоненты, поток запросов, диаграммы (Mermaid)
- Ключевые решения и их обоснование (со ссылками на конституцию)
- **Constitution check** — явная проверка плана на соответствие принципам конституции
- Порядок создания файлов

**Сопутствующие артефакты Spec Kit:**

| Файл | Назначение |
|---|---|
| `data-model.md` | Схема БД, сущности, связи (ER-диаграммы, определения таблиц) |
| `contracts/api-spec.json` | Контракты REST API в формате OpenAPI/Swagger |
| `contracts/signalr-spec.md` | Спецификации real-time протоколов (WebSocket-события, форматы сообщений) |
| `research.md` | Исследование технологий: версии библиотек, совместимость, альтернативы |
| `quickstart.md` | Ключевые сценарии валидации для ручного тестирования (шаги, ожидаемые результаты) |

**Структура design.md в Kiro** (по официальной документации) — шесть разделов:
Architecture, Data Flow, Interfaces, Data Models, Error Handling, Unit Testing Strategy.

## 5. Задачи (Tasks)

**Назначение:** декомпозиция плана в атомарные, упорядоченные по зависимостям шаги.

**Где живёт:** `tasks.md` во всех трёх инструментах (Spec Kit, Kiro, OpenSpec).

**Структура задачи:**
- Чекбокс для отслеживания выполнения
- Последовательный ID (T001, T002, …)
- Маркер параллелизации `[P]` — независимые задачи могут выполняться параллельно
- Метка пользовательской истории (P1, P3), если применимо
- Точный путь файла
- Чёткое описание

**Гранулярность:** 10–20 микро-задач на фичу; каждая соответствует одному коммиту или
независимому изменению файла. В Kiro при запуске всех задач строится граф зависимостей,
и независимые задачи выполняются параллельными «волнами».

**Трассируемость:** каждая задача ссылается на конкретные требования (requirement-to-task
traceability), что позволяет проверить покрытие требований задачами.

## 6. Чек-листы и анализ (Checklists, Analyze, Converge)

| Артефакт / команда | Назначение |
|---|---|
| `/speckit.checklist` | Генерация чек-листов качества требований (встраиваются в spec.md или отдельным файлом) |
| `/speckit.analyze` | Кросс-артефактная валидация: соответствие конституции, покрытие требований планом, противоречия, пробелы. Уровни серьёзности нарушений |
| `/speckit.converge` | Сверка кода со спекой; только добавляющие изменения (append-only) |
| Kiro: Analyze Requirements | Проверка требований на несогласованности, двусмысленности, конфликтующие ограничения и пробелы до фазы дизайна |
| OpenSpec: `/opsx:verify` | Проверка кода против изменения: completeness, correctness, coherence |

## 7. Proposal и Delta Specs (OpenSpec)

OpenSpec вводит два типа сущностей, отсутствующих в Spec Kit/Kiro:

**Proposal (`proposal.md`)** — «почему и что»: намерение, область, подход, влияние.
Создаётся командой `/opsx:propose`.

**Delta specs** — описание изменений требований относительно текущего состояния системы,
с секциями:
- `## ADDED Requirements` — новое поведение
- `## MODIFIED Requirements` — изменяемое поведение (включается полная новая версия требования)
- `## REMOVED Requirements` — удаляемое поведение (с указанием причины)
- `## RENAMED Requirements` — переименования

При архивировании (`/opsx:archive`): ADDED добавляются в основную спеку, MODIFIED заменяют
существующие версии, REMOVED удаляются; папка изменения перемещается в
`openspec/changes/archive/` с датой — для аудита истории.

## 8. ADR — Architecture Decision Records

**Назначение:** ПОЧЕМУ принято то или иное архитектурное решение. Долгоживущий слой,
переживающий отдельные фичи. Код показывает «что», ADR — «почему».

**Формат:** один Markdown-файл на решение, 1–2 страницы. Два канонических шаблона:
- **Nygard** (2011): Title, Status, Date, Context, Decision, Consequences
- **MADR** (2018): + Decision Drivers, Considered Options, Pros/Cons of the Options

**Хранение:** `docs/adr/` в том же репозитории, именование `NNNN-title-with-dashes.md`
(например, `0007-use-postgresql-for-orders.md`), индекс в `docs/adr/README.md`.

**Правила:** принятый ADR неизменяем; отмена решения — новым ADR со статусом
«Superseded by ADR-XXXX». Ревью — через PR, как код.

## 9. Дополнительные сущности экосистемы

| Сущность | Где встречается | Назначение |
|---|---|---|
| **PRD** (Product Requirements Document) | BMAD, классический product management | Бизнес-требования: проблема, пользователи, метрики успеха, scope |
| **RFC / Design Doc** | Google, Amazon, Stripe | Предложение дизайна с ревью-сообществом: контекст, дизайн, альтернативы, rollout |
| **Steering files** | Kiro | Долгосрочный контекст проекта: стек, стандарты, структура |
| **AGENTS.md / CLAUDE.md** | Claude Code, Codex, Cursor | Постоянные инструкции проекта для агентов (формат-агностик) |
| **capabilities.md** | SDD-плагины для Claude Code | Маршрутизация задач специалистам-агентам (тип, агент, навыки) |
| **review.md** | SDD-плагины | Вердикт ревью (GO/NO-GO) с результатами spec-guard и drift-detector |
| **Контракты (OpenAPI)** | Spec Kit `contracts/` | Машиночитаемые интерфейсы: эндпоинты, схемы запросов/ответов |
| **Матрица трассируемости** | IEEE 830 / 29148 | Таблица соответствия требований ↔ дизайн ↔ тесты ↔ код |

## 10. Жизненный цикл сущности

1. **Создание** — генерация из шаблона (команда агента или вручную).
2. **Ревью** — человек проверяет артефакт между фазами (review gates).
3. **Уточнение** — clarify-фаза: агент задаёт 5–10 целевых вопросов, ответы вносятся в спеку.
4. **Заморозка** — spec.md и plan.md становятся историческими записями.
5. **Реализация** — задачи выполняются агентом по порядку.
6. **Верификация** — analyze/converge/verify сверяют код со спекой.
7. **Архивирование** (OpenSpec) — дельты сливаются в живые спеки, изменение уходит в архив.
