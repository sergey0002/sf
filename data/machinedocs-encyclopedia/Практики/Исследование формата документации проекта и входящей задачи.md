# Исследование формата документации проекта и входящей задачи

> [!abstract] Короткий вывод
> Для ядра фабрики с **одним исполняющим агентом** не требуется заводить сложный оркестрационный пакет для каждой задачи. Более устойчивый минимум — документация и контракты рядом с кодом в Git; один короткий project entrypoint как карта; канонические файлы по разным назначениям; компактная нормализованная задача с источником и стабильным namespaced ID; критерии приёмки и проверка как явные поля; дизайн/план и дополнительные спецификации — по риску и изменяемой области, не по обязательной церемонии.
>
> **Уточнение пользователя, зафиксированное в манифесте:** единственный canonical task input — `task.json`; отдельный hand-authored `task.md` не нужен. В JSON должно быть достаточно структурированных данных, чтобы CLI создавал workspace/пути/ветки и необходимые артефакты по детерминированным правилам. Человекочитаемая проекция при необходимости — производный output, не альтернативная истина. CLI отвечает за повторяемые операции и формальную валидацию; понимание intent, смысловая проверка, поиск relevant code/docs/patterns, planning и архитектурные выводы остаются агенту через skills/instructions. `AGENTS.md` — короткая карта, не монолитная копия документации. Сейчас проектируется ядро одного агента; multi-agent task graph не входит в минимальный набор.

**Срез ресёрча:** 2026-11-21. Изучены первичные/официальные материалы GitHub Spec Kit, OpenSpec, OpenAI Harness Engineering, AGENTS.md, GitHub Issue Forms, Jira Forms/REST API, OpenAPI, JSON Schema, Diátaxis, arc42, C4, MADR, Google Cloud change approach, Anthropic harness article и Backstage TechDocs. В описаниях продуктов/методик отделены документированные функции от рекомендаций для нашего случая.

## 1. Границы исследования и язык выводов

Цель — определить полезные минимальные артефакты и их роли для **проектной документации и intake**, не выбирать фабричную платформу и не утверждать окончательный workflow. Сейчас проектируется ядро с одним агентом: задача может прийти из Jira, другого tracker или чата; ручной chat skill формирует `task.json`; integrations предполагаются через CLI; task ID/path и ветка должны учитывать источник; релизная ветка/цель и человеческие approvals важны. Отдельные требования из этих условий — проектные вводные, а не выводы внешних источников.

В тексте используются три метки:

- **Наблюдение источника** — прямо описанное свойство стандарта/системы/документации. Не означает доказанную эффективность.
- **Вывод для нашего случая** — интерпретация того, какой принцип переносим и с какой оговоркой.
- **Рекомендация v0** — предложение для обсуждения и последующей проверки, а не принятое решение.

Ни один рассмотренный продукт не является единой обязательной системой. OpenSpec, Spec Kit, Issue Forms, Jira, JSON Schema, C4, arc42, Diátaxis и MADR решают разные задачи и комбинируются.

## 2. Сравнение подходов и решений

| Подход | Документированный артефакт/механизм | Что полезно заимствовать | Чего не следует автоматически копировать |
|---|---|---|---|
| **OpenAI Harness Engineering** | Репозиторная база знаний как system of record; компактный `AGENTS.md` — карта к структурированным `docs/`; проблему решать недостающей legibility/проверкой, а не бесконечным наращиванием инструкций | Репозиторий проекта как единое место для versioned project knowledge; progressive disclosure; правила на уровне, где их можно найти и проверить | Их конкретный масштаб, внутренние инструменты, агентов и метрики. Это авторский инженерный отчёт о собственном опыте, не контролируемое сравнительное исследование |
| **AGENTS.md** | Открытая конвенция plain Markdown для инструкций coding agents; README остаётся ориентированным на людей, AGENTS дополняет его инструкциями о build/test/conventions; поддерживаются вложенные файлы для локального контекста | Один предсказуемый короткий вход в репозиторий, точные команды и ссылки на источники; разделение человеческого onboarding и operational guidance агента | Считать название или формат универсальным формальным стандартом с гарантированным исполнением всеми агентами. Совместимость — ecosystem convention, инструкция сама по себе не enforcement |
| **GitHub Spec Kit** | Отдельные constitution/principles, feature spec (что/зачем), plan (техническое как), tasks (реализуемые шаги); templates, optional clarification и consistency analysis | Различать intent/requirements и выбранную реализацию; преобразовывать только сложные изменения в отдельные план/задачи; шаблон — подсказка полноты | Всегда создавать весь набор документов. Полный SDD путь может производить заметную документацию; задачи на исправление/малые изменения не обязаны проходить семь стадий |
| **OpenSpec** | `specs/` описывает согласованное текущее поведение; `changes/<change>/` содержит предложение и delta-спеки, опциональный design и tasks; завершение переносит delta в каноническую спецификацию и сохраняет архив | Разделять «что система должна делать сейчас» и «что предлагается изменить»; brownfield-изменение описывать дельтой, затем актуализировать канон; дизайн — опционален для простых задач | Вносить обязательное архивирование/delta lifecycle в каждую задачу, пока нет нужды в крупном системном source of truth и дисциплины его обновления |
| **GitHub Issue Forms** | YAML-шаблоны превращаются в формы с типизированными input/textarea/dropdown/checkbox/upload, required/optional validation; ответы создают issue | Собирать вход понятным человеку способом и сделать обязательными только поля, нужные для triage/безопасности; тип поля помогает избежать неоднозначного свободного текста | Использовать GitHub issue body как внутренний canonical task format для всех источников. UX intake и execution contract — разные слои |
| **Jira Forms / REST** | Формы могут привязываться к work type, содержать required-поля и conditional logic; Jira REST API обменивается JSON и имеет свои issue keys/fields/status/version metadata | Отделять пользовательскую форму от Jira workflow; адаптер должен явно маппить внешние поля в нормализованные поля задачи; сохранять исходный key/link | Копировать Jira issue schema в ядро. Jira-specific status, field names и custom fields не должны становиться универсальной моделью проекта |
| **JSON Schema** | Формализует shape/типы/required/enums/constraints для JSON и позволяет проверять структуру автоматически | Версионировать schema, валидировать `task.json` до исполнения, отклонять неизвестный/невалидный envelope с понятной ошибкой | Принимать валидный JSON за достаточное или качественное требование. Схема не доказывает ясность, смысл, полноту, реалистичность acceptance criteria или наличие настоящего oracle |
| **ISO/IEC/IEEE 29148:2018 (требования)** | Описывает процессы и информационные элементы requirements engineering; качество требований связано, в частности, с необходимостью, однозначностью, выполнимостью, трассируемостью и верифицируемостью; требования формулируют «что», а не преждевременно «как» | Каждый критерий должен описывать наблюдаемый результат, иметь источник/ссылку и способ доказать выполнение; помечать assumptions/open questions | Переносить полноценный системный стандарт и его объём в лёгкий ticket. Заимствуются критерии качества, не обязательная документационная церемония |
| **OpenAPI** | Машиночитаемый контракт HTTP API: понятен людям и инструментам, может питать документацию, генерацию клиентов и тестирование | Для внешних API использовать контрактный формат, а не пересказывать эндпоинты только в narrative task | Вставлять всю API спецификацию в task. Задача ссылается на конкретный contract/path/version; API schema остаётся единственной canonical спецификацией интерфейса |
| **Diátaxis** | Различает tutorial, how-to, reference и explanation по пользовательской потребности | Хранить инструкции для выполнения, справочные факты и объяснение причин как разные виды материалов; не пытаться сделать один README универсальным | Навязывать все четыре раздела каждому проекту/фиче |
| **arc42** | Двенадцать тематических областей архитектуры: цели/качества, ограничения, контекст, стратегия, building blocks, runtime, deployment, crosscutting concepts, ADR, quality requirements, risks/debt, glossary | Использовать как меню вопросов/опциональный индекс архитектурной информации; фиксировать важное качество, границы и риск прежде всего | Заполнять все 12 разделов для небольшого проекта или задачи. arc42 допускает lean/thorough варианты; это структура покрытия, не единый обязательный документ |
| **C4 model** | Иерархические виды system context → containers → components → code плюс dynamic/deployment; notation/tooling-independent | Рисовать только view, который отвечает на конкретный вопрос; в большинстве небольших проектных обсуждений context/container помогают без диаграммы каждой функции | Создавать диаграмму «для документации» без решения/аудитории; C4 — модель представления, а не архитектурный стиль |
| **MADR / ADR** | Один decision record фиксирует архитектурно значимый выбор и его обоснование; минимальные поля включают контекст/проблему, варианты и выбранное решение | Сохранять дорогостоящие/труднообратимые решения отдельно от текущего описания и от задачи; связывать ADR из project context/spec | Создавать ADR на каждый implementation detail или копировать в README все исторические варианты |
| **Google Cloud change approach** | Для описываемого Google Cloud process выделены design, development, qualification, rollout; значительные изменения проходят design review; проверки/CI и release safety — отдельные этапы | Повышать глубину design/approval по риску; отличать критерии разработки от release qualification/deployment | Считать процесс Google необходимым для каждой малой задачи. Это опубликованная практика конкретной организации/класса систем |
| **Backstage TechDocs (docs-as-code)** | Рекомендует исходную Markdown-документацию рядом с кодом в repo; CI может build/publish rendered docs, Backstage служит discovery/view layer | Источник — версия в Git; сайт/портал — представление, не второй editable source of truth | Внедрять портал, MkDocs, storage bucket или отдельный docs build ради минимального single-agent core |

### Сопоставление двух workflow-моделей

**Spec Kit** лучше структурирует полный путь от пользовательского intent к плану и декомпозиции. Его сила — явное разделение «что/почему» от «как», optional clarification/checklist/analyze и связь задач с user stories. Стоимость — несколько артефактов и больше процесса. Для single-agent ядра полезны *разделения понятий*, но не обязательное число стадий.

**OpenSpec** лучше показывает жизненный цикл знаний для изменяемого brownfield проекта: каноническая спека фиксирует текущее поведение, change folder фиксирует предлагаемый delta, завершение обновляет канон и сохраняет контекст изменения. Стоимость — поддержка канонических spec domains и проверка их соответствия shipped code. Это хорошая модель для тех областей, где от актуальной spec есть реальная польза; не требуется применять к каждому bugfix.

**Вывод:** эти подходы не конкурируют с task envelope. Они описывают артефакты внутри исполнения/изменения. Intake задаёт задачу и её происхождение; spec — контракт поведения; plan — выбранный технический путь; ADR — принятое значимое решение; tasks — чеклист выполнения. Один маленький task может использовать только envelope, а сложный change — ссылаться на несколько таких артефактов.

## 3. Рекомендация v0 по project knowledge pack

### 3.1 Минимальная структура

```text
<project-root>/
├── <единственный манифест проекта — по существующему правилу владельца>
├── AGENTS.md                 # короткий entrypoint: карта docs и точные команды
├── README.md                  # человекочитаемый обзор/quick start
├── docs/
│   ├── index.md               # карта документации и источников истины
│   ├── project.md             # цель, границы, ограничения, компоненты/владельцы
│   ├── architecture/
│   │   ├── overview.md        # context/container или текстовый equivalent при необходимости
│   │   └── decisions/         # только значимые ADR, если они возникают
│   ├── specs/                 # поведение/контракты, которые важно поддерживать
│   └── guides/                # только если есть реальные процедуры/how-to
├── contracts/                 # машинные API/data contracts, если применимо
└── tests/                     # executable acceptance/regression oracle живёт рядом с кодом
```

Это **не приказ создать все перечисленные файлы**. Минимум для пустого или небольшого проекта: один `AGENTS.md`, один `README.md`, `docs/index.md` или простой список ссылок в AGENTS, `docs/project.md` только если нужны устойчивые границы/ограничения; `contracts/`, spec и ADR добавлять при соответствующей потребности. Не создавать пустые каталоги и placeholder docs.

Условие пользователя: манифест должен оставаться **единственным файлом в корне проектируемой песочницы**, копии манифеста в энциклопедии/подпапках не создавать. Поэтому показанная строка `<единственный манифест проекта>` — место для существующего корневого файла/правила, а не предложение размножать манифест. Любой дополнительный project knowledge pack должен соответствовать этому ограничению; точное расположение entrypoint требует согласования с фактическим форматом sandbox.

### 3.2 Роли файлов: source of truth не должен дублироваться

| Файл/тип | Ответ на вопрос | Источник истины для |
|---|---|---|
| `AGENTS.md` | Где карта, какие команды/ограничения важны агенту? | Короткие инструкции и навигация; не полный набор требований/архитектуры |
| `README.md` | Что это за проект и как начать человеку? | Краткий onboarding/quickstart |
| `docs/project.md` | Зачем система существует, каковы границы и важные quality constraints? | Устойчивый контекст проекта и подтверждённые ограничения |
| `docs/specs/**` или `contracts/**` | Какое наблюдаемое поведение/интерфейс должно сохраняться? | Канонический behavior/API contract для поддерживаемых областей |
| `docs/architecture/decisions/**` | Почему выбран один из значимых вариантов? | Запись конкретного принятого архитектурного решения; статус/дата должны быть явны |
| task contract (`task.json`) | Что именно надо изменить сейчас, откуда задача и как принять результат? | Единственный canonical structured input: intent/scope/criteria и snapshot внешнего запроса; не долговременная документация поведения |
| Код и исполняемые тесты | Что реализовано и что можно воспроизводимо проверить? | Реализация и executable oracle; не вся мотивация/план/история |
| Execution report/evidence | Что агент реально сделал и проверил? | Наблюдаемая история запуска, diff/ref и результаты команд; не подменяет исходную задачу |

Обновлять canonical spec только если изменилось долговременное поведение/контракт. Не вносить в проектный контекст временные детали текущего тикета, а в issue — огромную копию существующих docs. Ссылаться на канонический документ и фиксировать минимальный immutable snapshot необходимого external input.

### 3.3 Критерии хорошего project документа

- Есть явный scope/аудитория и статус: current, proposed, deprecated или historical.
- Каждое существенное правило либо имеет observable/automated check, либо явно обозначено как rationale/guidance.
- Текущие правила короткие; глубокая информация вынесена в специализированные файлы и доступна через карту.
- Архитектурные факты, проектные ограничения, implementation details и исторические rationale не перемешаны без маркировки.
- Для API/формальной схемы используется контрактный формат (OpenAPI/JSON Schema и т.п.) там, где его умеют проверить инструменты; narrative описывает причины/ограничения и ссылается на контракт.
- Git diff/review — основной механизм изменения docs вместе с кодом; CI проверяет только то, что умеет детерминированно проверять: schema, links, generated drift, contract tests.
- Для каждого поддерживаемого doc понятны владелец/область и условие обновления. Автоматическая свежесть по дате без проверки смысловой точности не доказывает, что файл актуален.

## 4. Формат входящей задачи: сравнение вариантов

### Вариант A — один Markdown contract

```markdown
---
contract_version: 1
source: jira
source_id: PROJ-123
---
# Исправить повторную отправку формы

## Intent
...
## Scope / not in scope
...
## Acceptance criteria
- [ ] Given ... When ... Then ...
## Validation
- `...`
```

**Плюсы:** хорошо читается/редактируется в Git, низкая стоимость для chat skill и человека, один файл, narrative естественно поддерживает вопросы и оговорки. **Минусы:** поле-значения и типы менее надёжны для адаптеров; YAML frontmatter может расползаться; статус/внешняя identity/branch/release/approval metadata смешиваются с текстом; валидировать глубже приходится парсером Markdown и соглашениями. Можно улучшить YAML schema, но это всё равно означает два слоя грамматики.

**Когда разумно:** на первом бумажном прототипе для маленького процесса без строгих machine routing/branch rules; когда чтение человеком важнее строгой интеграции. С учётом будущих Jira/других adapters и `task.json` для chat intake, вероятно, недостаточно как canonical internal envelope.

### Вариант B — `task.json` как единственный canonical task input (уточнённый вариант)

**Плюсы:** устойчивые типы/required fields и source-aware identity; единый вход для чата и tracker adapters; структурная валидация; все параметры, нужные CLI для scaffold/workspace/branch/artifacts, доступны из task JSON и project config. Нет ручной синхронизации Markdown narrative с JSON.

**Издержки:** схему нужно версионировать; JSON менее удобен для свободной редакторской дискуссии; JSON Schema проверяет форму, не содержание. Семантические поля всё равно готовит/проверяет агент и сохраняет в JSON, а не перекладывает задачу на CLI parser.

**Принцип:** `task.json` содержит единственный canonical task input. CLI может рендерить Markdown/summary только как повторно создаваемый view; не принимать ручные правки такого view назад как новый источник требований. Необходимые данные не должны жить только в `task.md` или чате.

### Вариант C — tracker как внешний source of truth, локальный `task.json` как execution snapshot

**Плюсы:** не дублируется содержание в Git; авторитетное состояние приоритетов/approval/status остаётся в исходном Jira/трекере.

**Минусы:** агенту требуется online-доступ и mapping к каждому tracker; задача может редактироваться после старта, что меняет intent под ногами; чат как источник остаётся без канонического тикета; воспроизводимость запуска слабее, если не хранить snapshot. Внешнее описание может быть недостаточно структурировано для безопасного исполнения.

**Применимый компромисс:** внешний tracker остаётся внешним source of truth; локальная задача всё равно имеет `task.json` snapshot нормализованного исполнения с `source.ref` и `source.revision`/`captured_at`. CLI детерминированно фиксирует изменение revision/hash, агент оценивает semantic drift и решает, нужна ли новая стадия/уточнение; текущий snapshot не переписывается незаметно.

## 5. Рекомендация v0 по incoming task

### 5.1 Идентичность и расположение

Рекомендуемый локальный путь как **гипотеза**: `tasks/<namespace>/<source-id>/task.json`. Отдельный hand-authored `task.md` не создаётся. Например: `tasks/jira/PROJ-123/task.json` и `tasks/chat/<generated-id>/task.json`. Кодировать/нормализовать символы ID и не строить path напрямую из недоверенного внешнего текста.

Для уникальности нужны оба уровня:

- `task_id` — внутренний стабильный UUID/ULID, если у фабрики появится собственное долговременное хранилище/повторные submissions;
- `source.kind + source.project/tenant + source.id` — внешняя identity и ссылка на исходную задачу.

На самом раннем filesystem-only v0 допустим namespaced key `jira:PROJ-123` или `chat:<uuid>` без отдельного внутреннего ID, но нужно учесть переименование/перемещение проекта и повторное создание. При нескольких sources нельзя использовать только `123`/`ABC-123` без namespace, потому что коллизии и неодинаковые форматы вероятны. Jira key — идентификатор источника, не универсальный первичный ключ нашей системы.

Branch name содержит безопасный slug и нормализованный task key; source ID не должен управлять произвольным путём/командой. Точная branch convention и release mapping задаются манифестом/настройкой проекта, не повторяются вручную во всех текстовых описаниях.

### 5.2 Предлагаемый минимальный envelope

Ниже **эскиз для обсуждения**, не согласованная schema. Поля можно разделить на required/conditional/optional, а структуру отточить в отдельной спецификации ядра.

```json
{
  "schema_version": "0.1",
  "task_id": "jira:PROJ-123",
  "source": {
    "kind": "jira",
    "project": "PROJ",
    "id": "PROJ-123",
    "url": "https://tracker.example/browse/PROJ-123",
    "revision": "optional-provider-revision",
    "captured_at": "2026-11-21T12:00:00Z"
  },
  "title": "Не отправлять форму повторно при двойном клике",
  "intent": "Пользователь получает один результат от одного осознанного submit.",
  "kind": "bug",
  "scope": {
    "in": ["защитить submit от повторного запроса"],
    "out": ["не менять API контракты и схему данных"]
  },
  "acceptance_criteria": [
    {
      "id": "AC-1",
      "text": "Given ... When ... Then ...",
      "verification": "tests/integration/form_submit_test.*"
    }
  ],
  "project_context_refs": ["docs/project.md", "docs/specs/forms.md"],
  "release_target": "optional-project-defined-value",
  "risk": "low",
  "authority": {
    "allowed": ["inspect", "edit_task_scope", "run_local_tests", "create_branch", "open_pr"],
    "forbidden": ["merge", "deploy"],
    "approval_required": ["merge"]
  },
  "open_questions": [],
  }
```

**Примечания к полям:** `source.kind` — controlled enum плюс adapter extension policy; `project`/tenant нужен только если источник его требует; revision/captured timestamp полезны для snapshot/provenance, но не обязаны поддерживаться каждым tracker; `release_target` может быть null/omitted до project configuration; `risk`, allowed actions и approval policy могут быть derived/enforced by policy, а не доверяться пользовательскому task input. Не разрешать внешней задаче увеличивать полномочия агента: envelope выражает intent/request, а runtime policy ограничивает authority.

### 5.3 Критерии качества текста задачи

Короткий человеческий contract по образцу текущей заметки [[Контракт задачи для агента]]:

1. Один title с результатом/дефектом, не просто «улучшить систему».
2. Intent/пользовательское последствие и observable текущий факт/evidence; при наличии ссылки на reproduction, logs, test или source location.
3. Scope in/out и негативные ограничения; неизвестные факты — вопросы/assumptions, а не домыслы агента.
4. Критерии по одному проверяемому результату, по возможности Given/When/Then; указать oracle: конкретный тест/команда, контракт, UI outcome или ответственный approver.
5. Ссылки на существующие project docs/specs/ADRs вместо копирования; ссылаться на нужные версии/path/anchors, если это существенно.
6. Release/target branch, risk и требуемые approvals задавать отдельно от описания intent; источник может их не знать.
7. При недостаточном контексте агент сначала предлагает конкретные уточняющие вопросы. Неблокирующее предположение помечается как assumption; блокирующее — останавливает изменения.
8. Обязательная фиксация результата: changed paths/PR ref, реальные команды и статусы, неисполненные проверки, известные риски и кто должен одобрить.

### 5.4 Содержательные поля — в JSON; rendering не является input

`task.json` должен содержать intent, evidence/source refs, scope/exclusions, acceptance criteria и oracle, constraints, assumptions/open questions, project context refs, release target и approvals/owners — с required/conditional rules в схеме. Агентский skill извлекает/формулирует эти данные, уточняет существенные неизвестные и отвечает за semantic quality. CLI только валидирует типы/структуру и использует конкретные поля для безопасного создания файлов, ветки и artifacts.

Если потребуется читабельное резюме, CLI может построить его как derived view из JSON и execution evidence. Этот файл regenerable, не редактируется как авторитетное требование и не обязателен для работы агента. Архитектурный подход/точные затронутые пути agent выбирает после исследования кода; не заставлять requester угадывать реализацию.

### 5.5 Границы task data и runtime state

В v0 следует отдельно ответить, где живут status, timestamps, attempts, branch, commits, approvals, test logs и artifact paths. Не стоит по умолчанию держать изменяемый runtime status одновременно в Jira, `task.json`, чате и отдельной БД. Один компонент должен владеть каждым типом истины; остальные представляют ссылки/снимки.

Рабочая рекомендация: `task.json` — intake snapshot/schema + source identity; данные выполнения и состояние жизненного цикла — отдельная запись/append-only execution report, или явно отделённая секция с владельцем и атомарным обновлением. Для простейшего v0 можно фиксировать конечный `result.md`/report рядом с задачей, но это не заменяет систему durable state, если нужны resume/retry. Выбор этого разделения — часть будущего workflow contract.

## 6. Как выбирать степень спецификации и архитектурной документации

| Класс изменения | Минимальный набор | Добавить при необходимости |
|---|---|---|
| Малый bug/local refactor с очевидной проверкой | `task.json` с source/scope/acceptance + ссылка на oracle; короткий task narrative по необходимости | Нет отдельной project spec/design/ADR |
| Новое/изменённое observable behavior | Task + behavior spec/delta или явные acceptance scenarios; тест/contract update | Plan если технический путь неочевиден; ADR если решение архитектурно существенно |
| API/data model/security boundary/несовместимое изменение | Task + точные ссылки на contract; явно зафиксированные backward compatibility/security criteria и owner/approval | OpenAPI/schema diff, threat model, migration/rollback, design review/ADR, release notes |
| Широкое изменение нескольких компонентов/quality attribute | Task + goals/non-goals, context/dependencies, measurable quality criteria | C4 context/container/runtime/deployment view или arc42-разделы по вопросу; варианты и trade-offs; rollout/observability |
| Процедурная операция для человека | Если работа нужна — task contract отдельно | Diátaxis how-to/runbook; не помещать operational instructions только в feature spec |

Порог «нужен ли план/approval» лучше определять risk policy/необратимостью/затрагиваемыми границами, не числом строк. На маленькой задаче полное SDD может стоить больше, чем риск ошибки; для миграции, изменения API или безопасности недокументированное решение может оказаться дороже короткого review. Конкретные пороги предстоит определить в workflow.

## 7. CLI и агент: граница ответственности

**В CLI (Python/shell) — детерминированные, повторяемые действия над явными structured inputs:** API/CLI adapter fetch и exact field mapping; snapshot/revision/hash/attachment persistence; JSON parse + schema validation/version migration; безопасная генерация task key/path/branch; collision/required-field/refs checks; каталоги/templates; Git status/fetch/checkout/diff по заданным refs; запуск разрешённых команд и запись точных exit codes/output refs; структурированные execution reports и при необходимости rendering из JSON; dry-run/idempotency/понятные ошибки.

**В agent skills/instructions — смысл и неоднозначность:** разбор сообщения и issue/comments; формирование intent и criteria в `task.json`; запрос уточнений и конфликтов; оценка completeness/oracle/risk; semantic retrieval релевантного кода/docs и pattern discovery; impact map; план; выбор тестов/дизайна; интерпретация ошибок и изменений; semantic architecture delta и review. CLI может предоставить точный grep/file/symbol search как инструмент данных, но не решает, какие совпадения релевантны. Не строить regex/fuzzy/“mask” эвристики, pretending to understand intent или скрытый auto-classifier внутри CLI.

Эта граница — зафиксированное направление проектирования, детали schema и команд ещё предстоит уточнить. Следующий раздел перечисляет конкретные формальные проверки, но не семантическую проверку смысла.

### Дополнительная capability: role-based model CLI

По уточнению пользователя в единственном корневом [манифесте](../../../Манифест агентной software factory.md) зафиксировано требование к CLI-клиенту, который вызывает несколько настроенных моделей через OpenAI-compatible API и маршрутизирует запросы по конфигу `role → model`. Это не изменение формата входящей задачи: role/model config — проектная конфигурация, а не дублируемые поля в `task.json`.

Рекомендуемая граница: лёгкий Python CLI client со списком providers/models, role mapping, limits/timeouts и secret references; shell — только wrapper. Skill выбирает роль, подготавливает смысловую инструкцию и контекст, а CLI маршрутизирует explicit call, возвращает/валидирует структурированный output и записывает call metadata/evidence. Если native subagents в основном runtime недостаточны, агент может запросить отдельное мнение/анализ у configured role.

Это **не эквивалент subagent runtime**: обычный OpenAI-compatible API не даёт автоматически изолированный workspace, собственные tools, permission boundary, durable state, pause/resume или handoff. На старте разумно делать только stateless model consultation без произвольного tool execution/code changes. Полноценный subagent runtime потребует отдельной спецификации.

**Оценка:** хорошая portability/fallback idea, но не обязательный этап каждого task. Основные trade-offs — дополнительная поверхность секретов и передачи кода/контекста провайдеру, cost/latency, неодинаковая поддержка параметров между «совместимыми» API и зависимость качества от role prompt/model. Нужно версионировать конфиг; хранить secrets вне repo/task JSON; allowlist ролей/models/параметров; ограничивать контекст, timeout/retry/cost; логировать provider/model/role/request ID/status/cost при доступности; валидировать JSON output shape. Вызовы и ответы считаются недоверенными результатами модели; основная модель/agent решает, как их использовать. Capability/eval tests должны проверять common API subset, structured output и отказные сценарии. Не строить custom proxy, пока нет отдельной нужды в централизованных credentials/policy/audit/rate limits.

### Session documentation skill и integrity CLI

Также пользователь поручил зафиксировать команду/skill **`задокументируй`**, доступную в любой момент текущего диалога. Она должна извлечь подтверждённые изменения/решения/evidence из сессии, определить активный task/stage и записать соответствующие изменения в task artifacts и затронутые canonical architecture docs; если работа идёт вне задачи — обновить только относящиеся к делу архитектурные разделы, не создавать task задним числом. Skill обязан различать реализованный факт, принятое решение, candidate/hypothesis и непроверенное; не переписывать исходный `task.json` snapshot незаметно и не заявлять о тестах без результата.

Architecture docs могут находиться в нескольких доменных папках. Предложено иметь общий machine-readable index и локальные индексы разделов. CLI integrity suite отвечает за структурную проверку/пересборку общего индекса, schema/frontmatter, уникальность IDs, ссылки/anchors, task/stage/artifact refs, cross-links task↔architecture history и известные release IDs/revisions. Он возвращает отчёт с file/path/JSON pointer и exit code. Он не определяет, какой документ релевантен новой сессии, и не переписывает семантическое содержание; это делает skill/агент, после чего CLI повторно валидирует структуру.

Это хорошо сочетается с прежним split: `task.json` — структурированный canonical task input; skill — смысловая маршрутизация/редактирование; CLI — проверяемые filesystem/index/link/task integrity операции. Требует позже специфицировать schema индекса, registered docs roots и link/task reference grammar; не означает, что команды уже реализованы.

### [ОБСУДИТЬ] Типизированные операции редактирования документации и их необходимость

Не делать CLI обязательным посредником для каждой Markdown-правки и не вводить CRUD-команды для всех видов документации без подтверждённой пользы. Для короткой правки прозы прямое редактирование Markdown агентом/человеком может быть проще. Типизированная операция (например, add/update glossary term или flow) оправдана, если она даёт конкретную детерминированную гарантию: schema/required fields, уникальность ID и ссылок, атомарное применение patch, проверку base revision/conflict и точечную запись без перегенерации всей страницы. Агент по-прежнему определяет смысл, выбирает сущность и готовит содержимое; CLI не классифицирует смысл и не генерирует canonical content самостоятельно.

Инструмент сам по себе не экономит LLM tokens. Сравнивать следует полный контекст, output patch, число вызовов/итераций и ошибки: прямое редактирование вероятно проще для одиночной Markdown-правки, CLI потенциально полезнее для повторяемых структурированных обновлений и проверки связей. Открытый пункт workflow: на tabletop walkthrough сопоставить необходимость/выгоду прямого редактирования и узких типизированных CLI-команд; фактические токены, latency, число итераций и частоту ошибок измерять только в будущем отдельно одобренном пилоте, выполнив все pilot prerequisites. Это сравнение пока не является решением о реализации CLI write API.

## 8. Что автоматизировать формально, а что оставить содержательной проверкой

### Детерминированно проверять

- JSON parse и `schema_version`; JSON Schema structural validation.
- Безопасность path/key: source ID не допускает traversal/подмену каталога; запрещённые characters/normalization.
- `source.kind` известен адаптеру; обязательные conditional fields присутствуют.
- Acceptance criteria не пусты для task kinds, где они требуются; каждое criterion имеет ID и, где поддерживается, способ проверки.
- Локальные ссылки на project docs/contract существуют; branch/release целевой выбор разрешён project configuration.
- Ссылки на внешний issue соответствуют `source.kind` adapter allowlist; credentials никогда не попадают в JSON/logs.
- Изменения code/spec/API contract сопровождаются определёнными проверками; CI evidence привязана к commit/ref.

### Не выдавать за автоматическую гарантию

- JSON Schema не поймёт, проверяемо ли предложение «сделать быстрее».
- Сходство названия задачи и acceptance criteria не доказывает, что агент верно понял user intent.
- Agent self-report не является независимым test oracle; test green не гарантирует соответствие неформализованной потребности.
- `last_verified`/timestamp не доказывает, что архитектурная заметка ещё соответствует коду.
- Наличие ссылки на ADR не означает, что решение актуально или approval получен.

Для содержания полезен brief completeness/review pass: intent, границы, edge cases, negative constraints, criteria↔oracle, ownership/approval и references. Вопросы надо задавать только по неоднозначностям, которые меняют решение/риск/проверку, а не проходить длинный generic questionnaire на каждый тикет.

## 9. Открытые вопросы до спецификации ядра

1. Как именовать task namespace/path при совпадении source IDs, переименовании Jira project или дублирующей ручной постановке?
2. Нужен ли отдельный внутренний UUID сейчас или можно начать с `source.kind:source.id` и мигрировать позднее?
3. Для каждого source — какие поля/статусы являются authoritative, как брать revision/snapshot, attachments и edits после начала выполнения?
4. Какие именно JSON-поля required/conditional для разных task kinds, и какой минимум source snapshot нужен каждому tracker?
5. Где хранятся mutable execution state, logs/evidence, branch/commit/PR refs, resume checkpoints и approvals?
6. Кто назначает release target и branch: requester, project config, release owner или adapter? Что делать, если target не указан/уже закрыт?
7. Какие поля required для bug, feature, docs, refactor, security issue? Нужны ли в MVP разные task kinds или один базовый contract?
8. Как определить acceptance oracle и условия завершения для документационных, performance, migration и security задач?
9. Какие approvals обязательны до изменения кода, PR, merge, deployment или внешнего эффекта; как статус approval проверяется технически?
10. Какая schema/version migration policy и backward compatibility для уже созданных task artifacts?
11. Что фиксировать в project context, чтобы агент быстро ориентировался, но не загружал лишнее; как определять stale docs и владельца?
12. Как документировать изменённое поведение после завершения: обновлять существующую canonical spec в том же PR, создавать delta proposal только для существенных изменений или иной способ?

## 10. Рекомендованный следующий артефакт (не пилот)

Следующий шаг — подготовить **draft contracts**: (а) минимальная project documentation schema/tree и правила авторитетности, (б) `task.json` JSON Schema + CLI command/side-effect contract + agent skill responsibilities и mappings из Jira/другого tracker/chat. Затем вручную/tabletop пройти несколько сценариев: bug из Jira, request из другого tracker, chat task, неоднозначная задача с блокирующим вопросом, release-specific change, отказ/approval. Это проверка полноты модели, не запуск агента и не empirical pilot. Сценарии должны выявить пропуски: source identity, repeat submit, task edits, attachments, missing criteria/oracle, approval, branch, resume/evidence, doc update, а также каждую операцию, которую CLI может выполнять детерминированно без semantic inference.

Практический прогон не предлагается до согласования workflow и его контрактов. Когда позже будет проектироваться реальный pilot, остаются обязательными условия: подходящий репозиторий, acceptance oracle, достаточно надёжный CI, изолированный sandbox, определённые owners/approvals, baseline/eval set и stop/rollback path. Это отдельный этап, не результат данного desk research.

## Ограничения ресёрча

Это desk research по официальным документациям, методикам и опубликованным engineering reports; не проведены практические прогоны инструментов, интервью с владельцами Jira/трекеров, usability test templates, измерение completeness/authoring effort, security audit или acceptance test of a schema. Утверждения авторов продукта/внутренних engineering reports не являются независимым доказательством эффекта. Обзор описывает практики и аргументы за/против. После уточнения пользователя зафиксированы как требования к проектированию: task.json — единственный canonical task input, отдельный hand-authored task.md не нужен; детерминированные операции принадлежат CLI, смысловые — агенту через skills/instructions; role-based model CLI может служить опциональным stateless fallback, если native subagents поддерживаются плохо; skill `задокументируй` и CLI integrity checks записывают session changes и проверяют общий индекс/task links. Это не означает, что уже утверждены конкретные JSON Schema, список CLI-команд, дерево проекта, lifecycle state model или vendor selection; multi-agent future architecture не проектируется на этом этапе.
