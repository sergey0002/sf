# Инструменты агентной среды

> [!info] Определение
> Практическая карта инструментов для управления агентами от задачи до релиза.
> Сначала определите capabilities и границы, затем выбирайте инструмент, а не наоборот.
> См. [[Harness-инжиниринг]], [[Сквозной цикл разработки]].

## Архитектурные слои и варианты

| Слой | Для чего | Примеры | Ключевой выбор |
|---|---|---|---|
| Work intake | Issue → задача агента | GitHub Issues/Projects, Linear, Jira | Задача структурирована и проверяема? |
| Agent runtime | Планирование и tool loop | Claude Agent SDK, OpenAI Agents SDK, LangGraph, Strands, OpenHands | Managed vs self-hosted; single vs multi-agent |
| Coding environment | IDE/CLI/async coding | Claude Code, Codex, OpenCode, Kilo, Cursor, Devin | Локально или headless; интерактивно или очередь |
| Orchestration | Durable workflow, retries, approvals | Temporal, Inngest, GitHub Actions, platform-native orchestration | Нужны ли durable state и human gates? |
| Isolation | Выполнение недоверенного кода | E2B, Docker, Firecracker-based microVM, ephemeral cloud runners | Уровень изоляции + egress controls |
| Context/code intelligence | Поиск, символы, архитектура | LSP, Sourcegraph, GitHub code search, repo maps, MCP | Точный symbol lookup + свежесть индекса |
| Policy/identity | Разрешения и правила | GitHub environments, OIDC, RBAC, policy-as-code | Кто/что может читать, писать, деплоить? |
| CI/verification | Build, test, scans | GitHub Actions, GitLab CI, Buildkite, Jenkins; SAST/SCA/DAST | Неподконтрольно агенту, одинаково для всех PR |
| Delivery | Promotion/rollback | Argo CD, Argo Rollouts, Flux, feature flags | GitOps, progressive delivery, rollback |
| Telemetry/evals | Traces, quality, cost | OpenTelemetry, Langfuse, Opik, Inspect AI, Harbor | Vendor-neutral traces + reproducible evals |

## Рекомендуемый reference stack (минимальный)

1. **Issue template** с objective, scope, acceptance criteria, risk tier и rollback.
2. **Planner → implementer**; план фиксируется в issue/PR до широких изменений.
3. **Ephemeral sandbox** на задачу, отдельная рабочая копия/ветка; no production credentials.
4. **Repo map + module context + LSP**; агент ищет существующее решение до создания нового.
5. **PR — boundary of trust**: diff, tests, logs/evidence, provenance, owner review.
6. **Independent CI**: clean runner, required checks, security scans, test suite.
7. **Environment-gated deploy**: staging → canary → production; approval и автоматический rollback.
8. **OpenTelemetry trace** связывает task/PR, agent/session, model, tool calls, tests, deployment.
9. **Eval suite** проверяет качество workflow на репрезентативных задачах перед сменой prompt/model/tooling.

## GitHub Actions: важные controls

- Явно задавать минимальные `GITHUB_TOKEN` permissions per job; например `contents: read` там, где нужна только проверка исходников, и расширять только по конкретной необходимости.
- Pin third-party Actions на full commit SHA; ревью и обновление pinned hashes.
- Для cloud auth — OIDC + short-lived scoped credentials, не постоянные ключи.
- `pull_request_target` и secrets: не исполнять код недоверенного PR с привилегированным токеном.
- Deployment environments: required reviewers, prevent self-review, branch restrictions, wait timers.
- Self-hosted runners не считать изолированными: untrusted workflows могут оставить persistence; предпочитать ephemeral clean runners и отдельные runner groups.
- Секреты становятся доступными только после approval защищённого environment; не передавать их coding agent в общем контексте.

## Sandbox: критерии выбора

- Понять границу: контейнер разделяет процессы, но обычно делит kernel; microVM даёт отдельный kernel.
- Network egress — deny-by-default или allowlist; отсутствие доступа к localhost/private endpoints.
- Credentials — short-lived, scoped, injected just-in-time; не в образе/репозитории/логе.
- Workspace ограничен; snapshot/cleanup гарантированы; нет общей файловой системы между задачами.
- Есть session logs, resource limits, timeout, kill/rollback; проверять доступ агента к публичному интернету.
- Учитывать supply chain: package registry proxy, lockfile, package allowlist/reputation checks.

> [!warning] Изоляция ≠ сетевая безопасность
> Изолированная VM может иметь открытый интернет и эксфильтрировать данные через публичный сервис.
> Проверяйте egress, а не только filesystem/compute isolation.

## OpenTelemetry для агентных прогонов

Рекомендуемая модель: единый trace с spans для `invoke_agent`, LLM/model call, tool call,
sub-agent/workflow, verification и deployment. Correlation fields: task ID, PR/commit SHA,
agent name/version, model/provider, tool name, environment, eval result. Измерять latency,
token/cost, tool failures, retries, test outcomes, policy denials и rollback.

**Не логировать по умолчанию** prompt/response с секретами и персональными данными.
Настроить redaction, ограничение доступа и retention. GenAI semantic conventions OpenTelemetry
пока имеют статус Development — зафиксировать версию схемы и контролировать обновления.

## Инструмент подбирать по задаче

| Сценарий | Хороший старт | Что не делегировать |
|---|---|---|
| Один разработчик, локальные изменения | IDE/CLI coding agent + LSP + существующий CI | Merge и secrets |
| Массовые issue-задачи | Headless runtime + очередь + ephemeral sandbox + PR automation | Self-approval |
| Мульти-репо / monorepo | Repo index/code search + module context + ownership | Неограниченный поиск по секретным репозиториям |
| Автоисправление CI | Triage/retry для transient; fix в PR для systemic | Изменение тестов/гейтов ради зелёного статуса |
| Agentic release | GitOps + environment approval + canary analysis | Production credentials у агента |
