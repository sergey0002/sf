# Ресёрч: альтернативы ТРИЗ для агентной разработки ПО

> [!abstract] Назначение
> Companion research register к [[Альтернативы ТРИЗ для агентной разработки ПО]]. Здесь отдельно
> записаны источники, что они поддерживают, границы применимости и уровень подтверждения. Практические
> workflow-рекомендации находятся в отдельном документе; они не являются результатом controlled trials
> сравнения методик на многоагентной разработке.

## Выводы по evidence

Для углублённого обзора каждой отдельной теории/инструмента ТРИЗ и подробного соответствия аналогам см. [[Ресёрч по теориям ТРИЗ и аналогам для агентных систем]] и практическую карту [[ТРИЗ и аналоги: карта методов для агентной разработки]]. Этот файл остаётся реестром источников первоначального сравнения методик.

1. **QAW, ADD и ATAM имеют наиболее прямое предметное соответствие software architecture.** SEI/CMU
   описывает их роли как elicitation quality requirements, design driven by quality attributes, and
   analysis of architectural risk/tradeoffs. Источники — официальные описания метода и кейсы; они дают
   хорошую спецификацию процессов, но сами по себе не доказывают сравнительную эффективность против
   иных процессов или улучшение output агентной разработки.
2. **DMAIC и PDCA/A3 хорошо документированы как process-improvement cycles.** ASQ/Lean Institute
   описывают назначение и шаги; эффект зависит от валидности baseline/измерений, причинного анализа и
   организационного контроля. Это не доказательство, что каждый bugfix должен проходить формальный
   DMAIC.
3. **Double Diamond — рамка для problem discovery/design iteration, а не техническая процедура и не
   root-cause model.** Это явно оговорено Design Council. Она полезна при неопределённости user need;
   не подтверждает correctness/performance/security инженерного решения.
4. **GMA структурирует многомерное qualitative problem space.** Авторский источник подробно объясняет
   параметры/конфигурации/consistency assessment. Комбинации — формальные design hypotheses, не
   эмпирически установленные решения; dimension choice, consistency judgement и explosion ограничивают
   полноту.
5. **SIT — TRIZ-derived toolkit.** Официальный источник описывает свои инструменты, но является
   поставщиком метода; не рассматривать как независимое сравнение/верификацию эффективности. Часть
   инструментов концептуально родственна ограничениям и принципам ТРИЗ.
6. **Нет найденной прямой независимой head-to-head оценки этих методов для многоагентной software
   factory.** Поэтому нижеследующая рекомендация является синтезом соответствия задачи и метода плюс
   локальной инженерной практики; предполагаемую эффективность надо проверять на собственных evals.
7. **Использование agentic coding demos/repos — свидетельство реализуемости конкретной техники, не
   доказательство процесса:** код/документация показывает, что implementation существует, но не
   изолирует эффект метода, baseline, репрезентативность, потери, качество и стоимость.

## Шкала статуса утверждений

| Статус | Значение |
|---|---|
| **Официальное описание метода** | Подтверждает, как автор/организация определяет метод; не доказывает универсальную эффективность |
| **Peer-reviewed / technical report** | Более формальное описание/анализ; качество зависит от дизайна исследования, выборки и внешней валидности |
| **Case report / application example** | Показывает применение в одном контексте, обычно без причинного сравнения |
| **Vendor / method-owner claim** | Полезно для идентификации инструмента/процесса; заинтересованный источник, не независимая проверка |
| **Практический синтез** | Рекомендация для применения; явно требует local evaluation, если речь об эффекте |
| **Не установлено** | Источники не позволяют делать соответствующий вывод |

## Источники: software architecture methods

### 1. SEI QAW / ATAM

**Barbacci et al. (2002), _SEI Architecture Analysis Techniques and When to Use Them_, CMU/SEI-2002-TN-005.**

- URL: https://www.sei.cmu.edu/library/sei-architecture-analysis-techniques-and-when-to-use-them/
- DOI/persistent record: https://doi.org/10.1184/R1/6583727.v1
- Тип: официальный SEI technical note.
- Использовано для: разграничения QAW и ATAM; QAW elicitation quality scenarios до полной архитектуры;
  ATAM после появления design artifacts для выявления risks, sensitivity points, tradeoff points.
- Достаточно подтверждает: назначение/шаги/условия применимости методов в SEI framework.
- Не подтверждает: точность предсказания production behavior без прототипа/измерений; преимущество над
  любой альтернативой; benefit в agentic development; универсальную окупаемость фасилитации.
- Уверенность: **высокая в корректности описания метода**, **низкая/не установлено для magnitude of
  outcome effect** на произвольной software team.

**Kazman, Klein & Clements, _ATAM: Method for Architecture Evaluation_, CMU/SEI-2000-TR-004.**

- URL: https://www.sei.cmu.edu/documents/629/2000_005_001_13706.pdf
- Тип: SEI technical report/method specification.
- Использовано для: ATAM lifecycle, quality-attribute scenario analysis, risks, sensitivity and tradeoffs.
- Граница: архитектурная evaluation фасилитируется экспертами и использует сценарии; ATAM не сводит
  достоинства architecture к единому объективному числу и не исполняет application benchmark.
- Статус: official method report; методические claims, а не head-to-head RCT.

### 2. Attribute-Driven Design (ADD)

**Kazman & Cervantes, _ADD 3.0: Rethinking Drivers and Decisions in the Design Process_ (SEI/SATURN 2015).**

- URL: https://www.sei.cmu.edu/documents/5832/ADD.3.0.Final_ki9IsLf.pdf
- Тип: авторский/SEI методический материал.
- Использовано для: iterative decomposition; design objectives, functional/quality drivers, constraints,
  concerns; selecting design concepts, instantiating elements and recording decisions.
- Граница: выбросить quality-attribute drivers из consideration нельзя, но quality scenarios тоже не
  полностью определяют правильную архитектуру; тактики и decisions всё ещё требуют технического знания.
- Статус: сильная спецификация процесса, ограниченное доказательство comparative effect.

**SEI, _Integrating Software-Architecture-Centric Methods_ и _Architecture-Centric Methods into XP_.**

- URLs: https://www.sei.cmu.edu/documents/734/2004_005_001_14396.pdf ; https://www.sei.cmu.edu/documents/2056/2004_004_001_14348.pdf
- Тип: SEI technical papers, включают кейсы и process guidance.
- Использовано для: взаимоотношения QAW → ADD → evaluation; linking scenarios, tactics, views and
  architecture decisions; ограниченные примеры применения в организации/software projects.
- Граница: кейсы иллюстрируют применение/артефакты; без сопоставимого control group не изолируют
  причинный вклад метода и не обобщаются на агентную работу.

## Источники: problem framing and improvement

### 3. Double Diamond

**Design Council, _The Double Diamond_.**

- URL: https://www.designcouncil.org.uk/resources/the-double-diamond/
- Тип: авторитетный primary account (Design Council разработал/распространяет модель).
- Использовано для: Discover/Define/Develop/Deliver; divergence/convergence; важная оговорка, что Double
  Diamond — визуальное описание процесса, а не универсальная пошаговая инструкция.
- Граница: design framing не равен causal diagnosis, technical architecture analysis или product outcome
  evidence. Официальный источник — описательный, не независимое испытание модели.
- Уверенность: высокая в определении; outcomes на конкретном продукте нужно оценивать локально.

### 4. DMAIC

**ASQ, _DMAIC Process_.**

- URL: https://asq.org/quality-resources/dmaic
- Тип: ASQ quality-method reference.
- Использовано для: Define, Measure, Analyze, Improve, Control; предназначен для улучшения существующего
  процесса с measurable gap, baseline, analysis and sustainment.
- Граница: это методическое описание. Наличие пяти фаз не гарантирует достоверной причинности;
  flawed instrumentation, confounding, selection effects и нестабильное workload портят вывод.
- Статус: сильное свидетельство общепринятого назначения метода; не источник для обещания конкретного
  ROI в software/agents.

### 5. A3 / PDCA

**Lean Enterprise Institute, _A3 Report_.**

- URL: https://www.lean.org/lexicon-terms/a3-report/
- Тип: Lean organization reference.
- Использовано для: A3 как структурированное problem-solving/dialogue artifact и evidence narrative,
  не только page-size report.
- Граница: официальное практическое описание; локальные causal outcomes не измеряет.

**Lean Enterprise Institute, _How to wipe out technical debt with PDCA_.**

- URL: https://www.lean.org/the-lean-post/articles/how-to-wipe-out-its-technical-debt-with-pdca/
- Тип: practice article / example.
- Использовано для: пример переноса PDCA в IT technical debt work.
- Граница: illustrative case; не controlled comparative study и не обязательное решение для каждого
  refactor.

### 6. Theory of Constraints (TOC)

**Lean Six Sigma Groep, _What is the Theory of Constraints?_**

- URL: https://leansixsigmagroep.nl/en/lean-agile-and-six-sigma/theory-of-constraints-uk/
- Тип: practitioner secondary explainer, не первоисточник и не peer-reviewed efficacy study.
- Использовано для: формулировки five focusing steps и оговорки inertia; практический источник также
  связывает constraint analysis с DMAIC.
- Граница: сама страница не подтверждает причинный throughput gain в software development. Для formal
  TOC deployment добавить первоисточник Goldratt/Goldratt Institute и domain-specific empirical evidence.

Практическое содержание в документе: identify/exploit/subordinate/elevate/repeat; software delivery
mapping к queues, lead time, WIP и throughput — **синтез**, не вывод из контролируемого DevOps study.
Не считать источники достаточным support для сильных эмпирических claims; локально строить flow metrics.
Если цитировать throughput claims, проверить исходную выборку, метрики, comparison group, organizational
context и publication bias.

## Источники: risk / failure analysis

### 7. FMEA/FMECA

**NASA Goddard, _Failure Modes and Effects Analysis (FMEA) / FMECA Handbook_.**

- URL: https://standards.nasa.gov/sites/default/files/standards/GSFC/Baseline/0/GSFC-HDBK-8004_Approved_0.pdf
- Тип: engineering handbook / formal guidance.
- Использовано для: system decomposition, failure modes, effects/causes, severity/occurrence/detection,
  actions/ownership and document control.
- Граница: handbook guidance, а не доказательство полноты списка; scoring can be ordinal/subjective;
  software-only hazards, interactions and common-cause failures требуют соответствующей модели.
- Практический вывод: FMEA помогает структурировать известные риски; не заменяет security threat modeling,
  fault-tree/system safety analysis или тесты.

### 8. Threat modeling

В практическом руководстве указана как соседняя практика, не как один формально сравниваемый метод.
Для product-specific risk work следует добавлять первичные документы выбранной модели (например, официальные
security framework/version, scope, trust boundaries and data classifications). В этом исследовании прямой
head-to-head efficacy claim не делается.

## Источники: idea generation / design space

### 9. General Morphological Analysis (GMA)

**Ritchey, _General Morphological Analysis: A general method for non-quantified modeling_.**

- URL: https://www.swemorph.com/ma.html
- Тип: авторская методическая статья (Tom Ritchey; morphological analysis practitioner).
- Использовано для: formalizing non-quantified problem via parameters and possible values; constructing
  configuration space; cross-consistency assessment to eliminate incompatible combinations.
- Граница: набор параметров и consistency ratings задают эксперты; output depends on framing and does not
  constitute statistically representative solution search. Formal consistency != empirical validation.
- Уверенность: высокая в объяснении процедуры; efficacy in a specific software architecture task requires
  pilot and comparison.

**Ritchey, _Morphological Analysis and Bayesian Networks_.**

- URL: https://www.swemorph.com/pdf/mabn.pdf
- Тип: method paper linking qualitative configuration spaces to Bayesian-network reasoning.
- Использовано для: дополнительного разграничения configuration space from probabilistic/causal evidence.
- Граница: Bayesian layer requires defensible conditional probabilities/evidence; adding a probabilistic
  notation does not cure weak input evidence.

### 10. Systematic Inventive Thinking (SIT)

**SIT official website, _The Method_.**

- URL: https://www.sitsite.com/method/
- Тип: method-owner/vendor primary description.
- Использовано для: terminology and tools in SIT, Closed World / Function Follows Form; selection as
  short constrained ideation toolkit.
- Граница: interested source; does not independently establish effect size, transfer to software agents, or
  superiority against TRIZ/design thinking/brainstorming. SIT is TRIZ-derived, therefore not a theoretically
  independent replacement.

### 11. QFD / House of Quality (not central recommendation)

**ASQ, _House of Quality_.**

- URL: https://asq.org/quality-resources/house-of-quality
- Тип: quality reference.
- Potential use: translate voice/customer needs to technical characteristics and priorities.
- Scope decision: not promoted as primary method in the practical guide because QAW already serves explicit
  software quality-attribute scenario elicitation and the user’s highest-risk need is software architecture /
  agent systems. Could be useful in product discovery/industrial requirement prioritization.
- Evidence caveat: tool page explains method; selection still depends on organizational context and validation.

## Источники: agentic software practice / implementation repositories

> Эти ссылки показывают pattern or runnable implementation/specification, а не доказанную эффективность
> методологии. Репозитории меняются; перед внедрением сверить состояние, security posture, license и commit.

### 12. SEI-method implementation exemplar

**rtym/sei-architecture-methodology**

- URL: https://github.com/rtym/sei-architecture-methodology
- Тип: community repository.
- Возможная ценность: prompts/artifacts/workflow scaffold для QAW/ADD/ATAM и трассируемой архитектурной
  работы.
- Ограничения: community project, не SEI endorsement и не peer-reviewed evaluation; проверить commit,
  license, quality, model dependencies and fit. Наличие prompts не подтверждает fidelity или outcomes.

### 13. Agent-run orchestration exemplar

**openai/symphony**

- URL: https://github.com/openai/symphony
- Тип: vendor/open-source prototype/specification (repository may evolve).
- Ценность: отдельные issue-oriented agent runs, orchestration lifecycle and inspectable execution model.
- Ограничения: implementation/example, не evidence for superiority of any listed method. Vendor-produced; test
  against local security, cost, reliability and maintenance needs.

### 14. Context engineering exemplar

**langchain-ai/context_engineering**

- URL: https://github.com/langchain-ai/context_engineering
- Тип: vendor/community pattern collection.
- Ценность: examples of selecting, writing, compressing and isolating agent context; implementation
  inspirations for artifacts in QAW/ADD process.
- Ограничения: educational/pattern repository, not comparative benchmark. Not proof that all patterns improve
  task success; adapt to our existing [[Управление контекстом многоагентных систем]] and local eval.

## Сравнительная карта: какой вопрос источники реально покрывают

| Метод | Источники подтверждают | Не подтверждают автоматически |
|---|---|---|
| QAW | Elicitation/prioritization of quality scenarios | That stakeholders named the right objective; quantified outcome improvement |
| ADD | Iterative architecture design from drivers/scenarios | That selected tactic is correct without evidence/prototype |
| ATAM | Structured identification of architecture risks/tradeoffs | Measured runtime quality or universally better architecture |
| Double Diamond | Discovery/definition and iterative solution-space framing | Root cause, technical correctness or causal product impact |
| DMAIC | Existing-process improvement cycle and phase logic | Valid causes from weak data; agent productivity gains |
| A3/PDCA | Structured problem-solving and check/adjust loop | Complete causal account from concise narrative |
| TOC | Focusing-step logic for a system constraint | That an apparent local queue is global constraint without flow evidence |
| FMEA | Structured failure-mode/risk inventory | Exhaustive risks, accurate ordinal score, elimination of hazard |
| GMA | Multidimensional qualitative configuration analysis | Empirical validity/probability of candidate configurations |
| SIT | Method owner’s structured ideation tools | Independent efficacy/superiority; independence from TRIZ |
| Agent repos | Working code, spec, or examples exist | Repeatable benefit, security, quality, total cost, cross-org transfer |

## Итоговая интерпретация для пользователя

- **Архитектура / tradeoffs:** QAW → ADD → ATAM — наиболее прямо соответствуют задаче и лучше всего
  поддержаны domain-specific методическими источниками. Доказательность здесь — прежде всего
  method-specification, не causal effectiveness trial.
- **Неясная пользовательская потребность:** Double Diamond на discovery/definition, затем QAW/test plan
  для technical constraints.
- **Повторяющийся measurable defect/process problem:** A3/PDCA для единичной короткой итерации;
  DMAIC для больших вариативных процессов с данным baseline. Выбор — прагматическая адаптация,
  не оценка универсального превосходства.
- **Queue/throughput:** TOC как диагностическая линза; в этом research register прямые первичные ссылки
  намеренно помечены как недостаточные, поэтому не делать heavy claim до пополнения библиографии.
- **Высокий impact / safety:** FMEA и threat modeling как complementary inventories/analysis; никаких
  claims полноты.
- **Candidate generation:** GMA для явно многомерного design space; SIT для короткой эвристической
  ideation, с оговоркой происхождения от TRIZ. Обе — generators, не verifiers.
- **Agentic execution:** все документы/рекомендации практического гайда — architecture/workflow synthesis.
  Не утверждать, что multi-agent role split повышает качество по определению. Проводить локальные evals,
  randomized/repeated where feasible, measure quality/cost/review burden, retain independent policy gates.

## Ограничения исследования и план валидации

### Что не было установлено

- Нет общего taxonomy/benchmark, который сравнивает все методы на одной серии реальных software tasks.
- Нет найденного независимого controlled study, изолирующего эффект QAW/ATAM/ADD, DMAIC, Double Diamond,
  GMA или SIT конкретно для многоагентной разработки.
- Method-owner pages и vendor repos имеют интерес/selection bias; case studies имеют confounding;
  publication bias и разные единицы успеха мешают переносить проценты.
- Автоматически извлечённые architecture docs, agent memory, incident narratives и generated evals
  могут быть stale, hallucinated, unauthorized или biased; источник/commit и reviewer обязательны.
- Для efficiency нужны полные затраты: model/token, CI, context maintenance, facilitator, reviewer/incident
  rework, opportunity cost; заделать новые gates может снизить throughput при наличии safety benefit.

### Рекомендуемый локальный протокол

1. Задать конкретный use case и baseline; не сравнивать abstract methodology labels.
2. Сформировать representative tasks из прошлых PRs/incidents, включая negative cases and high-impact risks;
   зафиксировать ground truth, repo commit и модель/toolchain.
3. Сравнить текущий workflow и минимально достаточное изменение: например, plain ADR vs QAW+ADD; A3 vs
   unstructured debugging; manual context map vs context-builder variant. Не обязывать каждую задачу к полной
   методике.
4. Предварительно зарегистрировать primary outcome, non-regression/security guardrails, cost, rubric, stopping
   rule, repetitions; blinded independent reviewer там, где возможен judgment bias.
5. Для nondeterministic agents — несколько прогонов, фиксированный snapshot, randomized order, report range/
   uncertainty. Отделить benchmark tuning data от held-out cases.
6. Roll out в shadow/canary с explicit rollback; не использовать небезопасные варианты для live learning.
7. Сохранить raw artifacts, run IDs, prompts/model versions, code diff, results/reversals; запретить implementation
   agent редактировать acceptance threshold/verifier в той же change path без независимого review.
8. Решать о расширении по многомерному результату: quality + safety + cost + time-to-review + maintenance.
