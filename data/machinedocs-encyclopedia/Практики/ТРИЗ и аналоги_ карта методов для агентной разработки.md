# ТРИЗ и аналоги: карта методов для агентной разработки

> [!abstract] Задача документа
> Раскрыть не только «40 принципов», а основные семейства инструментов классической ТРИЗ и отдельно
> показать, какие параллели/аналоги полезны для software- и multi-agent engineering. Соответствия
> ниже — функциональные аналогии, не утверждение, что методы эквивалентны или одинаково подтверждены.
> Источники, ограничения и оценки evidence вынесены в [[Ресёрч по теориям ТРИЗ и аналогам для агентных систем]].

## 1. Сначала таксономия: ТРИЗ — не одна техника

В общей структуре TRIZ Body of Knowledge выделяются базовые понятия/философии, теория развития систем,
ARIZ, substance-field analysis / standards, contradiction techniques (matrix, 40 principles, separation)
и scientific effects. В прикладной работе часто добавляют function analysis, trimming, resources, system
operator, cause-effect chain analysis и другие operators. Это разные инструменты с разными входами:

- contradiction tools — целевые конфликты между характеристиками;
- system/function/resource analysis — понять систему и выбрать leverage point;
- Su-Field/standards — моделировать тип взаимодействия и типовые трансформации;
- ARIZ — полный итеративный маршрут для сложных проблем, не synonym для contradiction matrix;
- trends/evolution/system operator — исследовать развитие во времени и на уровнях system/subsystem/supersystem;
- scientific effects / function-oriented search — найти исполнимый механизм из другого домена;
- IFR/ideality — задать направление и ограничить цену решения, но не обещать «решить всё бесплатно».

**На практике:** для мелкого defect достаточно reproduction + regression test; для архитектурного выбора
работать с quality scenarios/ADR; для хронической сложной проблемы применять только те стадии TRIZ или
аналога, которые меняют качество решения. Большой ритуал не равен большей доказательности.

## 2. Схема выбора по природе задачи

| Тип неизвестного | Подход TRIZ | Наиболее полезный аналог в ПО | Роль AI-агента |
|---|---|---|---|
| Какие требования/quality goals конфликтуют? | Contradiction analysis; IFR | QAW/ADD/ATAM, QFD для потребностей | Извлечь кандидаты требований и evidence; owner приоритизирует |
| Что именно в системе причиняет вред? | Function analysis, Su-Field, cause-effect chain | Tracing/code graph, RCA/A3, fault tree, FMEA | Собрать связи/таймлайн/тесты; не «объявлять root cause» по тексту |
| Как сформулировать сложную invention problem? | ARIZ | QAW + ADD + ATAM либо A3/DMAIC + design review | Заполнить структурированные черновики, предлагать reformulation |
| Как обойти physical contradiction? | Separation principles | Scope/condition/time separation, isolation, tiered policy | Показать варианты разделения; не изменять полномочия самостоятельно |
| Какие design concepts попробовать? | 40 principles/matrix, standards, SIT | Design patterns/tactics, morphological analysis, Double Diamond | Генерировать механизмы по разным prompt families |
| Можно ли сделать архитектуру проще/идеальнее? | IFR, resources, function analysis, trimming | dependency audit, simplification, TOC, platform/architecture fitness | Найти candidates и cost; build owner проверяет инварианты |
| Куда развивать систему? | system operator, evolution trends | architecture roadmap, scenario planning, fitness functions | Составлять сценарии и наблюдаемые indicators, не предсказывать уверенно |
| Как проверить, что идея работает? | ARIZ solution analysis; knowledge reuse | TDD/property tests, benchmark, experiment, canary | Подготовить независимый eval; не менять acceptance oracle |

## 3. Противоречия и 40 принципов: генератор поисковых направлений

### Что теория предлагает

Техническое противоречие описывает ситуацию «если изменить систему так, чтобы получить A, возникает
нежелательное B». Классическая матрица связывает пары из набора инженерных параметров с принципами,
которые авторы ТРИЗ извлекали из патентных аналогий. Ценность инструмента — организованный поиск
механизмов решения, а не автоматическое вычисление наиболее подходящего решения.

### Перенос в ПО: не маппить по имени параметра

Для software агентства полезнее сделать локальную contradiction record:

```yaml
id: CTX-14
improvement_goal: increase recall of relevant architecture constraints
worsening_effect: token_cost, latency, distraction, stale-context risk
mechanism_hypothesis: global context dump raises recall but lowers precision and freshness
workload: 40 representative cross-module change tasks
invariants: [ACL isolation, pinned source commit, no writes without PR]
```

Здесь параметры — измеримые outcomes, не попытка назвать token budget «массой». Только когда есть
правдоподобный mechanism и репрезентативное измерение, есть смысл генерировать решения.

### Параллели и практическое применение

- **SIT / ASIT:** облегчённые, TRIZ-derived prompts. Подходят как короткая сессия ideation для заданной
  системы; не независимая теория, не причинная диагностика.
- **Morphological analysis:** подходит, когда нужно сравнить комбинации способов retrieval, memory scope,
  permission, update owner and verification. Хорош для разнообразия альтернатив, не для каузального ответа.
- **SEI architecture tactics/patterns:** более software-native библиотека конкретных mechanisms для availability,
  performance, modifiability/security. В контексте software architecture обычно ближе к реализации, чем
  исходная 39×39 matrix.
- **Double Diamond:** дивергировать варианты только после того, как user problem определена; его discovery
  не заменяет инженерное тестирование.

### Agent workflow

1. Два read-only агента формулируют конфликт независимо, с metric/baseline pointers.
2. Системный владелец подтверждает цель, границы и реальность worsening effect.
3. Generator-агенты получают разные solution spaces (remove/partition, change control flow, state/data
   model, verification/operations), а не дублируют один список 40 principles.
4. Отдельный reviewer объединяет дубликаты и отмечает механизм каждого варианта.
5. Human owner выбирает prototype; verifier на закреплённом benchmark + regression suite.

**Не использовать:** число сгенерированных принципов, несколько совпавших LLM outputs или «матрица
посоветовала» как evidence за design.

## 4. Physical contradiction и separation: условно разнести противостоящие свойства

### Что теория предлагает

Physical contradiction формулирует, что один объект/параметр требуется в несовместимых состояниях.
Устранение часто ищут, разделяя состояния по времени, пространству, условию, компонентам/частям и
целому, или вынося конфликт на иной system level. ТРИЗ формулирует этот набор через устройство задач,
а не как список architecture styles.

### Software / multi-agent applications

| Конфликт | Separation option | Concrete system mechanism | Проверка |
|---|---|---|---|
| Agent должен иметь широкий контекст для recall, но узкий для privacy/cost | по пространству/актору | tenant/repo scoped retrieval; separate context views | ACL negative tests; retrieval recall by role |
| Агенту нужно автономно писать, но нельзя менять policy/прод | по условию/действию | sandbox worktree write; policy files read-only; approval gate for promotion | permission matrix + denied-action tests |
| Полная документация нужна для редкой задачи, но вредна всегда включённой | по времени/условию | progressive disclosure / on-demand context | held-out retrieval eval, cost, omission rate |
| Контекст должен быть shared для координации, но не конфликтовать | parts/whole | shared immutable task artifact + private scratchpads per worker | provenance, collision/rebase eval, stale snapshot check |
| Быстрый путь для простых задач и строгий для критичных | by condition/risk tier | deterministic risk router; tiered approval and eval policy | adversarial boundary tests; escalation recall |
| Model can suggest action, but trust boundary blocks direct effect | by system level | proposal agent → deterministic policy executor → owner approval | tool authorization tests, audit logs, no model-only bypass |

Разделение здесь не метафора ради творчества: оно превращается в access boundaries, runtime routing,
data contracts и explicit conditions. Условия должны быть не soft model instruction, а enforced policy,
если речь о безопасности/необратимых действиях.

## 5. IFR и идеальность: направление, не безусловная оптимизация

IFR полезен как способ поставить вопрос «может ли полезный результат прийти без дополнительного элемента,
издержки или вреда?». В software engineering сформулируйте его как observable outcome плюс ограничения.

**Плохо:** «агенты сами доставляют production-quality код мгновенно без затрат и ошибок».

**Лучше:** «на задачах класса A агент правильно находит impacted modules/required tests в ≥X случаев,
не получает cross-tenant data, не меняет protected policy, PR проходит независимо сформированные checks,
а reviewer effort и CI/model cost не превышают установленный budget; при uncertainty/escalation не пишет».

### Аналоги

- **QFD / Voice of Customer:** проверка, что target отражает реальную потребность, а не внутреннее удобство.
- **QAW quality scenarios:** перевод «идеально» в source/stimulus/environment/artifact/response/measure.
- **SLO/fitness functions:** закодировать часть критериев в runtime/CI checks.
- **Value engineering / cost-of-quality:** учитывать эксплуатационные издержки и нежелательные функции.

Идеальность не одно число. Не оптимизировать только PR throughput/correctness/token cost: multi-agent system
имеет целевые outcomes, guardrails and risk constraints. Избыточный контекст, инструменты и гейты имеют
maintenance cost; лишние жесткие требования могут замедлять и фрагментировать систему.

## 6. ARIZ — аналитическая процедура сложной проблемы

ARIZ-85C — многошаговая процедура (версия под названием 85C не сводится к «85 действий»). В её ходе
проблема упрощается до mini-problem/problem model, создаётся ресурсная модель operating zone/time,
формулируются IFR и physical contradiction, применяется knowledge base, а при блокировке происходит
reformulation/switch of problem. После концепта предусмотрены проверка и перенос решения. По исходному
документу MATRIZ это повторяемый research process; авторы требуют простых формулировок и нескольких циклов.

### Аналогия для software architecture: QAW → ADD → ATAM (не полная замена ARIZ)

- QAW уточняет quality needs и priorities.
- ADD итеративно строит architecture из quality drivers, functions, constraints.
- ATAM выявляет риски, sensitivity points, tradeoffs на design.
- Реальные incidents/process variations требуют A3/DMAIC; user discovery — Double Diamond; ideation может
  использовать TRIZ/SIT/GMA.

Эта связка близка к части ARIZ (problem framing → design → evaluation), но не следует полному TRIZ model
и не ищет автоматически physical contradiction or standards. Хорошее применение — сложное решение,
где можно привязать decisions к scenarios, прототипам, tests and risks.

### ARIZ-like task graph для multi-agent team

1. **Evidence retrieval:** read-only agents привязывают claims к repo SHA, traces, incidents, user feedback.
2. **Problem framers (2+):** создают independently competing problem models, помечая fact/hypothesis.
3. **Facilitator/owner:** согласует boundary, objective, constraints, stop conditions.
4. **Modeling agent:** строит function/data/trust-flow diagram и resource inventory.
5. **Idea agents:** alternatives by diverse search operator; separate physical-separation path from technical tradeoff.
6. **Red-team critic:** falsification, missed stakeholders, failure combinations, constraints.
7. **Human decision owner:** выбирает candidate + test or rejects framing.
8. **Bounded implementer:** selected hypothesis only, isolated branch, no policy/test-threshold edits.
9. **Independent verifier:** clean tests, architecture/security gates, perf evaluation.
10. **Learning curator:** creates reviewed ADR/eval regression; not an autonomous policy editor.

Каждый agent stage — candidate aid. Слишком дробная схема для простых bugs увеличивает latency/cost and
hand-off errors; использовать dynamic depth by risk/uncertainty.

## 7. Function analysis, Su-Field, cause-effect chains: понять mechanism

### Функциональная модель

Функциональный анализ описывает components/actors, action and object, useful/insufficient/excessive/harmful
interactions, границы и operating zone. Для ПО удобно строить несколько дополняющих графов:

- static dependencies: module/import/call/API/data ownership;
- dynamic execution: traces, queues, retries, event flow;
- control/trust: identities, tools, permissions, untrusted data, promotion path;
- user/value path: request → interaction → user outcome.

Не сводить один граф к единственной «истинной» системе. Static code graphs не раскрывают runtime
routing/intent/authorization; traces не показывают всех редких branches.

### Su-Field model (Substance–Field)

Классическая модель — две «substances» и взаимодействующее поле, используемая для типизации полезного,
вредного, недостаточного или чрезмерного взаимодействия и выбора стандартов. Буквальные substance/energy
аналогии подходят не ко всему software. Для agentic system осторожно адаптировать в типизированный
interaction model: actor/tool/data object + information/control/action channel + effect; отдельно сохранять
trust boundary and side-effect. Для например `retrieval-agent → returns stale policy chunk → coder writes
unauthorized config` модель должна показать не абстрактное «поле», а точную source version, retrieval path,
permission and resulting write.

### Аналоги и где они сильнее

- **Distributed tracing / call graph:** реконструировать наблюдаемую execution path.
- **RCA + causal graph / fault tree:** проверять причинные ветви и combinations.
- **FMEA / threat modeling:** перечислять отказ/угрозу, effect, controls and residual risk.
- **Data-flow and taint analysis:** source/sink, propagation, sensitivity; более конкретно для security.
- **Datalog/architecture rules/fitness functions:** executable enforcement for known graph properties.

ТРИЗ модель — генератор вопроса «что именно взаимодействует и как изменить», но у агента её нужно
синхронизировать с runtime evidence. Один LLM-нарратив не является graph truth.

## 8. Resource analysis, function trimming, system simplification

TRIZ ресурсные списки включают ресурсы system/subsystem/supersystem, space/time, substances/fields,
information/function, waste and available/underused capabilities. Trimming asks whether an element or its
function can be removed/combined/transferred while retaining useful outcome. Для ПО это сильная практическая
параллель к code simplification, dependency removal, dead-code analysis, operational load reduction.

**Candidate resource inventory для agent factory:** existing contracts/tests, branch/worktree isolation,
owner metadata, cached build artifacts, feature flags, unused scheduler capacity, telemetry, data access,
review expertise, user feedback. Resource is not free if it introduces operational cost, risk, licensing,
privacy exposure or new coupling.

**Trimming questions:**

1. Does this component/function change an observable outcome?
2. Can caller or platform perform function safely (transfer) with tests?
3. Can function disappear by changing interface/requirement/process?
4. Is intermediate component redundant, or is it enforcing a hidden trust/quality boundary?
5. What new coupling, ownership, availability, performance, blast radius or migration risk follows?

**Analogs:** TOC (reduce avoidable work at constraint); dependency/code audit; design-by-contract; API
surface reduction; value-stream mapping; YAGNI/deletion with regression checks. “Trimming” must never mean
remove audit/security safeguards because their immediate output looks indirect. Have owner review scope.

## 9. Cause-effect chain analysis and root-cause finding

TRIZ cause-effect chain analysis expands from a negative effect through contributing causes, using a chain
of why/useful-harmful functions, and seeks a root problem that is actionable. It is adjacent to RCA but not
identical to empirical causal inference. In distributed software, prefer plural contributing causes; beware
single-root-cause fallacy and hindsight.

**More evidence-oriented analogues:** incident timeline, blameless postmortem, fault-tree (top event → logic
combination), DMAIC Measure/Analyze, causal graph, change-point analysis and controlled experiment.
**Agent use:** collect traces, code changes, test history and incident reports; propose multiple causal paths
with evidence links and falsification tests. Owner verifies; never accept “five whys” or fluent narrative
without direct signal.

## 10. 76 Standard Solutions and function transformations

76 standards are a structured library of transformations to common Su-Field problem classes; they are not
76 code design patterns nor all-purpose prompts. Use only after an explicit interaction model is available.
Software translation might be policies/mechanisms such as add mediator/feedback, introduce controlled
subsystem, make interaction measurable or shift to higher/lower system level. Those are prompts to inspect
architecture patterns and security controls, not direct prescriptions.

**Agent process:** map interaction → label inadequate/harmful/useful-but-insufficient effect → generate
candidate transformations → translate each into a software mechanism (e.g. typed mediator, deduplication,
contract validation, queue, rate limiter, policy check) → test semantics, failure modes, observability and
performance. At each translation, domain owner confirms no hidden invariant was lost.

**Analogs:** architecture tactics/pattern catalog, security control catalog, design patterns, API contracts,
reliability patterns, FMEA controls. Unlike standards, these are domain-specific and may be directly
implemented/tested; their exact match matters.

## 11. System operator / Nine Windows and system evolution trends

Nine Windows considers subsystem/system/supersystem × past/present/future. It can expose interfaces,
resources, different stakeholders and time horizons missed by file-level coding task. In agentic engineering,
create windows for: model/agent/tool, orchestration factory, repository/platform, team/user/organization;
then past/current/future or pre-incident/current/target states. Do not force nine boxes when a simple dependency
map answers the issue.

Evolution laws/trends can prompt questions: rising dynamism, transition to supersystem, increasing ideality,
mono→bi→poly, interaction field changes, trimming/convolution. They are not validated deterministic laws for
software roadmaps. Treat each as possible scenario, attach leading indicators, explain counter-scenario and
revisit against data.

**Analogs:** architecture roadmap; system dynamics/causal loops; scenario planning; QAW/ADD/ATAM; service
blueprints; platform evolution/fitness functions. System operator is spatial-temporal structuring; causal-loop
analysis is directional hypothesized influence. They complement but are not equivalent.

## 12. Scientific effects and function-oriented search

Classical TRIZ uses effects knowledge bases to search for a physical/chemical/geometrical mechanism that
performs target function. In software analogue, search for algorithms, protocol capabilities, database/index
operations, hardware primitives, existing modules, and architectural tactics. Crucial difference: in software
repository a mechanism can often be benchmarked/verified directly; a general science effect does not itself
implement product behavior.

Agent pipeline: encode target function and constraints → search approved source/doc/repo index → retrieve
algorithm/pattern candidates with provenance → generate a tiny prototype → property/benchmark/security test.
Avoid model knowledge recall as sole proof of library API, capability, licence or performance. Pin version and
verify source.

## 13. SIT and GMA: modern lightweight idea-search parallels

### Systematic Inventive Thinking (SIT)

SIT is a compact TRIZ-derived method. Commonly described tools: subtraction, division, multiplication, task
unification and attribute dependency (terminology differs among SIT/ASIT sources). It is easy to expose as
short prompts: remove an element, split component/state, duplicate an element carefully, assign a second task
to existing component, make dependency adaptive. Use for constrained ideation, not diagnosis. Because it shares
lineage/concepts with TRIZ, comparing both as independent theories is inappropriate.

### General Morphological Analysis (GMA)

GMA structures multidimensional qualitative configurations and uses cross-consistency assessment to remove
incompatible pairs. Unlike contradiction analysis, it need not assume there is one central contradiction or
causal chain. Use when architecture choice spans context source × retrieval × memory scope × update owner ×
permissions × verification; reduce dimensions using hard constraints; maintain rationale for compatibility
judgments; prototype shortlisted combinations.

The CCA is not causal inference/probability estimation. An AI can enumerate combinations and apply explicit
machine-checkable incompatibilities, but expert judgment remains necessary for semantic compatibility.

## 14. Analogues catalog: when it is the primary method

| Method | Prefer it over TRIZ when… | TRIZ can supplement by… |
|---|---|---|
| QAW/ADD/ATAM | quality attributes and software architecture are central; need scenarios, design tactics and risk review | Generate alternatives for a confirmed architecture conflict |
| QFD | product/customer needs need traceable prioritization to technical measures | Resolve a technical conflict after need validation |
| Double Diamond | problem itself is uncertain, user research is needed | expand options after definition |
| A3/PDCA | incident/rework needs a short evidence-and-countermeasure loop | propose mechanism-level countermeasures |
| DMAIC | recurring variation and metrics make statistical diagnosis useful | ideate improved mechanism after Analyze |
| TOC | queues and system throughput show a likely constraint | explore removal/transfer/partition alternatives at constraint |
| FMEA/FTA/threat model | safety/security/failure modes and controls dominate | add candidates to prevent/mitigate mechanism |
| GMA | space of combinations is broad, multidimensional and qualitative | add conflict-specific solution transformations |
| SIT | short facilitator-led ideation is desired; time/training budget small | broader tools if problem remains stuck |
| TDD/property testing/fitness functions | need executable acceptance and non-regression | create candidate mechanism; tests determine accept/reject |

## 15. Method selection as a multi-agent router

Use a router that assigns method based on **problem type + stakes + evidence readiness + cost**. This is not a
LLM free-choice: deterministic policy may require security review, protect assets and forbid unapproved tools.
The router should return method selection plus alternatives, confidence, missing inputs and reasons.

```yaml
problem_class: architecture-quality-conflict
suggested_route: QAW -> ADD -> ATAM
why: quality goals and existing cross-service design are implicated
required_inputs: [system_map, scenario_owner, workload_baseline, constraints]
optional_lenses: [TRIZ-contradiction, morphology]
stop_or_escalate_if: [no measurable success criterion, auth/data boundary unknown]
agent_permissions: read-only evidence gathering; no protected-policy writes
human_owner: platform-architecture
acceptance_oracle: independent quality-scenario tests and owner approval
```

### Recommended separation of agent roles

- **Fact gatherer:** code/data/dependency graph, source pointers, commit/version and traces.
- **Requirement elicitor:** questions/interview synthesis; no unilateral priority assignment.
- **Method analyst:** prepares a method-shaped model (contradiction, quality scenario, DMAIC baseline,
  morphological space, FMEA rows) with facts and hypotheses separated.
- **Alternative generator:** diversity across architecture/operation/product routes.
- **Adversarial reviewer:** attacks assumptions, identifies missing scenarios, privacy/failure coupling.
- **Experiment designer:** writes held-out eval/sample/metric/guardrail/rollback before implementation.
- **Implementer:** bounded approved hypothesis only.
- **Independent verifier:** tests on clean state; cannot be same unreviewed agent modifying oracle.
- **Knowledge curator:** reviewed ADR/eval/context update with staleness and provenance.

Scale role count to risk. For small changes, one engineer/agent plus strong tests is often more reliable than
complex role-play with repeated summaries.

## 16. Outcome evaluation for each method

| Stage | Measure |
|---|---|
| Framing | owner-rated frame correctness; unresolved factual claims; false assumptions |
| Search | unique mechanisms after dedupe; relation to constraints; search coverage, not idea count alone |
| Architecture | quality scenario coverage; risks/sensitivity points identified and closed; invariant violations |
| Diagnosis | causal claims confirmed vs rejected; recurrence and false localization |
| Safety | unauthorized data/action; adversarial case escape; policy bypass; incident/rollback |
| Outcome | task/user value, defect recurrence, reliability/performance, change failure, maintainability |
| Cost | engineer/facilitator/reviewer time, LLM/tool cost, CI, context maintenance and extra latency |
| Learning | regression/eval examples gained; stale/contradicted knowledge deleted or superseded after review |

Before/after comparison must control model, repository commit, task mix and test environment as far as
possible. For stochastic agents use repeated runs and independent review; disclose uncertainty. A method can
be useful on high-risk framing despite increased time: measure value as well as efficiency.

## 17. Anti-patterns across theory and analogues

- Equating TRIZ with 40 principles, or applying the matrix to every agent task.
- Calling QAW/ATAM/TOC/FMEA “TRIZ” merely because they can be combined with TRIZ.
- Treating SIT as independent corroboration of TRIZ.
- Treating an architecture graph, causal diagram, matrix or checklist as data instead of model.
- Promoting generated source-code analysis, FMEA scores, evidence summaries or future trend as verified truth.
- Making general performance claims based on vendor case studies or a single team pilot.
- Choosing a method because it has many terms/templates rather than matching the question.
- Letting same model produce requirements, code, tests, thresholds and final verdict without independent gates.
