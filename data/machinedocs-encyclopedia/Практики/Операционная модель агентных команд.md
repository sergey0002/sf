# Операционная модель агентных команд

> [!info] Определение
> Организационные, платформенные и процессные условия, при которых coding agents
> повышают полезный delivery outcome, не перегружая ревью и не снижая стабильность.
> DORA подчёркивает роль окружающей среды и организационных возможностей, а не только выбора модели.
> См. [[Сквозной цикл разработки]], [[Evals и метрики агентной разработки]], [[Инструменты агентной среды]].

## Семь возможностей DORA для AI-assisted development

| Capability | Практическое применение для агентной команды |
|---|---|
| Clear, communicated AI stance | Approved tools, границы данных/действий, роли и эскалация |
| Healthy data ecosystem | Актуальные, качественные API/contracts/docs/ownership |
| AI-accessible internal data | Контролируемый доступ к коду, runbooks, ADR и knowledge base |
| Quality internal platform | Paved roads: sandbox, CI, templates, approved MCP/tools, telemetry |
| Strong version control | Малые коммиты/PR, review, rollback, traceability |
| Working in small batches | Маленькие задачи, быстрый CI, ограниченный blast radius |
| User-centric focus | Outcome и feedback пользователя важнее числа сгенерированных строк |

DORA сообщает, что AI усиливает существующие сильные и слабые стороны организации; трактовать
это как исследовательскую ассоциацию, а не гарантию причинного эффекта конкретного инструмента.

## Роли и ответственность

| Роль | Владеет | Не должен делегировать агенту |
|---|---|---|
| Product/task owner | Intent, acceptance, приоритет, scope | Ответственность за ценность/приоритет |
| Agent platform owner | Runtime, sandboxes, identities, logs, eval harness | Разрешение обходить guardrails |
| Code owner | Архитектура, локальные правила, review | Approval своего чувствительного изменения при конфликте интересов |
| Security owner | Threat model, policy, incident response | Финальная оценка риска high-impact изменений |
| Release owner/on-call | Promotion, canary, rollback | Production accountability |
| Agent | Ограниченные исследования/изменения/предложения | Самостоятельное расширение scope/permissions |

## План внедрения

### 0. Baseline и инвентаризация

- Составить inventory агентов, моделей, IDE plugins, MCP servers, skills, CI workflows.
- Измерить текущие lead time, review queue, batch size, failed deployments, rework/incidents.
- Выбрать workflow с повторяемыми задачами и понятным test oracle.
- Зафиксировать forbidden paths/data/actions и owner.

### 1. Assisted

Человек сохраняет исполнение и решения; агент предлагает патчи, тесты и документацию.
Проверить, что измеряется качество предложений и cost на принятое изменение.

### 2. Bounded PR automation

Агент в отдельной ветке/ephemeral sandbox создаёт draft PR; merge остаётся человеку.
Required CI, provenance, review templates и fallback должны быть настроены.

### 3. Workflow automation под policy

Автоматизировать только обратимые low-risk действия (например, ограниченная классификация/retry).
Действия с секретами, инфраструктурой, permissions, production promotion — отдельный approval path.

### 4. Continuous improvement

Сэмплировать traces/PRs, пополнять eval dataset, устранять повторяющиеся причины ошибок.
Каждый change model/prompt/tool/sandbox — versioned, eval-gated и откатываем.

## Entry criteria для пилота

- [ ] Точное описание задачи и acceptance oracle
- [ ] CI детерминирован/достаточно надёжен для пилота
- [ ] Sandbox и разрешения ограничены; credentials не shared/long-lived
- [ ] Code owners и human review capacity определены
- [ ] Stop/rollback owner и incident path известны
- [ ] Baseline и eval set заморожены до запуска
- [ ] Политика использования данных и выбранного провайдера одобрена

## Exit / scale criteria

Масштабировать только если пилот показывает приемлемое качество и безопасность на заранее
определённой выборке, reviewer throughput выдерживает, нет неприемлемого роста rework/incidents,
а cost per accepted outcome понятен. Если task completion растёт, но очередь ревью или escaped
incidents тоже растёт — это не готовый успех; уменьшить batch size/автономность и усилить feedback.
Числовые пороги задаются командой по её baseline и риску, универсального порога нет.

## Dashboard без vanity metrics

| Измерение | Примеры |
|---|---|
| Flow | Lead time по стадиям, review wait, blocked time |
| Quality/stability | Change failure, escaped defects, rework/churn |
| Agent effectiveness | Accepted-on-first-review, task eval pass rate, retries |
| Safety | Policy violations, unauthorized actions, secret incidents, egress denials |
| Cost/capacity | Cost per accepted change, review minutes, CI/sandbox spend |
| Human experience | Interruptions, confidence calibrated to outcomes, satisfaction |

Показывать срезы вместе; не использовать индивидуальные PR/token counts как performance ranking.

## Operating cadence

- **Еженедельно:** ошибки пилота и review bottleneck, sampled diff review.
- **При изменении модели/инструмента:** offline regression + adversarial evals до rollout.
- **Ежемесячно:** permission/tool inventory, incident/bypass review, cost и cohort analysis.
- **После инцидента:** preserve trace/diff/runner artifacts, revoke credentials, определить trust path,
  добавить регрессионный adversarial case и проверить восстановление.
